`step1_audit.py`はファイル選択・Excel読込・表示、`data_validation.py`は判定と集計、
`time_utils.py`は時刻変換を担当する。機械学習モデルやAPIからは、ファイルI/Oなしで
`audit_dataframe(data)`を利用できる。

## 判定の使い方

```python
from data_validation import audit_dataframe, summarize_audit

# dataは呼び出し側が用意したDataFrame
audited = audit_dataframe(data)
summary = summarize_audit(audited)
candidates = audited.loc[audited["学習候補"]]
```

元の行・インデックスを維持したコピーに、項目別の状態、比較可能性、不一致、取消、
重複、学習候補の列を付ける。`valid`、`missing`、`conversion_error`、`invalid_type`、
`non_finite`、`non_integer`、`out_of_range`、`total_mismatch`、`wait_mismatch`、
`time_reversed`、`cancelled`を区別する。
学習候補は取消以外で、人数・待ち時間が両方`valid`の行。
除外理由は重複し得るため、その件数の合計は学習候補外件数とは限らない。

時刻は同日として計算し、23:00を超える受付・案内を範囲違反とする。
案内が受付より前なら、丸める前に時刻逆転として検出する。
待ち時間の比較には従来の整数分への丸めを使う。日付またぎの補正は行わない。

## Step 2: データ前処理・特徴量設計

設計理由と代替案は[ADR-0003](docs/adr/ADR-0003.md)を参照。

```python

# dataは呼び出し側が用意したDataFrame。生Excelをコミット・アップロードしない。
prepared = prepare_training_data(data)  # 天気は受付時点の値か未確認なので既定では除外

    ["学習候補", "日付検証結果", "前処理学習候補"]
].value_counts(dropna=False)
date_counts = prepared.metadata["日付"].value_counts().sort_index()

# 境界日は実際の営業日数・期間を確認して決める。変数は呼び出し側で指定する。
parts = split_by_date(prepared.metadata["日付"],
                      train_end=train_end, validation_end=validation_end)
X_train, y_train = X.iloc[parts.train], y.iloc[parts.train]

# 将来の予測も同じ変換を使う。案内時刻・待ち時間は不要。
prediction_X = build_features(reception_data)
```

初期のXは大人・子供・受付時刻（分）の3列と曜日の固定7列の計10列。予約由来の列、案内時刻、
待ち時間、取消、識別情報、日付そのものは含めない。目的変数はStep 1で記録値との
一致を確認した計算待ち時間（整数分への丸め）とする。

天気が受付時点の記録と確認でき、運用でも取得できる場合だけ、学習・予測の両方で
`weather_at_reception=True` を使う。天気の固定6列を追加し、欠損は「不明」、
辞書外の文字列は「その他」にする。天気を有効にした場合は計16列となる。
設定は学習と予測でそろえる。

日付は年付きの文字列または日付型を採用する。Excel数値シリアルは既定では拒否するが、
ブックの設定を確認して `excel_date_system="1900"` または `"1904"` を指定すると変換する。
例えば `prepare_training_data(data, excel_date_system="1900")` とし、数値日付を含む予測入力でも
同じ設定を `build_features()` に指定する。1900方式の60、小数部、範囲外は拒否する。

### 日付単位の検証と最終テストの隔離

`split_development_test()` が日付を昇順に整理し、最新2営業日を先に隔離する。
今回、本人が指定した最終テスト日は **2026-07-12・2026-08-07**。
特定の日付や226件という件数をモデルの処理には埋め込まない。
CLIの `--expected-test-dates` で、事前指定した日付との一致を確認できる。

残り12営業日を `expanding_date_folds()` で次の3foldに分ける。

| fold | 学習 | 検証 |
| --- | --- | --- |
| 1 | 最初の6営業日 | 次の2営業日（7〜8日目） |
| 2 | 最初の8営業日 | 次の2営業日（9〜10日目） |
| 3 | 最初の10営業日 | 次の2営業日（11〜12日目） |

行数比率では分けず、同じ営業日は同じ区間へ入れる。前foldの検証日は次foldの学習へ入る。
不完全な検証窓や日数不足ではエラーにし、余った日を無言で捨てたりランダム分割したりしない。
`compare_models()` へ渡すのは分離済みのdevelopmentだけ。各foldでモデルをcloneし、
Ridgeのスケーラーも学習行だけでfitする。検証データや最終テストをfit・early stoppingには使わない。
モデル比較・選定の判断には検証結果を使い、最終テストはモデル選択・重み調整にも使わない。
通常の比較CLIには最終テストの評価機能を追加せず、下記の専用CLIに分離する。

主要指標は検証MAE（分）。fold別の学習・検証MAE/RMSEとその差、検証営業日別の件数・MAE/RMSE、
fold間の等重み平均・標準偏差（`ddof=0`）、OOF全検証行をまとめたMAE/RMSE、営業日を等重みにした
MAE平均を返す。学習誤差は学習行自身への誤差であり、将来性能の見積りとは区別する。
営業日ごとの件数が異なるため、fold平均・OOF・日別平均も区別する。
3foldは学習期間が重なるため独立ではなく、標準偏差は信頼区間ではない。
14営業日という少なさを踏まえ、わずかな差だけで優劣を断定しない。

### 自動記録と状態

内部IDはUUID、表示番号はJST暦日ごとの `YYYYMMDD-001` 形式、受付順はDBの連番とする。
別接続の同時受付も `BEGIN IMMEDIATE` 内で採番・集計・保存し、一意制約で重複を防ぐ。
時刻はロック取得後に取得し、タイムゾーンなし・直前の記録より過去のシステム時刻は拒否する。
初期構成では推論もこのトランザクション内で実行するため、混雑時はロック待ちが発生し得る。

| 保存領域 | 主な記録 |
| --- | --- |
| `receptions` | ID・表示番号・受付順・受付日時・大人/子供/合計・状態・最新呼出時刻・案内/取消日時・実待ち分・取得元/記録時刻 |
| `reception_snapshots` | 本人を除く受付直前の未案内総数・前方組数・同人数帯の前方組数・1〜2/3〜4/5名以上の組数・取得元/取得日時 |
| `predictions` | 受付時の予測値または未取得理由・モデル版・注意文・判断日時・取得元。実績とは別保存 |
| `reception_events` | 登録・呼出・不在・復帰・案内・取消と状態変更前後・発生/記録日時・操作元 |
| `idempotency_keys` / `daily_counters` / `store_metadata` | 二重送信防止・日別採番・記録時刻整合性。DB版は`PRAGMA user_version`で管理 |

`waiting`（待機）、`called`（呼出中）、`absent`（不在）は未案内として待ち組数に含める。
`seated`（案内済み）、`cancelled`（取消済み）は除外する。
全未案内状態から案内・取消が可能。待機→呼出、呼出→不在、不在→待機/再呼出を許可し、
完了状態からの復帰は禁止する。同じ状態への再送は記録を増やさない。
前日の未処理組は翌日も残し、自動で取消・案内済みにはしない。

受付直前の総数と前方組数は初期仕様では同じ値になるが、混雑量と受付順の意味を分けて保存する。
スナップショットは後の案内・取消・新規受付でも書き換えない。
**受付順と案内順は別**で、後から来た2名組を先に案内できる。
「人数や席の空き状況により、ご案内順が前後する場合があります」という注意文を返す。
席の空き状況を取得しているという意味ではなく、現在は席・天気・予約等の推測値を保存しない。

案内時だけ `(seated_at - received_at).total_seconds() / 60` を実待ち分として保存する。
0分や秒を含む値も記録できる。呼出時刻からは計算せず、取消時は実待ち分を未確定のままにする。
閉店後や日付をまたぐ実際の業務記録も残せるが、既存の同日・23:00以下という学習候補契約は変えない。
新しい受付DB、特に待ち時間0分の記録は、現在のモデルへ自動的に混ぜない。
