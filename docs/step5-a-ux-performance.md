## 通信・操作・一覧更新

待機計測は初回を含む0〜60,000msの区間。ちょうど60,000msの更新も数える。各API応答は即時で、予測可能な値はテスト用フィクスチャ。実際の曜日・時間・モデル可用性による判定は引き続きサーバーが行う。

| シナリオ | 改善前 | 改善後 |
| --- | --- | --- |
| 初回 `/public/queue` | 1回 | 1回 |
| 初回 `/predict` | 0回 | 1回 |
| 待ち組あり、60秒の `/public/queue` | 13回 | 13回 |
| 待ち組あり、60秒の `/predict` | 0回 | 2回：初回＋60秒時点 |
| 待ち組なし、60秒の `/predict` | 0回 | 初回1回、0組確認後の追加0回 |
| 一覧不変、60秒の一覧全体置換 | 13回 | 1回：初回のみ |
| 標準人数で1組受付する操作 | 2回 | 2回 |
| 標準人数で連続2組を受付する操作 | 4回 | 4回 |
| 大人2名に変更して受付する操作 | 3回 | 3回 |
| 1組受付時の登録POST／公開一覧GET | 1回／2回 | 1回／2回 |
| 連続2組受付時の登録POST／公開一覧GET | 2回／3回 | 2回／3回 |

「標準人数」は既存どおり大人1名・子供0名。「受付する」→「この人数で受付する」の2操作で完了する。新しい確認ボタンは設けていない。

待ち組ありの連続受付で、人数選択から即座に確定した場合は、2組合計でも参考予測POSTはトップ初回の1回だった。人数選択で400ms待ってから確定した場合は最初の大人1名用が加わり合計2回となり、次のお客様ではキャッシュを再利用した。大人2名へ変更した場合はトップの結果を再利用して合計1回だった。予測応答を待つ操作や、予測成功を受付確定の条件にする処理はない。

公開一覧は従来どおり応答完了から5秒後に更新し、遅いGETを重複させない。受付成功後は即時に再取得する。通常のスタッフ操作の反映は次の5秒更新＋通信・処理時間であり、予測の60秒更新には依存しない。

予測は大人・子供の組合せごとに60秒保持し、最大32件に制限する。同じ人数で安定しているトップ画面の追加取得は約1分に1回で、5秒更新ごとの推論は行わない。人数変更は400ms待って最後の入力を取得する。4名表示は選択時に取得し、人数や表示が変わった古いリクエストは取り消す。待ち組数0を確認すると取得・定期更新を止め、0→待ち組ありの変化では改めて取得する。合計0人など無効な人数を選択中は、この変化があっても予測POSTを送らず人数選択の案内を保つ。

キャッシュによって参考値の取得から時間が経つ点は、取得時刻を示して補う。同じ人数の定期更新中は直前の数値と取得時刻を保ち「更新中」を添え、文字の切り替わりを抑える。再取得は15秒でタイムアウトし、失敗時には数値を消して表示不可を伝える。人数が変わった場合は別人数の古い値を表示しない。受付確定時の値は従来どおり受付APIがその時点で返す予測・スナップショットを使用する。画面用の丸めは参考表示だけで、APIの予測値やモデルは変更しない。

## 表示・コントラストの静的確認

1024×768・1366×768では、幅960px以上かつ高さ700px以上の2カラム規則が適用される。左に参考予測→待ち組数→受付ボタン、右に完了通知と一覧を置き、一覧内部をスクロールする。通知で左側の主要情報やボタンを押し出さない構造を確認した。

768×1024の縦向き、390×844のスマートフォンでは縦並びとなり、受付ボタンを画面下部に置く。通常文字は18px、予測値は大きく、ボタンの最小寸法は44px以上。短い画面や拡大時はページスクロールを許す。これらはHTML・CSSの規則の確認であり、実際の見切れ・文字配置・タッチ操作を検証した結果ではない。

CSSで使われる文字色と背景色23組をWCAGの相対輝度式で計算した。確認した全組が4.5:1以上。代表例は本文 `#27352e`／白 **12.84:1**、説明 `#536256`／ページ背景 `#f4f3ec` **5.81:1**、主ボタンの白／`#285b46` **7.85:1**、エラー `#8e271d`／`#fff1ec` **7.75:1**。無効ボタンも `#536256`／`#e8ece5` **5.40:1**。実ブラウザの描画・フォーカス表示・読み上げ順序は別途確認が必要。

## 実ブラウザでの比較手順

同じ端末・ブラウザ・DB・モデル・受付時刻条件をそろえ、READMEのローカル起動方法で画面を開く。

1. DevToolsのNetworkでキャッシュ無効、記録消去後に再読み込みする。HTML/CSS/JSの転送量・リクエスト数を記録し、Performanceで主要情報と受付ボタンが表示されるまでの時間を3回測る。改善前と比較するときは同じネットワーク・CPU条件を使う。
2. 待ち組ありで60秒待ち、`public/queue`は約5秒間隔、`predict`は初回＋約60秒後となることを確認する。待ち組なしでは初回後に予測が増えないことも確認する。
3. 標準人数で連続2組、大人2名、人数の連打、通信失敗からの再送を試す。受付を妨げる予測待ちがなく、登録が重複しないこと、通知中も次のお客様が開始できることを確認する。
4. スタッフ操作から一覧反映までの時間を測る。人数変更中や一覧スクロール中に更新しても、フォーカス・スクロール位置が不用意に変わらないことを確認する。
5. 1024×768、1366×768、768×1024、390×844で、予測可能／不可・長い一覧・呼出中／不在・完了通知・説明展開を確認する。文字サイズ200%でも主要操作に到達できることと、横向き通常表示の主要情報・受付ボタンに見切れがないことを確認する。

予測不可の曜日・時間、未配置モデル、待ち組数0では数値が表示されない。数値表示の確認はサーバーの既存予測条件を満たすデータ・時刻・モデルで行い、UI確認のために予測条件を変更しない。
