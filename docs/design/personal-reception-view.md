# 個別スマートフォン受付画面の設計案

2026-10-28。**将来向けの提案であり、今回の実装対象ではない。** スマートフォン画面、以下のAPI・テーブル、QR、LINE連携、外部公開は追加していない。現在のloopback・Host・Origin・スタッフ認証、Step 4のDB契約、固定RFとStep 3の評価結果を維持する。

## 既存契約と表示の意味

[ADR-0005](../adr/ADR-0005.md)、[受付ストア](../../reception_store.py)、[API](../../prediction_api.py)を前提とする。

- 表示番号はJSTの`YYYYMMDD-NNN`、内部IDはUUID、受付順は`reception_order`。日付をまたぐ未処理受付も残る。画面では「123番」を大きく、受付日を常に補足し、番号全体で識別する。
- 未案内は`waiting`・`called`・`absent`。呼出・不在でも待ち組数に含む。`seated`・`cancelled`は終了。スタッフ操作の呼出・不在・復帰・案内・取消をそのまま反映する。個別画面から状態を変更する機能は初期案に含めない。
- 登録直前の`snapshot`と登録時の`prediction`は保存済みの不変情報。`POST /receptions`の冪等再送は、状態変更後でも初回応答を返すため、最新状態の取得には使わない。

個別画面には「自分の番号・人数」「現在の状態」「受付順で自分より前にいる未案内組数」「受付時の参考待ち時間と取得時刻」を表示する。「人数や席の空き状況により、ご案内順が前後する場合があります。」も残す。

現在の前方組数は、本人を除く`reception_order < 本人の順番`かつ状態が未案内の受付を数える。前日分も含め、本人より後の受付は含めない。本人が終了した場合は`null`として「ご案内済み」「受付取消」を示し、0組待ちと混同しない。保存済みsnapshotは更新しない。自分より前の組が案内・取消になると減り、後着組が先に案内されても減らない。これは席への案内順の保証ではない。

現行RFの入力は人数・受付時刻・曜日で、待ち組数・空席数を含まない。前方組数の減少や経過時間から予測分を引かない。表示名は**「受付時の参考待ち時間（残り時間ではありません）」**とし、予測不可は「受付時は参考待ち時間を表示できませんでした」とする。状態取得のたびに推論せず、初回の予測値・時刻・注意文を保持する。

## 受付と端末を安全に紐づける

番号・UUID・公開一覧だけで本人認証しない。提案する権限は「一つの受付を読む」だけとし、短命・一度限りのランダムなQR引換トークンを、スマートフォンの読取セッションへ交換する。これは戸籍上の本人確認ではなく、引換権利を持つ端末への閲覧許可である。QRの盗撮・転送による先取りは残るため、店頭で本人だけに渡す運用と失効・再発行が必要になる。

発行元は将来認証する店舗端末またはスタッフ用サーバーとする。店舗端末にはサーバー管理の端末セッションを設け、**その端末が登録した受付**との対応を登録トランザクションに記録する。例として将来の`POST /kiosk/receptions`を設け、人数と同じ`Idempotency-Key`で既存の登録処理を利用し、認証済み端末との紐づけも同時に保存する。公開`POST /receptions`が返すUUIDを渡しただけで引換権利を発行してはならない。端末の所有記録がない既存受付は、スタッフが確認して発行する。ブラウザのJavaScriptにスタッフトークンや端末秘密鍵を埋め込まない。

トークンは暗号学的乱数で256ビット程度を生成し、DBには検証用ハッシュ・対象受付・発行端末・有効期限・使用日時・失効日時を保存する。初期案の引換期限は2分、セッション上限は24時間、受付終了後は30分で失効とし、店舗運用を確認して決める。午前0時だけを理由に終了させない。交換時は一つのトランザクションで未使用・未失効を検査し、消費とセッション発行を行う。再使用を拒否し、紛失時はスタッフが旧権利を失効して再発行する。交換応答が不明ならまずセッションを確認し、取得できなければ再発行を案内する。受付登録自体をやり直さない。

セッションは`Secure; HttpOnly; SameSite=Lax`の専用Cookieを使い、トークンの生値をlocalStorageに保存しない。全APIで対象受付との権限一致・期限・失効を検証し、交換回数を制限する。推測困難な乱数、サーバー側の権限・失効管理、HTTPSとCookie属性は[OWASPのセッション管理指針](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)を参照した設計提案である。

セッション交換を含む状態変更APIはJSON本文・許可Originを検証し、Cookie認証にはCSRF対策を適用する。`SameSite`だけに依存せず、店舗端末の登録・引換権利の発行・失効にも同じ方針を適用する。

QRは引換トークンをURLのfragmentに入れ、読込後すぐ`history.replaceState`で除去してPOST本文で交換する。fragmentも画面・履歴やJavaScriptから漏れる可能性があるため、外部スクリプト・解析サービスを載せず、CSP・`Referrer-Policy: no-referrer`を設け、本文・Cookie・トークンをログへ残さない。通常セッションをURLで受け付けない。印刷した受付票やスタッフによる手渡しなど、共有タブレットの即時復帰を妨げないQR受渡し方法を別途決める。今回は完了通知へQRを追加しない。

## 追加APIの案と更新負荷

以下は名称を含めて未実装。通常の個別読取APIには受付IDを入力させず、セッションから対象を解決する。

| API案 | 認証・用途 |
| --- | --- |
| `POST /kiosk/receptions` | 将来の端末認証。既存の人数制約・冪等登録を再利用し、端末と受付の対応を記録 |
| `POST /kiosk/reception-claims` | 端末認証＋所有確認。端末自身の登録だけを対象に引換権利を発行。受付を増やさない |
| `POST /personal/session` | 引換トークンを消費し、一受付限定の読取Cookieを発行 |
| `GET /personal/reception` | Cookie認証。本人の現在状態・前方組数と不変の登録時参考値を返す |
| `DELETE /personal/session` | Cookie認証＋同一Origin/CSRF対策。閲覧権限を失効しCookieを削除 |
| `POST /staff/receptions/{id}/claim` | 将来のスタッフ権限。確認後の再発行と旧権利の失効。公開APIにしない |

個別GETの最小応答は`display_number`、`total_people`、`status`、`current_ahead_groups`、`captured_at`、`queue_revision`と、`initial`内の登録日時・登録時前方組数・snapshot取得時刻・参考予測の状態/分/予測日時/モデル版/注意文とする。内部UUID、他組の一覧、スタッフ情報、操作履歴、実待ち分は返さない。人数内訳も初期案では不要。認証不正・期限切れ・失効は統一した401、過剰アクセスは429として、番号の存在を推測させない。DB失敗は503で成功を装わない。

画面表示中は前回完了から5秒後にGETし、重複取得しない。復帰時はすぐ取得、非表示中は停止、失敗時は最終更新時刻と「更新できていません」を表示して段階的に間隔を延ばす。終了状態を確認後は定期取得を止める。初期案ではSSE・通知配信を必須にせず、前方組数減少は通常、次の取得で反映する。これはブラウザ非表示中の即時通知を保証する設計ではない。

ETagと`If-None-Match`はメモリ内で管理し、個別情報の`no-store`を維持する。認証・失効確認を304より先に行う。revisionは本人の状態だけでなく、**他組の案内・取消等**も検知できる全体版とする。現在のイベント最大IDを基にした不透明な版を候補とし、将来の復元・訂正を考慮してDB世代も含める。本人の状態・前方集計・版を同じ読取トランザクションから返す。304では最後に確認できた時刻を更新し、一覧の再描画や再推論を行わない。現在のスタッフ状態変更トランザクションは短いまま保ち、HTTP待機や推論を追加しない。SSEは同時端末数・5秒更新の負荷を計測してから検討する。

## 記録と将来の動的残り時間モデル

既存の受付・snapshot・予測・状態変更イベントは活用するが、現行DBは`user_version=1`で自動移行しない契約である。将来の端末所有・引換・セッション用テーブルの追加は、別ADR、移行手順、バックアップ・復元試験を伴う変更とする。認証監査の保存期間は業務・学習記録と分け、失効済み認証情報は必要以上に保存しない。

独立した残り時間モデルには、予測した時点の受付状態・経過分・現在の前方組数/人数構成を、観測日時・記録日時・取得元・その情報が利用可能になった日時と共に記録する。空席など未取得の情報を0や推測で埋めない。特徴量観測と予測記録を別にし、後者には予測基準時刻、モデル版、出力、予測種別を保存する。現在の`predictions`を更新せず、登録時参考予測と動的予測を区別する。

正解は予測基準時刻から実際の`seated_at`までとし、呼出時刻で代用しない。取消・未案内は残り0分にせず、打切りとして評価対象と扱いを明示する。遅延記録・訂正も履歴で区別し、予測時に未取得だった後日の情報を特徴量へ混ぜない。同一受付の複数観測や同一営業日が学習・検証をまたがない時系列評価で、単純な基準モデルとのMAE、過小/過大予測、人数帯・曜日・経過時間別の誤差、区間予測を出す場合の被覆率を確認する。データ量と業務上許容できる誤差を確認するまでは表示しない。既存RF・Step 3の評価を置き換えない。

## LINE・外部公開の扱い

まず通常のWeb閲覧を独立させ、LINEミニアプリは将来の入口・本人セッションの連携アダプターとして検討する。LINEのユーザーであることと、特定の受付を閲覧できることは別なので、LINE利用時も店頭引換等による受付との紐づけが必要になる。クライアントが申告するプロフィールを信用せず、LINE連携時はサーバーでトークンと対象チャネル・期限を検証する。[LINE公式のユーザー情報取扱い](https://developers.line.biz/en/docs/liff/using-user-profile/)を確認した方針であり、現在はSDK・LINE API・チャネルを追加しない。表示名・写真・電話番号等は取り込まず、連携を採用する場合に限り最小の識別子と同意・解除方法を設計する。LINE通知やバックグラウンド更新の提供可否は別途検討する。

実スマートフォン接続には現在と別の公開環境設計が必要で、HTTPS、端末/スタッフ認証、アクセス制御、負荷制限、監視・バックアップ・保存期間を整備してから判断する。今回、localhostやOrigin/Host制限を緩めない。実装前の検証には、引換の先取り/再使用/期限切れ/再発行、他人の受付へのアクセス拒否、応答紛失、前日受付、案内順の入替、前方組の取消、失効後304の拒否、既存冪等登録の維持を含める。
