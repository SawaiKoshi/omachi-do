# Step 5-B: v2受付ストアの統合

## 対象と境界

`ReceptionStore`は既存v1と移行済みv2を扱う。新規DBは従来どおりv1を作成する。
v2の新規作成・アプリ起動時の移行・未知スキーマの修復は行わない。
既存ファイルが0バイトの場合も、破損の可能性があるため再初期化せず拒否する。

この工程では一時領域内の合成DBのみで書込みを検証した。実DB2件、バックアップ、
指定実験用DBには接続して更新せず、RF・Excel・前処理・特徴量・評価・モデル・UIも変更しない。
訂正API・スタッフ画面・操作IDを処理するAPIは追加しない。

## 移行コードの再レビュー

- SQLiteのrow factoryを`sqlite3.Row`にしても、整合性・メタデータ・保存値の検査が正しく動くようにした。
- 検証済みの登録情報ファイルがリンクへ置換された場合、別ファイルへ書き込まないよう保護した。
- スキーマ署名はSQL文字列リテラル内の空白を保持し、意味の異なる定義を同一視しない。
- 空テーブルの連番、日別採番の型、イベントの時刻逆転、受付前のイベント、
  スナップショットと記録上の待ち組数、受付用キーの人数を検査する。
- 移行実装ハッシュには共有検証モジュールも含める。

移行の明示コマンド・全旧列の型付き比較・12工程の例外注入・強制終了回復・バックアップ復元は維持する。
ファイル移行は引き続き[合成移行ラボ](sqlite-v2-migration-lab.md)内でのみ行う。

## 版とDB識別子の固定

`expected_schema_version=1`または`2`を指定すると、異なる版を拒否する。
省略時は既知の既存スキーマを識別するが、一度開いたストアはその版に固定する。
同じインスタンスが、後から置き換わった別版へ追従することはない。

既存ファイルの初期検査は読取専用接続で行い、列・CHECK・外部キー・インデックス・トリガーの定義、
SQLite整合性、履歴の再生結果を照合する。照合用の参照スキーマはメモリ内で構築し、対象DBへDDLを送らない。

各業務トランザクションでも、DMLの前に版・定義・設定を再確認する。
v2では`database_id/write_epoch`も初期値に固定する。別DBへの置換や世代変更を検出した場合は
ストアを再生成するまで拒否する。v1の凍結コードをv2へ接続した場合も、書込み前に失敗することを検証した。

## v2の通常操作

`staff_write_mode='legacy'`、`seat_corrections_enabled=0`を維持する。
新規受付・呼出・不在・待機への復帰・案内・取消の業務上の結果はv1と同じ。

| 操作 | revision | 監査イベント |
| --- | --- | --- |
| 移行済み既存受付 | 0 | 旧イベントのID・8列を保持し、`legacy_v1`のまま |
| 新規受付 | 0 | `registration_v2`、受付直後の状態JSON |
| 状態変更 | +1 | `staff_legacy_v2`、変更前後の状態JSONとrevision |
| 同状態への再送 | 不変 | 追加しない |
| 同じ受付キーの再送 | 不変 | 初回応答を返し、採番・推論・登録を繰り返さない |

状態JSONには`status/called_at/seated_at/cancelled_at/actual_wait_minutes/revision`を保存する。
更新は期待する現在revisionをWHERE条件に含め、行・時刻メタデータ・イベントを同じ
`BEGIN IMMEDIATE`トランザクション内で確定する。失敗時は全体をロールバックする。

受付時のID・番号・時刻・順番・人数は状態更新で変更しない。スナップショット・予測JSON・初回応答JSONも更新しない。
実待ち分は従来どおり元の受付時刻から案内時刻までを小数分で計算する。

履歴の検査では、旧履歴からの状態と呼出・案内・取消日時、実待ち、revisionを再生して現在値と比較する。
v2の前後JSONも照合し、`staff_v2`形式の履歴がある場合は、操作記録の対象・種別・revision・結果・要求ハッシュを確認する。
この検査は記録上の整合性を確認するもので、実際の接客状況が正しかったことの証明ではない。

## API互換性と非公開情報

HTTPルート・レスポンスモデルは変更しない。既存の`GET /queue`、`GET /public/queue`、
`POST /predict`、`POST /receptions`、スタッフ操作はそのまま使用する。

ストア自身の受付応答からもrevisionを除外し、初回受付応答の保存形式を維持する。
操作ID・監査JSON・DB識別子・世代・モードを顧客向け応答に追加しない。

凍結した`f470ddf`のストア、現在のv1、v2に同じ合成操作を行い、受付応答と保存JSONを比較する。
HTTPでは数値予測あり・モデル利用不可の両方を比較し、数値検証には学習不要の合成推定器を使う。
実モデルを変更せず、同じ予測処理へ渡る特徴量の列と値も比較する。

## 次の操作ID・revision保護への準備

現段階のスタッフ操作には永続操作IDがないため、`staff_operations`へ架空のIDや操作者を作らない。
同状態への再送が無変更になることと、操作IDによる冪等性は区別する。

`revision_required`では既存の`transition()`を、同状態への再送も含めて拒否する。
この判定は書込ロック内で、時刻や状態を更新する前に行う。
顧客の新規受付・予測・一覧表示は継続できる。訂正機能は無効のまま。

次工程では認証主体に結び付く操作ID、正規化要求の比較、期待revision・世代の検証、
再送結果の永続化を実装する。同一IDの再送を確認してから版を判定し、古い要求の再適用を防ぐ。
すべてのスタッフ更新経路が対応するまで、訂正機能を有効にしない。

訂正済み履歴の再生、訂正対象と周辺受付の品質隔離、レビュー権限、学習用抽出の強制除外は未実装。
通常の受付・案内記録を自動で学習許可にせず、既存モデルへも自動投入しない。

## 検証

```sh
.venv/bin/python -B -m pytest -q -W error
node tests/frontend/reception.test.mjs
git diff --check
```

同一キー・同時受付・競合する終端操作・イベント追加後とコミット直前の失敗を検証する。
不完全スキーマ、版の偽装、履歴欠落、前後JSONの不整合、DB/世代の置換は修復せず拒否する。
HTTPテストがサンドボックス内で進まない環境では、許可されたサンドボックス外実行で確認する。

2026-10-29の検証結果: Python **989 passed in 17.42s**（既存922件＋追加67件）、
JavaScript **111 passed**。移行ラボの112件も全件再実行した。
