# Step 5-B: 案内完了訂正APIと品質保留

## 実装範囲と保護条件

既存のv2スキーマ・追記専用監査・操作ID/revision/write_epochを利用する。
DDL、スキーマ版、移行コマンド、Random Forest、特徴量、推論処理、顧客UIは変更しない。
検証で更新するファイルは、一時ディレクトリ内の合成DBだけとする。
実DB・バックアップ・指定実験用DBを移行せず、スタッフモード・世代・訂正フラグも変更しない。

新しい訂正を実行できるのは、v2かつ`staff_write_mode=revision_required`、
`seat_corrections_enabled=1`の場合だけ。フラグの設定API・自動有効化は追加しない。
v1、legacy、訂正無効の場合は状態や操作台帳を変更せず409で拒否する。
過去に確定した同一操作の結果取得・再送は、無効化後も履歴の読取りとして扱い、再更新しない。

## API

| メソッドとルート | 用途 |
| --- | --- |
| `GET /staff/receptions/{id}/events` | 対象イベントID・元状態・記録時刻をスタッフが確認 |
| `POST /staff/receptions/{id}/seating-corrections` | 現在有効な案内完了を訂正 |
| `GET /staff/receptions/{id}/data-quality` | 品質問題と学習利用の保留状態を確認 |

全ルートに既存スタッフ認証・ローカル接続・Host・Origin制限を適用する。
操作結果は既存`GET /staff/operations/{operation_id}`で認証付きで再取得できる。
監査主体は共有認証を表す`shared_staff_token / shared-staff`で、個人識別ではない。
トークン自体やそのハッシュを台帳へ保存しない。

訂正本文は次の6項目のみ。復帰先や案内日時は受け付けない。

```json
{
  "operation_id": "ca7ba052-a415-4394-8821-12f102e10a95",
  "expected_revision": 1,
  "write_epoch": "6b176cfe-d7af-4c67-95c0-cb5d140db53d",
  "target_event_id": 2,
  "reason_code": "accidental_seating",
  "reason_detail": "案内完了を誤って押したため"
}
```

UUIDは非nilの標準表記へ正規化する。revisionとイベントIDはbool・文字列・小数を認めず、
SQLite整数の範囲に制限する。理由コードは`wrong_reception / accidental_seating / other`、
理由詳細はすべてのコードで空白のみを認めない1〜500文字とする。
理由の文字列はそのまま監査するため、内容変更は別の要求になる。

成功時の応答形式は既存の操作結果と同じ9項目で、`action=seating_correction`。
同一操作ID・同一正規化要求・同一主体なら、操作当時の保存済み本文とステータスを返す。
別受付・別対象イベント・別理由・別revision・別世代・別主体でのID再使用は409。
通常の案内操作と訂正操作の間でも、同じIDを使い回せない。

対象がない場合は404、古いrevision・世代・対象イベントは409を操作結果として保存する。
無効な入力・認証失敗・機能無効・DB障害は未確定操作として扱う。
不一致の保存結果を最新条件でやり直す際は、最新情報と新しい操作IDが必要。

## 訂正の原子性と履歴

書込トランザクションは`BEGIN IMMEDIATE`で開始する。
新規訂正では、既存履歴・品質問題の完全性を先に検査する。
対象が同じ受付の最新イベントであり、現在状態がseated、イベント種別がseated、
元状態がwaiting/called/absent、未訂正であることを確認する。

復帰先は対象イベントの`from_status`から決める。受付ID・番号・受付日時・順番・人数は保持し、
現在の`seated_at / actual_wait_minutes`をNULLへ戻す。`called_at`は元の記録を保持する。
revisionを1増やし、`seating_corrected`イベントへ訂正対象・理由・変更前後の状態を追記する。
元の案内イベントは更新・削除しない。移行済みのlegacy_v1案内イベントも、同じ条件で訂正できる。

状態更新、revision、訂正イベント、品質問題、操作結果のすべてを同じトランザクションで保存する。
コミット直前に全履歴を再生し、必要な品質問題と保存行が証跡・ポリシー・時刻まで完全一致することを確認する。
品質保存処理が例外を出さず一部を落とした場合も、成功にせずすべてロールバックする。
既存の外部キー・一意制約・追記専用トリガーも維持する。

訂正後の実際の案内は、新しい操作IDと現在revision/世代で実行する。
実待ち分の計算は従来どおり、元の受付日時から実際の案内日時までの差とする。
元の受付応答キャッシュ・予測JSON・スナップショットは、そのまま保存する。
古い案内要求の再送は元の成功結果を返すだけで、現在状態には適用しない。

## 品質保護ポリシー

`policy_version=seat-correction-v1`を使い、誤案内と訂正の間の**event_idの開区間**から影響を求める。
同じ日時のイベントもIDで順序を確定し、時刻の精度で取りこぼさない。

| 対象 | issue_kind | 判定 |
| --- | --- | --- |
| 訂正された受付 | invalidated_seating | 無効化した案内イベントを記録 |
| 区間中に登録された他の受付 | snapshot_context | 受付時の待ち組数・前方組数等が不正確な可能性 |
| 上記のうち登録直前の記録上の待ち組数が0 | prediction_gate | 誤案内による予測抑止の可能性 |
| 区間中に状態変更された他の受付 | workflow_impact | 呼出・不在・復帰・案内・取消・他の訂正による間接影響の可能性 |

prediction_gateの判定は、全イベントの状態を順にたどって登録直前のactive集合を求める。
待ち組数が正の値同士で変わる場合は、数値予測に影響したと推定しない。RFに待ち組数の特徴量はない。
workflow_impactは因果関係の断定ではなく保守的なレビュー対象であり、1受付1訂正につき関連イベントIDを全件保持する。

各問題は訂正イベント、対象受付、根拠イベント、ポリシー版、記録時刻に結び付ける。
複数の訂正が重なる場合も、原因ごとに別の問題として残す。
再案内によって保留を自動解除せず、保存済みスナップショットや予測も修正しない。

品質参照APIは、問題の有無にかかわらず`training_use=blocked`を返す。
レビュー・assessment・学習抽出はこの工程では実装しない。未対応のレビュー/assessment履歴があれば起動を拒否する。
問題が複数ある受付は全原因を保持し、一部の問題だけ消して学習許可とする経路は設けない。

**品質問題の記録だけで、将来の学習混入防止が完成したとは扱わない。**
SQLiteの自動学習利用は許可しない。将来の抽出では、全問題の最新レビュー、現在revision、
有効な案内イベント、イベント/問題/レビューの検査済み範囲が揃うことを必須にする。
未評価・未レビュー・未解決・古い評価は除外し、その条件を強制する抽出・認可処理が完成するまで停止を維持する。

## 必須シナリオの結果

| 時刻 | 操作 | 確認した結果 |
| --- | --- | --- |
| 18:00 | 001受付 | 元のID・番号・受付順・受付日時を保存 |
| 18:10 | 001を誤案内A | 現在待ち組0、誤った実待ち10分の案内イベントを保存 |
| 18:10:30 | 002受付 | 保存スナップショットの待ち組数/前方組数は0のまま |
| 18:11 | 001を訂正B | 001→002の受付順、現在待ち組2へ復帰。001の案内日時/実待ちを取り消し |
| 訂正後 | 古いAを再送 | 保存結果だけ返り、現在の001はwaiting、revisionは2のまま |
| 18:25 | 新IDで001を再案内 | 元の18:00受付から25分と記録。002のみ待機 |

訂正後に現存active一覧を受付順で集計すると、002の前方には001が1組含まれる。
既存APIにない「既存受付の前方組数API」は追加せず、内部集計で検証した。
002の保存済み前方組数0を1へ書き換えることはしない。
001にはinvalidated_seating、002にはsnapshot_contextとprediction_gateを記録し、再案内後も保留を維持する。
両受付の初回応答・予測JSON・スナップショット・採番情報は変更されない。

## 予測の安定性

既存PredictionServiceと特徴量生成は変更しない。
同じモデル・時刻・人数では、待ち組数が正である限り同じ特徴量を渡す。
誤案内で0組となると既存ロジックどおり予測を抑止し、訂正で回復した後の新しい要求では正常に推論する。
呼出・不在・訂正によって保存済み受付時予測を再計算しない。

合成推定器で、抑止前と回復後の特徴量バイト列・予測応答が一致すること、
待ち組数が1から2になっても数値予測を独自補正しないことを検証する。
時刻や人数の変更による正常な予測変動は既存モデルに任せる。
NaN、Infinity、負値、不正shape・文字列は既存のprediction_failed応答となり、正常な数値として公開しない。
根拠のない最大分数や丸め込みは追加しない。業務上の上限を設ける場合は別途データ分布・運用根拠の検討が必要。

顧客UI、更新間隔、キャッシュは変更しないため、既に表示された誤案内中の情報は撤回できない。
匿名の`/predict`プレビュー履歴はDBに残らず、過去の表示を全件特定することもできない。
訂正直後の表示回復は既存の次回更新・新しい予測要求で行われ、即時push更新は追加しない。

## 検証と残る工程

新規テストはストア・HTTP API・履歴検査に分け、全DBを一時領域に限定する。
元3状態への復帰、同一/異なるUUIDの並行訂正、同時刻・重複する影響区間、
無効対象、世代/revision不一致、通信応答喪失後の再送・結果照会・再起動、
全書込み段階の例外と品質記録の無言の欠落を検証する。
例外時は状態・イベント・操作・品質問題・時刻メタデータ・連番を含めDBバイト列の完全復元を確認する。

旧v1の部分的な初回応答JSONもそのまま保持できるよう、保存操作結果の固定項目は
元の受付・スナップショット・予測テーブルを参照して検査する。
初回キャッシュを補完/書換えず、JSONのboolと整数等の型差も破損として拒否する。

これらを品質問題の自動解除や学習許可の根拠にはしない。
