# 合成call限定スタッフUIと未確定操作の復旧

記録日: 2026-11-10。[ADR-0016](../adr/ADR-0016.md)で、
[ADR-0015](../adr/ADR-0015.md)の次工程のブラウザ接続を記録する。
通常の閲覧専用ラボと一般のスタッフ画面に書込みを開放する変更ではない。
Windows実ブラウザと実タブレットの確認は未完了である。

## 接続する範囲

専用`staff_call_https_lab.py`が生成した新規一時DBだけを使う。
既存operations APIへのcallのみを接続し、waiting/absentからcalledへ変更する。
seat・absent・return・cancel・訂正・品質承認・LINEは接続しない。
通常の8443ラボ、実DBのモード、TLS・Cookie・Origin・CSRFの検査は変更しない。
モデルを読み込まない合成環境であり、予測結果の性能評価ではない。

call UIは認証、合成call限定の応答ヘッダー、v2・revision_required・書込み可能・訂正無効等の
検証済み設定がそろう場合だけ有効になる。ヘッダーの存在だけでサーバー権限が増えることはない。
通常ラボと一般画面ではcallボタンや未確定操作の保存を開始しない。
同一origin内のWeb Locks排他を取得できたタブだけが新規呼出・再送を行う。
未対応・別タブが所有中の場合は閲覧に限定し、既存未確定操作の照会だけは認証後に行える。

主な実装の分担は次のとおり。業務APIの状態遷移・認証方式は追加しない。

| ファイル | 責務 |
| --- | --- |
| [staff.mjs](../../web/staff/assets/staff.mjs) | 既存の一覧・認証・全ページ整合性を維持し、合成call能力を検証して接続する |
| [staff-call.mjs](../../web/staff/assets/staff-call.mjs) | 確認・独立通信・受領証検証・復旧・タブ排他を扱う |
| [staff-call-journal.mjs](../../web/staff/assets/staff-call-journal.mjs) | 秘密情報を含まない固定要求の保存・読戻し・期限・破損検出を扱う |
| [prediction_api.py](../../prediction_api.py) | 既存スタッフ専用オリジン検査の下で新しい2つのJS資産を配信する |
| [staff_call_https_lab.py](../../staff_call_https_lab.py) | 既存のcall限定ゲートを維持し、起動表示を今回の接続に合わせる |

## 確認から結果まで

1. waiting/absent行を右スワイプ、または常設「⋯」でメニューを開く。
   スワイプはメニュー表示だけで、呼出を実行しない。
2. 「呼出」を選ぶと最新operation-contextを取得する。
   日付付き番号、受付日時、大人・子供の人数、現在状態と「呼出」を確認画面で示す。
   対象の受付IDは内部で保持・照合し、確認画面では日付付き番号で人が対象を確認する。
3. 「呼出を確定」で再度operation-contextを取り、確認時点の対象と保護情報を照合する。
   状態・revision・database_id・write_epoch・設定等が変わった場合は送信せず、再確認を求める。
4. UUIDを一つ作り、固定要求をsessionStorageへ保存・読戻し検証してからPOSTする。
   連打や5秒更新で別IDを発行せず、一度に一つの未確定操作しか開始しない。
5. 成功・無変更・保存済み拒否は、本文の対応とresponse_status/outcomeを検証する。
   保存された結果は過去の受領証として扱い、現在の一覧へそのreceptionを流用しない。
6. 最新operation-contextでDB・世代・revision等との整合を確認した後に未確定記録を解決し、一覧を再取得する。
   contextの取得・照合に失敗した場合は受領済み結果をメモリに維持し、POSTを繰り返さず照会で確認する。
   記録解決後に一覧の取得だけが失敗した場合は、既存fail-closedで表示を閉じ、読取りをやり直す。

確認画面は背後へのタップを遮断し、確定・キャンセルを56px以上の高さで表示する。
初期フォーカスはキャンセルへ置き、Tabで背後へ抜けず、Escまたはキャンセルで元の行へ戻れるようにする。
対象の失効時は古い行への強制的なフォーカス復帰を行わない。

操作POSTと結果照会は一覧・詳細更新から独立し、15秒の通信期限を持つ。
通常の5秒ポーリングで中止せず、古い応答を新しい画面に上書きしない。
一覧は既存の全ページ取得・集計・受付順と差分DOMを維持する。
確認中の対象変更では確認画面を失効させるが、送信後の固定記録は消さない。

## 結果不明を失敗と扱わない

| 状況 | 扱い |
| --- | --- |
| 正常な保存結果でstate_changed/no_change | 過去の操作結果を確認。現在状態は再取得する |
| 正常な保存結果でrejected | 拒否が記録された操作。新revisionで自動再送しない |
| POST応答喪失・期限超過・不正形式 | 結果不明として固定記録を維持し、結果照会へ進む |
| 本文が保存結果ではない409 | 結果不明のまま照会。期待revisionを書き換えない |
| 結果照会のHTTP 200 | 取得成功。本文response_status/outcomeで元の操作を判定する |
| 結果照会404・通信失敗 | 未実行の証明にしない。新しいIDを発行しない |
| ログアウト・認証切れ | 受付情報を消し、未確定記録は保持。再ログイン後に先に照会する |
| DB・世代変更、期限超過、記録破損 | 再送・新規呼出を止め、手動確認が必要と表示する |

結果不明では「結果を照会」と、条件を満たした場合の「同じ操作を再送」を人が選ぶ。
再送は同一ID・同一本文のまま行い、受付ID・database_idも付け替えない。
操作結果と現在の受付状態を区別するため、結果照会の保存時刻と新たに取得した状態を混同しない。

## sessionStorageと排他の境界

保存するのは形式版、操作ID、受付ID、固定4項目の要求、database_id、作成時刻・期限等の最小記録だけ。
共有資格情報、Cookie、CSRF、受付詳細、予測JSON、スナップショット、操作応答全文は保存しない。
CSRFは既存GET sessionからメモリに取得し、POSTはCookie・同一Originと既存方式で送る。
認証情報を操作本文へ入れない。

通常の復旧期間は24時間。保存不能・読戻し不一致では最初のPOSTも送らない。
別の最小guard記録を先に書くことで、未確定本文だけの欠落や保存途中の不完全な組を検出する。
同じ画面で一度固定した記録の本文・時刻等が変わった場合も停止する。
guardは認証・署名ではなく、記録全体を消した後の再起動や悪意ある改変の完全な検出を保証しない。
未確定の間は新しい呼出を止め、メニューを閉じる・タブを切り替える・ログアウトするだけでは記録を解決しない。
期限を超えるか時計が逆行した場合は固定要求を捨て、操作ID・受付ID・database_idと要手動確認の
最小マーカーを残す。24時間は結果不明の自動消去・失敗確定の期限ではない。
DB再生成後には別database_idを検出して旧要求を送らない。

再読込み・再ログインは、同じ記録を検証し、認証と現在DBを確認してから結果照会する。
期限内pendingは認証済み一覧の初回反映後に一度結果を自動照会するが、POSTを自動再送しない。
未確定が残る場合や期限後の最小マーカーは、表示された照会ボタンから人が確認する。
保存値は権限の証拠にしない。Web Locksが取れなくても照会を許し、新規POST・再送は止める。
Web Locksは同一ブラウザの同一originの協調排他であり、別端末や別ブラウザを排他しない。
タブの閉鎖・ストレージ消去・ブラウザ終了で記録は失われ得る。完全な喪失を検出できるとは保証しない。
サーバー側の未確定操作検索や実店舗の手動照合手順は未完成で、実運用の復旧完了とは扱わない。

## Windowsブラウザの手動確認

実DBへ接続しないことを確認し、8443等のstaff.localhostラボは停止する。
Cookieはポートで分離されないため、二つのラボを同時利用しない。
既存のリポジトリ外証明書を使って起動する。資格情報をコマンド・URL・開発者ツールへ貼らない。

```bash
.venv/bin/python -B -m staff_call_https_lab \
  --cert "$omachi_tls_dir/staff.localhost.pem" \
  --key "$omachi_tls_dir/staff.localhost-key.pem"
```

1. `https://staff.localhost:8444/staff/login`で証明書エラーがないことを確認する。
   開発用共有資格情報でログインし、合成call限定であること、他操作が実行不能であることを確認する。
2. 1024×768、1280×800、縦向き、PCで確認画面・結果欄が見え、ボタンを押しやすいことを確認する。
   タッチの右スワイプと「⋯」は同じメニューを開き、スワイプだけで状態変更しないことを確認する。
3. waiting行で呼出を選択する。確認画面の日時・人数・状態を一覧と照合し、キャンセルで変更がないことを確認する。
   もう一度確認して確定し、calledへ変わることを確認する。absentでも同様に行う。
   called・案内履歴には新規呼出がなく、call以外が実行できないことを確認する。
4. 確認画面を開いたまま5秒更新を複数回待つ。内容不変なら画面・フォーカスが揺れず、
   背後の行が誤って選択されないことを確認する。Tab・Shift+Tab・Esc・キャンセルとフォーカス復帰を確認する。
   確認画面を閉じた状態では、一覧内スクロールやスワイプを背景更新が不要に中断しないことを確認する。
   確定の連打で送信が増えないことも確認する。
5. 別タブを同じoriginで開き、新規呼出が制限されることを確認する。
   Web Locks未対応・ストレージ拒否の環境では、閲覧できてもcallを送信できないことを確認する。
6. ブラウザの通信制御でPOST送信後に切断する試験を行う場合、成否を推測しない。
   「結果不明」が残り、新規呼出ができないことを確認し、通信を戻して結果照会する。
   結果不明の再読込み・再ログイン後も同じ操作IDを扱うことを確認する。
   ネットワーク障害のタイミング次第では保存前の切断にもなるため、必ず結果照会と現在状態を分けて確認する。
7. 未確定操作を残してラボを終了・再起動し、合成DBの変更を検出して旧要求の再送を止めることを確認する。
   元の合成DBは消えるため、その結果を新DBから取得できるとは期待しない。
8. ログアウト・期限切れで受付情報が消えること、通常8443ラボでは呼出を実行できないことを確認する。

秘密情報を含むスクリーンショット、Cookie、リクエスト認証ヘッダーは共有しない。
ブラウザの応答喪失再現だけでは、サーバー側確定後の全障害を証明したことにしない。
実タッチ感度・フォーカス・Cookie強制・Web LocksとsessionStorageの実挙動はこの手動確認の対象である。

## 2026-11-10追記: 確定成功通知のコンパクト化

利用者から、Windowsブラウザで001番の呼出・一覧への反映と、他操作が実行不能であることの確認報告を受けた。
その際、成功後にも下部の大きな通知が残って一覧を狭める問題が報告された。
従来は成功にも復旧用パネルを使い、一覧再取得の完了前に成功メッセージを設定していた。
今回の修正後の通知・描画・実タッチは、利用者による再確認が必要である。

- 成功受領証（state_changedまたはno_change）と最新operation-contextを照合し、既存どおりジャーナルを解決する。
  その後、全ページ一覧の再取得も成功し、同じDB・世代・設定と対象のrevisionを確認できた場合だけ、
  コンパクトな確定通知へ切り替える。保存結果と現在状態は引き続き別として扱う。
- 既存の上部44px更新表示枠内に成功通知を置き、一覧・集計のための領域を追加で消費しない。
  通知表示中は同じ枠の最終確認時刻を一時的に隠す。エラー等の表示は成功通知より優先する。
  行・一覧DOMの作り直し、スクロール変更、自動フォーカス移動は行わない。
- 通常は約5秒で通知の表示だけを消す。「閉じる」でも消せる。
  読取りや操作を妨げないよう、通知内のフォーカス・ポインター滞在中は消去を待ち、離れてから5秒とする。
  politeなライブ領域、44pxの閉じるボタン、拡大時に枠内で読めるテキスト領域を用意する。
  手動で閉じたボタンにキーボードフォーカスがあった場合だけ、最新情報取得ボタンへ戻す。
- 結果不明、照会404、通信失敗、拒否・競合、期限超過、現在状態や最新一覧が未確認の場合は、
  自動消去の対象にしない。既存の継続表示・照会／固定再送の導線を維持する。
- 通知タイマーはDOM表示の消去だけを行い、ジャーナル・固定要求・操作ID・受付状態・操作結果を変更しない。
  通知ごとの世代で古いコールバックを拒否し、新操作・非表示化・ログアウト・停止で通知とタイマーを破棄する。
  再読込み時に過去の成功通知を保存・復元する処理は追加しない。
