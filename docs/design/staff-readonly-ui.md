# Step 5-B: スタッフログイン・閲覧専用画面

## 範囲と入口

今回の画面は既存のブラウザセッションとスタッフ読取りAPIを使う。
受付・予測・学習データ品質の書込み処理、状態遷移、スキーマ、顧客用UIは変更しない。
呼出・不在・復帰・案内・取消・訂正・品質レビュー・通知のボタンや送信処理は実装しない。

| URL | 内容 |
| --- | --- |
| `/staff/login` | 共有スタッフ認証情報の入力 |
| `/staff/` | 認証済みの閲覧専用受付一覧・最近の案内履歴・詳細 |
| `/staff/assets/staff.mjs` | 専用JavaScript |
| `/staff/assets/staff.css` | 専用スタイル |

HTMLと資産は、明示設定された `https://staff.localhost[:port]` だけで提供する。
顧客用のlocalhost/127.0.0.1では、正しいスタッフヘッダーを付けても提供しない。
一覧HTMLはCookieセッションを確認し、未認証ならログインへ303で移動する。
HTMLには受付情報を埋め込まず、JavaScriptも認証確認後にだけ取得・表示する。
JSON用の厳しいCSPを維持し、専用HTMLだけ自己オリジンのscript/style/connectを許可する。
インライン実行、eval、フレーム、オブジェクト、base、通常フォーム送信は許可しない。

## ログイン・ログアウト

入力欄はpassword型で、nameを持たず、JavaScriptでの接続確認まで無効とする。
既存の `POST /staff/session` へ `X-Staff-Token` として送信し、送信開始前に入力欄を空にする。
共有トークンをURL・本文・HTML・配布JS・ログ・Cookie・ブラウザストレージへ保存しない。
サーバーからのエラー本文は表示せず、固定の案内文を使う。
これは個々のスタッフを本人確認する仕組みではなく、従来の共有主体を維持する。

成功後は既存のSecure/HttpOnly/SameSite=Strict Cookieを使い、CSRFは認証済みAPIから取得してメモリだけに保持する。
fetchは同一オリジン限定、資格情報はsame-origin、キャッシュなし、リダイレクトはエラー扱いとする。
スタッフ専用HTTPSホストでなければ、画面・直接のコントローラー呼出の双方で通信を止める。
HTTPへのフォールバックはない。

ログアウトは直ちに一覧・組数・詳細を消してから、既存の `DELETE /staff/session` にCSRFを送る。
成功応答で失効を確認した場合だけログアウト完了と表示する。
応答が失われた場合は閲覧を再開せず、完了未確認として明示的な再試行を求める。
再試行の401/403はCSRF不一致の場合もあるため、それだけで失効と断定しない。
安全な `GET /staff/session` の401で失効を確認できた場合だけ完了にする。
有効セッションならCSRFを再取得して次の明示的な再試行だけに使い、受付情報は戻さない。
403や通信失敗のままなら未確認を維持する。
ネットワーク断中はサーバー側失効を保証できないため、接続回復後に完了を確認する必要がある。

## 読取りと集計

既存の `GET /staff/receptions` をactive/recently_seatedの両方で使い、1ページ100件で全ページを取得する。
各ページのview_version/as_of、順序、受付IDの重複、カーソルの進行・重複を検証する。
両一覧のview_versionが一致した場合にだけまとめて表示し、同じIDが両一覧に存在した場合も拒否する。
最初の50件や100件を全体と扱わず、全active行からwaiting/called/absentを別々に数える。
上限100ページを超える場合は集計不能として表示を止め、不完全な組数を出さない。

未案内一覧は元のreception_order昇順、最近の案内は直近24時間の有効案内event_id降順である。
日付付き番号、受付時刻、大人・子供の人数、現在状態を表示する。
同じ内容の更新では行を作り直さず、スクロールやキーボードフォーカスを維持する。
番号を選ぶと `GET /staff/receptions/{id}/operation-context` で詳細を取得する。
要求したID・一覧のview_versionとの一致を確認し、案内時刻・実待ちと管理用の参照情報を閲覧できる。
一覧が更新されて版が変わった場合は詳細を閉じ、古い対象を表示し続けない。
v1/legacyでも閲覧でき、revision等が未設定なら「—」と表示する。モードや訂正フラグは変更しない。

## 更新と失敗時の扱い

お客様用一覧の既存5秒間隔を参考に、スタッフ画面も1回の更新完了から5秒後に次を取得する。
お客様用の更新間隔・予測キャッシュ・推論ロジックには手を加えない。
各更新でセッションを確認し、1回の通信とJSON取得には15秒の期限を設ける。
通常の定期更新は重ねず、明示的な新しい取得では古い通信を中止する。
中止できない古い応答でも、認証・一覧・詳細ごとの世代を比較して破棄する。

取得中に前回表示を残す場合は、更新中であり前回の情報であることを明記する。
通信失敗・409・不正形式・全件未取得では組数・行・詳細を消し、最新情報として見せない。
409は次の読取りで先頭から取得し直すだけで、受付状態を変更する再試行は一切しない。
401/403や期限切れでは情報とCSRFを消し、ログインへ移動する。
絶対期限・アイドル期限をクライアント側にも保守的に設定し、遅延した応答で期限を延長しない。

非表示タブ・pagehideでは機密DOMとメモリ内表示データを消し、通信・定期更新を止める。
復帰時にはセッションと全件を取り直す。BFCacheの戻る操作でも古い受付情報をそのまま表示しない。
API文字列はtextContentとDOM生成だけで描画し、innerHTML等の実行経路へ渡さない。
ログアウト未確認中は復帰・定期更新で情報を復元しない。
別タブでの失効は次の認証確認で検出するため、複数タブの即時一斉消去は保証しない。

## HTTPS確認と次工程

合成DB専用のローカル環境とWindows/WSL2での手順は
[HTTPS開発手順](staff-readonly-ui-https.md)に記載する。
実DB・バックアップ・指定実験DBを起動対象にしない。
証明書・秘密鍵・共有認証情報はGitに含めず、信頼ストアやネットワーク設定を自動変更しない。

この実行環境には実ブラウザがないため、実画面の描画、Windows/WSL2の名前解決、証明書信頼、
ブラウザがCookie属性を実際に強制する動作、タブレット/PCの操作性は手動検証が残る。
NodeのDOM・通信模擬試験とPythonのHTTP/TLS試験を実ブラウザ試験と混同しない。

次のスワイプ工程へ進む前に、HTTPS実機でログイン/ログアウト/期限切れ/通信喪失/戻る操作と、
ページをまたぐ組数、番号からの詳細、タブレットとキーボードの可読性を確認する。
右スワイプや三点メニュー、案内直後の訂正導線、重要操作の確認、操作IDの保持は後続工程で実装する。
LINE・品質clear・学習承認は独立した将来工程のままとする。

## 実行結果

- Python全件：`1586 passed`、`-W error`（既存1537件、新規ルート30件、HTTPS環境19件）。
- JavaScript全件：`175 passed`（既存顧客画面111件、スタッフ画面64件）。
- 全ページ151件の正しい集計、409/通信失敗/不正データでの非表示、古い応答破棄、期限切れ、ログアウト応答喪失・再確認を検証した。
- 一時証明書を使う実TLS通信で、ホスト名検証、Cookie属性、Origin/CSRF拒否、ログアウト後401を確認した。ブラウザのCookieポリシー強制やWindows側の信頼設定の確認ではない。
- 実DB2件、バックアップ2件、指定実験DB、モデル、Excel、既存フロントエンドと品質管理処理を含む93ファイルは、保存した基準とのSHA-256照合で一致した。
- 証明書・秘密鍵はリポジトリに作成せず、実DB移行・モード変更・訂正有効化、commit/push/PR/mergeは行っていない。
