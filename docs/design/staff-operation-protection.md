# Step 5-B: スタッフ操作ID・revision・書込み世代

## 適用範囲

呼出・不在・復帰・案内・取消に、認証付きの保護専用APIを追加する。
既存の本文なしAPIを変更する方式では既存クライアントを壊すため、新しい名前空間を使う。
DB定義・バージョン・移行処理は変更しない。新規DBは引き続きv1で、保護付きAPIはv2でのみ利用できる。

この工程の書込み検証は一時ディレクトリ内の合成DBのみで行う。
実DB・バックアップ・指定実験用DBの移行やモード変更、世代変更は実行しない。
`seat_corrections_enabled=0`を維持し、訂正API・品質管理操作・スタッフ画面は追加しない。

## 認証とAPI

すべての新ルートに既存の`X-Staff-Token`認証を適用する。ローカル接続・Host・Origin制限と
`Cache-Control: no-store`も維持する。再送・結果照会も毎回認証する。
監査主体は`principal_kind=shared_staff_token`、`principal_id=shared-staff`で固定し、
共有認証であることを表す。個別スタッフを識別したとは扱わない。
トークン、そのハッシュ、本文で指定された主体を保存しない。

| ルート | 用途 |
| --- | --- |
| `GET /staff/receptions/{reception_id}` | 同じ読取トランザクションの受付状態・revision・write_epoch・モード |
| `POST /staff/receptions/{reception_id}/operations` | 5操作を共通の保護で処理 |
| `GET /staff/operations/{operation_id}` | 認証主体に結び付いた操作結果を照会 |

POST本文は以下の4項目のみ。UUIDはnilを拒否し、標準表記へ正規化する。
revisionはbool・文字列・小数を認めず、SQLiteの非負符号付き64ビット整数に制限する。

```json
{
  "operation_id": "c2502de4-c733-4c04-b6c2-367ec1052425",
  "action": "seat",
  "expected_revision": 3,
  "write_epoch": "6b176cfe-d7af-4c67-95c0-cb5d140db53d"
}
```

`action`は`call / absent / return / seat / cancel`のみ。受付日時や案内日時をクライアントから受け取らない。
応答には操作ID・対象・操作・outcome・元のHTTPステータス・記録日時・結果revision・受付結果・エラーを返す。
受付結果は従来の`ReceptionResponse`と同じ項目に限定する。
書込み世代はスタッフ専用読取りでのみ返し、顧客API・初回受付応答へ追加しない。

結果照会のHTTPステータスは、記録があれば200、未登録・異なる認証主体なら404。
応答の`response_status`が元の操作の200/404/409を表す。POST再送は元のHTTPステータスと本文を返す。
この記録は操作当時の結果なので、後続操作後の現在状態を知るには受付読取りAPIを使う。

## 要求の同一性と永続結果

要求形式v1では、形式バージョン・受付ID・操作・期待revision・write_epochを固定キーのJSONにし、
UTF-8・キー順固定・余分な空白なしで保存する。認証主体と操作IDは別カラムで管理する。
保存には要求全文・SHA-256・認証主体・結果本文・結果ステータス・結果revisionを含む。
ハッシュだけで同一性を判断せず、正規化した全文と認証主体も照合する。

同じ操作IDで同一要求・同一主体なら、保存済み結果をそのまま返す。
現在状態から応答を再構成せず、revision・イベント・時刻メタデータも更新しない。
異なる受付・操作・期待revision・世代・主体で同じIDを再利用した場合は409で拒否し、既存記録を変更しない。

構文上有効な新規要求のrevision不一致、世代不一致、不正遷移、対象なしは、拒否結果として永続化する。
同じ拒否要求の再送も同じ結果になる。最新状態でやり直す場合は、最新情報を取得し、新しい操作IDを使う。
不正形式・認証失敗では操作IDを確保しない。DB障害では全体をロールバックし、同じIDで再試行できる。

## 同時操作とトランザクション

`BEGIN IMMEDIATE`で書込ロックを取得したあと、次の順で処理する。

1. スキーマ・設定・ストアに固定したDB識別子/世代を検証する。
2. 同じ操作IDの記録を検索し、同一要求なら保存結果を返す。
3. 新規操作は現在の世代、期待revision、状態遷移の順に検証する。
4. 有効な変更では元の受付日時から時刻・実待ち分を計算し、`WHERE id=? AND revision=?`で更新する。
5. revisionを1増やし、変更前後JSON・操作ID付きの`staff_v2`イベントを追加する。
6. 成功/無変更/拒否の操作結果を`staff_operations`へ追加し、同じトランザクションをコミットする。

イベントから操作記録への外部キーは既存の遅延制約を使い、コミット時に成立させる。
例外時は受付・イベント・操作記録・メタデータ時刻・連番をまとめて戻す。
同じ操作の同時送信は1件だけ確定し、別操作で同じrevisionを使った競合は1件だけ状態変更に成功する。

新しいIDでも、期待revisionと世代が一致し、現在と同じ状態になる要求は`no_change`として保存する。
revision、イベント、案内時刻、実待ち分は変更しない。古いrevisionを無変更扱いで通すことはない。
新規の無変更/拒否操作は監査記録と単調な記録時刻を保存するため、DBファイル全体が無変更とは限らない。

起動時の履歴検査は、全操作の要求ハッシュ・要求各項目・保存結果の対応、時刻、
成功イベントとの対応、過去revision時点の状態・実待ち、受付時の固定情報との一致も確認する。
訂正・品質レビュー等の未対応履歴は引き続き自動修復せず拒否する。

## 旧経路からの回避防止と互換性

既存の更新経路はすべて`operation()`から`ReceptionStore.transition()`へ入る。

| 旧POSTルート末尾 | 対象状態 |
| --- | --- |
| `/receptions/{id}/call` | called |
| `/receptions/{id}/absent` | absent |
| `/receptions/{id}/return` | waiting |
| `/receptions/{id}/seat` | seated |
| `/receptions/{id}/cancel` | cancelled |

v1とv2の`legacy`では従来APIの仕様を維持する。
`revision_required`では`transition()`先頭のロック内ゲートで5経路すべてを拒否し、無変更要求も通さない。
既存の`events_legacy_mode`トリガーも維持する。保護付きAPIは両モードで動作する。
`legacy`で旧APIを使う場合は操作ID等の保護が必須ではないため、全経路で保護を強制するには後工程での明示的切替が必要。
今回は切替コマンドや設定変更APIを追加せず、合成テスト内だけで切り替える。

新規受付・予測・公開待ち一覧・顧客画面は変更しない。
受付ID・番号・順番・受付時刻・人数、受付スナップショット、予測JSON、初回応答JSONも保持する。
案内時の実待ち分の式は従来どおり`(案内日時 - 元の受付日時).total_seconds() / 60`とする。
RF・特徴量・前処理・Excel・評価・学習済みモデル・学習への自動投入処理は変更しない。

## 復元時の条件と今後の課題

バックアップの内容だけでは復元された事実を自動判定できない。
復元後は受付を再開する前に、停止した環境で新しいwrite_epochを設定し、ストアを作り直す運用が必須。
今回はこの変更と復元を合成DBでのみ検証し、実DB向けコマンドは追加していない。
世代の変更を検出した既存ストアは、DBへ追従せず再生成まで拒否する。

バックアップに残っている同一操作は旧世代でも保存結果を返せるが、再更新はしない。
バックアップに残っていない古い操作は、期待revisionが偶然一致しても世代不一致で409になる。
新世代で処理するには、最新情報と新しい操作IDが必要。

共有認証は個人の特定・権限分離を提供しない。操作記録の保持期限・容量管理、
復元時の世代変更の運用手順、将来の認証主体変更時の結果照会方針は後工程で決める。
操作記録の削除や期限切れによるID再利用は実装しない。

次工程の訂正API・品質管理の実装に進める基盤は整うが、訂正機能は無効のままにする。
後続工程では「案内済み→訂正→古い案内要求の再送」が再案内されない完全な結合テストと、
訂正対象・周辺受付の品質隔離、未解決データの学習抽出除外を必須とする。
