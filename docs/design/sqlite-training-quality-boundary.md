# Step 5-B: 品質レビューとSQLite学習候補の抽出境界

## 方針と現時点の権限

学習利用は既定で禁止する。共有スタッフ認証は、品質問題のhold/excludeと、保留/除外の
品質判定を追記できる。clearやeligibleの権限は与えない。
HTTPアプリには承認用の本人確認・根拠確認機構を接続せず、設定や環境変数による解除も追加しない。
従来の品質参照APIは引き続き`training_use=blocked`を返す。

解除・候補化のコード経路は、明示的に渡した信頼済み承認機構がある場合のみ検証できる。
今回その機構を用意したのは一時領域の合成テストだけであり、実運用の学習許可は有効化していない。
実データの読取り抽出やファイル出力、実DB移行・モード変更、モデル再学習も実行しない。

v2の既存テーブルと制約を使い、DDL・スキーマ版を変更しない。
既存のRF・Excel・前処理・評価・顧客UIは変更しない。

## 追加した境界

| 実装 | 役割 |
| --- | --- |
| quality_protocol.py | 正規化要求、根拠の形式、保存結果、承認のデータ契約 |
| quality_review_store.py | 保護付き追記と再送・競合・原子性 |
| quality_history.py | レビュー/判定と操作台帳の双方向検証、過去の確認範囲の再生 |
| quality_policy.py | 原則禁止の採否判定、信頼済み確認者による再確認 |
| sqlite_training_extract.py | 一貫した読取スナップショットから承認済み候補だけを返す |

reception_schema.pyは訂正による品質問題の網羅性を検査したあと、新しい品質履歴も検査する。
staff_operation.pyとReceptionStoreの操作結果照会は品質操作を認識する。
新規の監査行や判断理由は、既存の追記専用トリガーで更新・削除・REPLACEを禁止する。

## レビューと認証

追加ルートはすべて既存のスタッフ認証・Host・Origin・ローカル接続制限の対象。

| ルート | 内容 |
| --- | --- |
| GET /staff/receptions/{id}/quality-context | revision、世代、検査範囲、各問題の最新レビュー、最新判定ID |
| POST /staff/receptions/{id}/quality-reviews | 問題ごとの判断を追記 |
| POST /staff/receptions/{id}/quality-assessments | 受付単位の判定を追記 |

操作ID、期待revision、write_epoch、理由コード、理由詳細、根拠、期待する検査範囲を必須とする。
レビューはissue_idとexpected_review_numberも比較する。初回の期待番号は0。
判定はexpected_assessment_idを比較し、初回は0とする。
品質操作では受付状態やrevisionを変更しないため、revisionだけを競合防止に使わない。

検査範囲は全体の最大event_id・issue_id・review_idの3値。
他の受付の訂正で新しい問題が追加された場合や、別問題のレビューが増えた場合も古い要求を拒否する。
有効な新規要求の不一致は409、対象なしは404、承認権限不足は403として保存する。
構文不正は保存前に拒否する。

同一UUID・同一主体・同一正規化要求の再送では保存結果を返す。
異なる内容・主体・操作種別でUUIDを再使用した場合は409。
再送と結果照会も認証し、保存結果を返す前に品質履歴の完全性を検査する。
結果はその操作当時の履歴であり、現在の学習利用許可として使わない。

判断日時はサーバー時計で記録する。主体は操作台帳への外部キーから追跡する。
共有トークンで記録する主体は`shared_staff_token / shared-staff`であり、個人名を確認したとは扱わない。
トークン自体やトークンハッシュを保存しない。要求本文で主体・承認機構を指定することもできない。

## 解除の根拠とデータ契約

clear/eligibleには、外部確認資料の参照referenceと、intake_verified・seating_verified・
context_understoodの3つの厳密なtrueを要求する。
ただし、これらの値を送信しただけでは確認済みにならない。
信頼済み承認機構のverify()が、本人確認済みstaff_account・権限・資料・対象revision・
有効案内イベント・確認範囲を独立に検証し、厳密なTrueを返す必要がある。
未設定、例外、取消済み権限、異なる承認機構・契約、真偽値以外の返答は許可しない。

承認記録にはサーバー側で付与したauthority_id、データ契約、有効案内イベント、revisionを保存する。
要求と承認はrequest_jsonの別部分に分け、全体のハッシュも保持する。
再送の同一性は利用者の要求で比較し、後から権限状態が変化しても過去の操作結果を書き換えない。
抽出時には承認権限と根拠を再確認し、失効した許可を使わない。

固定データ契約は`rf-intake-actual-wait-v1`、品質判定版は`sqlite-quality-v1`。
この契約は元の人数・受付日時と、現在有効な案内実績による正確な実待ち分だけを対象にする。
誤りの可能性がある受付スナップショットや保存予測を特徴量として許可する契約ではない。
snapshot_context等をclearしても、保存済み値を正しい値へ修復したことにはならない。

## 抽出の採用・除外条件

extract_candidates()は既存DBをmode=roで開き、query_only・foreign_keysを確認する。
BEGIN後の最初のSELECTで読取スナップショットを確定し、その中で以下を検証する。

1. 既知のv2スキーマ、全受付履歴、訂正履歴、必要な品質問題の完全な網羅性。
2. レビュー・判定と操作台帳の一対一対応、理由・時刻・順番・参照revision。
3. 最新判定がeligibleであり、現在revisionと有効案内イベントが一致すること。
4. 検査済みevent/issue/reviewの全体範囲が現在値と一致すること。
5. 全品質問題の最新レビューがclearで、現在revision・案内イベント・event/issue範囲に対応すること。
6. 現在の世代と承認用の世代が一致し、既知の品質判定版・データ契約であること。
7. 承認機構が現在も根拠と権限を認めること。
8. 受付・案内の日時にタイムゾーンがあり、順序・案内イベント・実待ち計算が整合すること。

未評価、未レビュー、hold/exclude、古いレビュー、古い判定、案内なし、無効化済み案内は除外する。
品質問題の欠落、未知の形式/版、履歴不整合等で証明できない場合は、候補を部分的に返さず抽出全体を停止する。
未知・失効した権限は候補にしない。受付が再案内されても問題やレビューを自動解除しない。

返すデータはsnapshot、candidates、excludedの3部分。
candidatesには承認済み行だけを入れ、除外行には受付IDと理由以外の人数・日時・学習ラベルを含めない。
候補には受付ID・受付順・人数・正確な受付/案内日時・実待ち分・受付revision・有効案内イベントID・
assessment ID・品質判定版・データ契約・抽出時刻を含める。
batchのsnapshotにはdatabase_id・write_epoch・event/issue/review/assessmentの境界を残す。
保存予測・スナップショット・認証主体・台帳の要求本文は候補の特徴量に渡さない。

抽出中に別端末が更新しても、途中から新しい時点の情報を読み混ぜない。
WALの合成試験では読取開始後に訂正がコミットされても、旧snapshotの結果は内部整合性を維持し、
次の抽出は訂正後の状態を見て除外する。
候補batchは一時点の監査結果なので、将来の学習開始前には鮮度と権限を再検証する必要がある。

## 前処理との関係

既存prepare_training_data()は学習候補フラグを再判定するため、全行へ品質フラグを付けて渡す方式は使わない。
SQLite境界で不許可行を先に除き、許可した候補だけを返す。
合成テストでは、境界から得た承認済み行だけを変換して既存前処理へ渡し、未承認行が増えないことを確認する。

実装にはExcel形式への汎用変換、ファイル出力、モデル学習の呼出しを追加しない。
既存監査処理には整数分への丸め・日付またぎ非対応等があるため、小数分・日付またぎのSQLite実績を
自動で既存前処理へ通すこともしない。抽出境界では0分・小数分・日付またぎの正確な値を保持する。
実運用のアダプターは、変換でラベルが変わらないことを別工程で検証・承認する必要がある。

## 001・002の結合結果

元の時系列は、18:00受付001、18:10誤案内、18:10:30受付002、18:11訂正、18:25実案内。
001の正しい実待ちは25分、invalidated_seatingは残る。
002の保存スナップショットは0組のままで、snapshot_context・prediction_gateは両方残る。

| 合成試験の段階 | 候補 |
| --- | --- |
| 再案内後も未レビュー | 001・002とも除外 |
| 信頼済み確認者が001の問題を確認し最新判定 | 001の25分だけ候補。002は案内なし・未解決で除外 |
| 追加で002を18:31に案内し、問題の片方だけ確認 | 002は除外。全体範囲が変わり001の旧判定も除外 |
| 全問題を現在の実績に結び付けて確認し両者を再判定 | 合成承認機構がある場合だけ001=25分、002=20.5分が候補 |
| 同じDBを既定の承認機構なしで抽出 | 候補0件 |
| 後からhold/exclude、新規問題、新たな訂正等が追加 | 古い承認を再利用せず除外または再確認 |

保存済み予測・スナップショット・初回応答・受付実績・状態イベントは品質操作で変更しない。
同じ時刻・人数・モデルの合成予測は、レビュー前後で特徴量バイト列と17.125分の結果が一致した。
待ち組数の補正式や特徴量の追加は行っていない。

## 未解決の運用条件

実運用の本人確認・品質承認権限・外部資料の検証・取消運用は未接続。
これらが十分になるまではclear/eligibleと実データの学習利用を有効化しない。
共有スタッフによるボタン操作だけで学習許可する経路は設けない。

全体watermarkを使うため、無関係な新規受付やレビューでも古い判定が保留になる。
これは漏れを避ける保守的な設計であり、実データ量で性能・運用負担を評価する必要がある。
将来範囲を狭める場合は、間接影響を漏らさない新しい判定版が必要。
全履歴検査・権限再確認の負荷、抽出batchの保管・失効・学習開始時再確認、スタッフUI、
既存前処理との互換性、実DB移行・復元後の世代変更を、実適用前の別工程として残す。

今回の抽出結果は学習候補であり、モデルの再学習や本番モデルへの切替を許可するものではない。
