# ADR-0010: スタッフ専用オリジンとブラウザセッション認証

- 状態: 採用済み方針の後追い記録（今回レビュー対象）
- 記録日: 2026-11-02
- 記録区分: Step 5-Bの認証基盤・ログイン画面工程で採用した判断を今回初めてADR化する
- 関係: [ADR-0005](ADR-0005.md)の共有ヘッダー認証を維持してブラウザ用経路を追加。店舗公開への変更ではない

## 背景

顧客画面と同じJavaScriptへ共有スタッフトークンを配布できない。
ブラウザで安全に閲覧するには、認証秘密の保存場所、Cookie、CSRF、期限、専用ホストをまとめて設計する必要がある。
ポートだけを変えてもCookieはホスト間のようには分離されない。

## 決定

1. ブラウザ認証は既定で無効とし、`create_app(staff_browser_origin=...)`で明示設定する。
   HTTPSの`staff.localhost`専用オリジンを使い、顧客用localhost/127.0.0.1と分ける。
   スタッフホストでは`/staff/`だけを提供し、顧客HTML・公開APIを混在させない。
2. 既存`POST /staff/session`で共有資格情報を一時的にヘッダー送信し、サーバー側セッションへ交換する。
   入力を送信開始前に消し、HTML・配布JS・URL・ログ・DB・ブラウザ保存領域・Cookieに共有トークンを保存しない。
   認証エラーには固定文を使い、秘密情報を表示しない。
3. セッションはプロセスメモリで管理し、256ビット乱数の不透明IDを発行する。
   検索キーはIDのハッシュとし、Cookieは`__Host-omachi-staff`、
   `Secure; HttpOnly; SameSite=Strict; Path=/`、Domainなしとする。
   絶対期限1時間・アイドル15分、最大256件、ログイン試行は全体で毎分10回まで。
   再ログインで旧セッションを失効し、再起動でも全失効する。
4. `GET /staff/session`で認証とCSRFを取得し、CSRFは画面メモリだけに保持する。
   Cookieでの書込みには厳密なOriginと`X-CSRF-Token`を必須にし、SameSiteだけに依存しない。
   ログイン前はCSRFがないため同一Originと共有資格情報ヘッダーを必須にする。
   `DELETE /staff/session`でサーバー側も失効する。
5. loopback接続、Host、HTTPSオリジンを検査し、スタッフ接続の転送ヘッダーを拒否する。
   CORS・HTTPフォールバックを追加せず、不正Cookieからヘッダー認証へ戻らない。
   HTML/資産は専用ホストで配信し、一覧HTMLはセッションを確認する。
   CSP、no-store、Referrer-Policy等で表示・取得の境界も維持する。
6. 認証主体は共有の`shared_staff_token / shared-staff`で、個人の本人確認とはしない。
   Cookie経路の業務POSTは既存の保護付き操作・訂正APIに限定し、v2 revision_requiredを必要とする。
   旧APIや品質レビュー・学習承認への権限を追加しない。現UIは状態変更APIに未接続である。
7. ログアウト開始時に受付表示を消す。通信応答喪失時は失効未確認として表示再開を止め、
   明示的な再試行・安全なセッション照会で確認する。401/403の書込み失敗だけで失効完了と断定しない。
   期限切れ・認証失敗・非表示化・履歴復帰時も古い機密DOMを表示し続けない。

## 理由

既存の認証と保護付き操作を再利用しながら、共有秘密を配布資産から除き、顧客との権限を分離できる。
専用ホスト・Cookie属性・Origin・CSRFの複数の検査でブラウザの自動Cookie送信に対処する。

## 代替案

| 案 | 判断 |
| --- | --- |
| JS埋込み・localStorage保存の共有トークン | 顧客や配布資産への秘密漏洩につながるため不採用 |
| 顧客と同ホストの別ポートだけで分離 | Cookie境界として不十分なため不採用 |
| SameSiteだけ、開発時だけHTTP Cookie | 必要なCSRF/TLS保護を弱めるため不採用 |

## トレードオフ・影響

現セッションは単一プロセス用で、複数workerの共有・永続化は未実装。
共有資格情報と全体ログイン上限には可用性・責任者特定の制約がある。
ブラウザやOSの資格情報保存機能まで制御できるとは主張しない。
店舗LANには専用ホスト・TLS・端末/個人認証・失効・ログ・セッションストアの別レビューが必要。
認証用DBテーブルを増やさず、受付・予測・品質承認を変更しない。
