### 業務上の背景と初期モデルの対象

開発者本人はPISOLAで約2年半勤務している。本人の現場経験では、通常の平日は待ち組が
ほとんど発生せず、土日祝日や長期休暇などに待ち組が発生しやすい傾向がある。
平日のデータが少ない背景には、店舗の営業特性と、待ち組が発生したケースを中心に収集したことが
関係しており、単なる収集不足とは扱わない。ただし、これは本人の定性的な観察であり、
待ち組発生確率を定量的に検証した結果ではない。実データの曜日だけで祝日だったとは断定しない。

初期モデルの対象は「待ち組が発生する状況での案内までの待ち時間予測」と位置づける。
通常の平日や待ち時間0分を含む全来店客への予測性能は未検証であり、現時点ではモデルの学習・
精度評価そのものも実施していない。収集対象の偏りを踏まえ、全来店客へそのまま一般化しない。

将来は平日・長期休暇・祝日を含めたデータを収集し、待ち組が発生しないケースも確認する。
必要に応じて、待ち組発生の分類と、待ち組が発生した場合の待ち時間回帰を組み合わせる
2段階モデルも検討する。祝日・長期休暇の特徴量は未実装の候補として記録し、
営業カレンダーと受付時点での利用可能性を確認してから採否を決める。

## 決定: 説明変数は許可した列からだけ生成する

`preprocessing.py` を追加し、既存のpandas・NumPy・標準ライブラリだけを使う。
特徴量変換は `build_features()` に集約し、学習と将来の予測で同じ変換を使う。
I/O、モデル、標準化、欠損値の統計的補完は追加しない。

| 項目 | 決定・理由 | 代替案と保留理由 |
| --- | --- | --- |
| 曜日 | 年付き日付から算出した月〜日の固定7列を0/1で表す。受付時点で既知で、曜日に大小関係を持たせない | 元の曜日列は不一致を混入し得るため使わない。0〜6の整数はモデルによって順序・距離を仮定する。週末フラグの併用は情報が重複するため保留 |
| 大人・子供 | 受付時点で申告される人数。席の収容人数や構成との関係が考えられるため別々に採用 | 合計人数も同時に入れると完全に重複する。合計人数はStep 1と同じ整合性検証にだけ使う。実際の予測寄与は未検証 |

### 天気の符号化

前後の空白だけ除去し、`晴れ / 曇り / 雨 / 雪 / その他 / 不明` の固定6列に変換する。
欠損・空白は「不明」、辞書外の文字列は「その他」。数値や真偽値は型の誤りとしてエラーにする。
辞書外値を雨等へ推測して寄せない。例えば「晴」「晴時々曇」は現仕様では「その他」となる。
実データに多い表記は本人の環境で確認し、必要なら対応表とテストを別途追加する。

カテゴリを全データから発見する処理はなく、学習時に見なかった値でも列構成が変わらない。
将来、学習で辞書や補完値を求める変換を採用するときは、学習区間だけで決定し検証・テストへ適用する。
現段階ではfitを伴うエンコーダー、スケーラー、統計的補完は存在しない。
将来導入する場合は先に日付で分割し、各時系列検証の学習区間だけでfitする。
検証・テストにはtransformだけを適用し、全区間を連結してfitしない。
Pipeline等でモデルと一緒に管理し、評価データを書き換えても学習側の変換結果・学習済み統計が
変わらない回帰テストを、その実装時に追加する。将来の未実装処理の安全性まで今回保証したものではない。
有効化フラグ自体は記録の利用可能性を証明しない。データ収集方法の確認と、運用でも同じ入力を
取得できることが必要。未確認なら既定の天気なしを使う。

### 必ず除外するもの

- 予約件数6列（11/13/17/18/19/20時台）、`当日予約追加後か` とその派生値。
- 案内時刻、記録・計算待ち時間、取消、学習候補、品質判定列。目的変数の検証にだけ使う。
- 呼び出し番号、氏名等の識別情報、その他の未許可列。
- 当日全体の来客数・平均待ち時間・受付後の待ち組数等。行順から混雑を再構成する処理も追加しない。

列を何個か削除して残り全部を使う方法では、後から増えた列が紛れ込む。
そこで出力列を固定する。生データや監査DataFrame全体をモデルへ渡さず、必ず返値の `X` を使う。
将来、受付時点の待ち組数等を追加するなら、イベント発生時刻・同時刻の扱い・取得遅延まで確認する。

## 日付変換

日付はPythonの `date` に統一する。年を含む `YYYY-MM-DD` / `YYYY/M/D` の文字列、
`date`、時刻が午前0時のnaiveな `datetime` / `Timestamp` / `numpy.datetime64` を受け付ける。
うるう日等は暦として検証する。日付は店舗の現地暦日として扱う。

年なし、日月順が曖昧な表記、日時文字列は推測しない。
Excel数値シリアルは既定では従来どおり拒否する。最終レビューで要求された変換に対応し、
`parse_date()` / `build_features()` / `prepare_training_data()` に
`excel_date_system="1900"` または `"1904"` を明示した場合だけ変換する。
方式はブックの設定を本人が確認して指定する。年代や値からは推定しない。

| 日付方式 | 許容する整数シリアル | 境界の解釈 |
| --- | --- | --- |
| 1900 | 1〜2958465。ただし60は拒否 | 1=1900-01-01、59=1900-02-28、61=1900-03-01、上限=9999-12-31 |
| 1904 | 0〜2957003 | 0=1904-01-01、上限=9999-12-31 |

1900方式の60は実在しない1900-02-29なので `invalid_date` とする。1900方式の0は暦日として
採用しない。小数部は `time_component` として拒否し、日付へ丸めない。範囲外、無限大、
真偽値も拒否し、NaN等は欠損のままにする。文字列の数値は自動的にシリアルと解釈しない。
日付方式を明示しない既存の呼び出しと463件のテストは維持した。
変換後のmetadataは通常のdateなので `split_by_date()` はそのまま利用できる。

根拠: Microsoftの[日付方式の説明](https://support.microsoft.com/en-gb/excel/date-systems-in-excel)、
[Date1904仕様](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-xls/4a5e900a-0eb0-4355-8fc1-81aab8f46e8b)、
[1900年のうるう年の扱い](https://learn.microsoft.com/en-us/troubleshoot/microsoft-365-apps/excel/wrongly-assumes-1900-is-leap-year)。
方式を1900に固定する代替案は設定違いで日付がずれるため不採用。
自動でブックを開いて設定を取得する案はI/Oを増やしStep 1の責務に影響するため今回は追加しない。
その代わり、呼び出し側が方式を確認して渡す必要がある。
openpyxl等が日付セルをdatetimeにした場合は上記の条件で受け付ける。
既に外部ライブラリで暦日に変換された値からは、元のシリアル60だったかは復元できない。
時刻成分は切り捨てず、タイムゾーン付き日付も勝手に変換しない。
必要になった場合は店舗TZと元データの契約を決めて拡張する。

`valid / missing / conversion_error / invalid_type / time_component / timezone_aware` に加え、
明示的なシリアル変換では `invalid_date / out_of_range / non_finite` を区別する。
日付の欠損を前の行で埋めない。結合セルが原因であっても、意味を確認せず補完すると別の日へ混入し得る。
日付が不正な行はStep 1の判定を残したうえでStep 2では対象外とし、全行の診断に理由を残す。

## 目的変数と行の対応

`prepare_training_data()` は受け取った診断列を信用せず、Step 1を再実行する。
Step 1の候補かつ日付がvalidの行だけを抽出し、`計算待ち時間` を `y`（`待ち時間_分`）にする。
同日差を整数分へ丸め、記録待ち時間との一致を確認済みの行に限る。記録値での無条件な代用や
不一致の修正、翌日への補正、目標226件への調整は行わない。

取消・待ち時間不明・不整合行を除くため、この教師データは実際に案内され、整合する記録を持つ組の
待ち時間を表す。取消客が案内された場合の仮想待ち時間や、全受付客の離脱までを推定するものではない。
営業途中の記録には未案内が含まれ得るため、後でモデルを評価するときは収集完了の確認も必要。

返値は `X / y / metadata / diagnostics`。X・y・metadataは同じ行順・元インデックスを保つ。
metadataは日付と0始まりの元行位置だけ。diagnosticsは全行の候補・判定・重複・元行位置を保持する。
重複インデックスでも `.iloc` の行位置で確実に対応できる。入力は変更しない。
Step 1どおり重複は報告のみで保持する。真正の重複を繰り返し学習する重みへの影響は残課題。
`build_features()` 単独は不正な入力をエラーにし、無言で行を捨てない。
候補0件の場合は列構成を保つ空の結果を返す。学習・評価できることを意味しない。

## 日付単位の分割と次の評価

`split_by_date(dates, train_end=..., validation_end=...)` は、日付を正規化して次の区間へ分ける。

1. 学習: 日付 <= train_end
2. 検証: train_end < 日付 <= validation_end
3. 最終テスト: validation_end < 日付

返値はX・y・metadataに対する0始まりの `.iloc` 位置。未ソートや重複インデックスでも対応を維持する。
同じ日は必ず同じ区間に入り、学習日の最大値は検証日の最小値より前になる。
不正日付、境界の逆転・一致、いずれかの区間が空ならエラーとする。
データが1日分しかない場合などにランダム行分割へ切り替えない。
年付き日付の検証が十分な営業日数の確認に置き換わるわけではない。

本人の確認により、学習候補は2026-05-24〜2026-08-07の14営業日と分かった。
Step 3では、この営業日数の少なさを考慮し、最終テストを温存した日付ベースの検証を行う予定とする。
境界日・比率はまだ確定しない。ラベルや性能を見て境界を都合よく動かさず、
日付と運用の評価期間から、学習・検証・テストそれぞれに確保できる営業日数を確認して決める。
最終の連続した期間をテストとして温存し、その手前で「過去で学習→直後の数日を検証」を
学習期間を広げながら繰り返す。今回その交差検証ループやモデル選択は実装しない。
既知の同日運用では前日までの案内結果を次の日の予測前に収集可能という前提がある。
記録の取得遅延がある運用なら、日付だけで十分とせず、ラベルが取得できた時刻に合わせて間隔を設ける。

後続工程では学習区間の待ち時間中央値を返すベースラインと比較し、分単位のMAEを報告する。
営業日別の件数・誤差、曜日・時間帯・人数別の偏りも見る。今回の学習候補は226件あるが、
評価単位となる営業日は14日と少なく、時系列評価は不安定になり得る。
記録のない月〜木曜日の性能を主張しない。検証期間で選択し、最終テストでの繰り返し調整はしない。
