# ADR-0002: データ品質監査の責務分離と判定結果

- 状態: 採用（実装済み・開発者本人による実データ監査結果を反映）
- 日付: 2026-10-26

## 背景

既存スクリプトはimport時にExcelを読み、人数・待ち時間の判定を複数の箇所で実施していた。
取消の案内時刻も変換失敗として集計しており、業務状態と不正データを分けにくかった。
今後の機械学習モデルとAPIで判定を再利用するため、I/Oから切り離す。

Codexには元Excelの内容の読込・変更を禁止し、合成データで実装を検証した。
その後、開発者本人がWSL Ubuntu環境でリファクタリング後の実装を使って実データを監査した。
本ADRは両工程を区別し、本人から共有された実測結果を記録する。
実データ全行を新旧実装で自動比較する検証までは実施していない。

## 決定

1. 3モジュールを維持する。
   `step1_audit.py`はファイル選択・Excel読込・表示・CLI、`data_validation.py`は入力構造、
   人数・取消・待ち時間・学習候補の判定と集計、`time_utils.py`は型別の時刻変換を担当する。
   `main()`とエントリポイントガードを設け、import時のI/Oをなくす。
2. 判定を共通化する。
   `validate_people()`と`audit_dataframe()`は共通の人数判定を呼ぶ。
   数値は旧スクリプトの集計と同じ`pd.to_numeric`で変換し、時刻は`parse_time()`で変換する。
   従来の`to_minutes()`は、失敗時にNaNを返す互換用の入口として残す。
   値と状態の組には小さなNamedTupleを使い、新たな依存は追加しない。
3. 状態コードは文字列にする。
   `valid`、`missing`、`conversion_error`、`invalid_type`、`non_finite`、`non_integer`、
   `out_of_range`、`total_mismatch`、`wait_mismatch`、`time_reversed`、`cancelled`を区別する。
   人数は項目順の入力エラーを優先し、次に整数・範囲・合計を検査する。
   待ち時間は項目別状態を保持し、取消、受付・案内・記録値のエラー、時刻逆転、不一致の順に代表理由を返す。
   不一致や時刻逆転のフラグも独立して保持するため、複数の問題を確認できる。
4. 取消フラグを保持し、案内時刻の変換失敗から区別する。
   空白を除いた案内時刻が「取消」で始まるという既存ルールを維持する。
   `キャンセル`列に真偽値を保持し、取消文字列を時刻変換に渡さない。
   `案内時刻検証結果`と`待ち時間検証結果`には`cancelled`を返す。
   取消行も人数・受付・記録待ち時間の検証を行い、待ち時間の記録有無も別途検出する。
   これは取消と変換失敗の区別であり、汎用の業務ステータスと品質結果を別々の型・スキーマに
   完全分離した実装ではない。検証結果の状態コードには業務上の取消も含まれる。
5. 受付から案内までは同日として計算する。
   根拠は依頼者が提示した「受付から案内まで日付をまたがない」という運用条件。
   時刻差は丸め前に負数を検出し、翌日の時刻への補正は行わない。
   記録待ち時間との比較は、従来どおり整数分への最近接丸め（中間は偶数側）を使用する。
6. 同日運用とは別に、23:00を受付・案内の上限とする。
   根拠は依頼者が提示した「PISOLAは23:00閉店」という条件。
   この条件に基づく監査方針として、受付・案内とも23:00は許容し、それを超える時刻を
   `out_of_range`として学習候補から除外する。同日運用だけから導かれる制限ではない。
   汎用の`parse_time()`は23:00超も時刻として変換でき、店舗の上限は
   `data_validation.py`の`CLOSING_MINUTES`と`_business_time()`で判定する。
   閉店後の案内が正当な記録として存在する場合も除外し得ることが制約となる。
   営業時間の変更、閉店後案内の許容、店舗・曜日ごとの営業時間、日付またぎ運用が必要になった時点で、
   受付と案内それぞれの許容範囲を本人が確認し、境界テストと学習候補への影響を含めて見直す。
   開店時刻は与えられていないため追加の下限を仮定しない。今回この実装は変更しない。
7. 学習候補は全検証の結果から導出する。
   取消以外で人数・待ち時間がともに`valid`の行を候補とし、目標件数を使わない。
   重複は従来どおり報告だけとし、除外条件には加えない。
   不一致・不正行も元の行とインデックスを維持したコピーに残す。
8. 入力の不確かさは処理前にエラーにする。
   `.xlsx`が1件の場合だけ自動選択し、複数ある場合は引数による明示指定を求める。
   ロックファイルを除外し、必須列・DataFrameの列名重複・0件を検査する。
   シート、ヘッダー、読込範囲、Nullの指定は維持する。
9. 移行の比較コードはテストに置く。
   本番に旧・新の人数判定を並存させず、旧式との回帰テストで互換性を確認する。
   225通りの人数組合せ、旧学習候補式、人数不一致1行・待ち時間不一致4行・取消2行を含む合成例を検証する。
   元Excelにアクセスしないガードを設け、Excel読込は一時領域で生成したブックで検証する。

## 検討した代替案

| 代替案 | 判断理由 |
| --- | --- |
| スクリプト内のベクトル判定と単体検証関数を並存 | 条件の変更時に片方だけ更新されるため、共通関数にまとめる |
| クラス階層・リポジトリ層・外部の検証ライブラリを導入 | 現在の規模では3モジュールと関数で責務を表現できる |
| 変換結果をNaNに集約 | 欠損・変換失敗・範囲違反の原因を区別できないため、値と状態を返す |
| 数値を`float()`だけで変換 | 旧`pd.to_numeric`が拒否していた`"1_0"`等を受け入れるため、旧集計側に合わせる |
| 取消行を不正データとして一括集計 | 業務上の取消とデータ品質の問題を分けて報告する必要がある |
| 汎用の業務ステータスと品質結果を別スキーマに分離 | 現在必要な取消フラグと項目別状態で表現できるため、APIの契約確定時に再検討する |
| 23:00超を報告だけにして学習候補に残す | 提示された閉店条件に合わせて現状は除外するが、正当な閉店後案内がある場合は見直しが必要 |
| `keep_default_na=False`で文字列`"NaN"`を保持 | 既存の欠損解釈や監査件数に影響し得るため、今回は変更しない。必要なら別途提案・検証する |
| 時刻逆転を日付またぎとして補正、または不一致行を削除 | 同日という業務条件と、元データを勝手に修正・削除しない制約に反する |
| 重複を学習候補から自動除外 | 現行の候補条件を変更するため、業務上の方針が決まるまで報告にとどめる |

## 意図的な仕様差分

- importでは監査を実行しない。実行時は`main()`を使う。
- ファイル0件・複数件、必須列不足、DataFrameの列名重複、データ0件を明示的なエラーにする。
  拡張子の大文字表記も許容する。
- 取消の案内時刻は変換失敗に数えない。取消行の記録値などの問題は項目別状態として保持する。
- 23:00を超える時刻を候補外とする。丸めると0分になる短い時刻逆転も候補外とする。
  いずれも従来候補になる場合があり、旧式との差をテストで明示する。
- 検証関数への直接入力では`pd.NA`等は欠損、文字列`"NaN"`は変換失敗、NumPyの真偽値も型違反とする。
  Excel読込では`"NaN"`もpandasによって欠損に変換されるため、直接入力と区別する（後述）。
  人数の`"1_0"`等は旧スクリプトの学習候補判定と同じく変換失敗とする。
  従来の`validate_people()`単独で返していた理由とは異なる場合がある。
- 新旧人数判定の差の表示を回帰テストに移し、監査出力を状態別の集計と要確認行の表示に整理する。
  「不正人数」は真偽値の型違反も含む。比較可能件数は型違反を除く。

## 採用理由とトレードオフ

既存の3モジュールと関数で責務を分けることで、追加依存なしに、Excel読込と独立して
判定をテスト・再利用できる。新旧判定を本番で二重管理せず、合成データの回帰テストに比較式を置く。
そのため、テストの対象外となる実データの全行互換性まで証明するものではない。

文字列の状態コードと診断列は既存の呼び出しやDataFrameで扱いやすい一方、
業務状態と品質を完全分離した型の保証はなく、API公開時の契約確定が必要になる。
代表理由は最初の問題を優先するため、複数の問題を見る際は項目別状態と独立フラグも参照する。
特に取消行では待ち時間の代表理由が`cancelled`でも、受付や記録値の問題が残り得る。
不一致と時刻逆転の独立フラグも同時に立ち得るため、理由別件数の合計を候補外件数とみなさない。

23:00上限は閉店条件を明示できる一方、正当な閉店後案内も除外し得る。
元データを修正・削除せず残すことで、業務ルールの見直し後にも再判定できる。

## 合成ExcelによるNaN読込の確認

`tests/test_step1_audit.py::test_excel_na_inference_differs_from_direct_validation`で、
pytestの`tmp_path`内に空欄、文字列`"NaN"`、`"通常の文字列"`を持つ合成Excelを生成する。
人数・受付時間・待ち時間の3項目をそれぞれ検証し、実際の`load_excel()`経由で`pd.read_excel()`を呼ぶ。
元Excelは使用せず、既存の一時領域限定読込ガードも維持する。

読込設定は`sheet_name="Sheet1"`、`header=1`、`usecols="B:U"`、`na_values=["Null"]`。
`keep_default_na`は指定していないため既定の`True`となり、`"Null"`以外にもpandas標準の
欠損表現が適用される。次が今回の合成Excelテストによる確認結果である。

| 入力 | 現行read_excelの読込後 | 読込後の検証結果 | 同じ値を読込せず検証関数へ直接入力 |
| --- | --- | --- | --- |
| 空欄（合成時は`None`） | 欠損値（`pd.isna`がTrue） | `missing` | `missing` |
| 文字列`"NaN"` | 欠損値（`pd.isna`がTrue） | `missing` | `conversion_error` |
| `"通常の文字列"` | 同じ文字列を保持 | `conversion_error` | `conversion_error` |

直接入力は`audit_dataframe()`へ値を持つDataFrameを渡し、対応する項目の検証結果を比較する。
`validate_people("NaN", 2, 1)`が`conversion_error`となる既存の単体テストとも整合する。
ここでの通常の文字列は人数・時刻・待ち時間として解釈できない値を使っている。

現行読込後は、元セルの空欄と文字列`"NaN"`の区別が失われる。
文字列を保持する要件が将来必要なら、`keep_default_na=False`と明示的な`na_values`の設計を
別途提案し、既存の欠損表現・検証結果・学習候補への影響を検証する。今回は読込仕様を変更しない。

## 影響・残課題

本人による実データ監査と要確認7行の一致確認は実施済み。
実データ全行を新旧実装で自動比較する検証は未実施であり、必要に応じて本人の環境で実施する。
旧判定式との自動比較は合成データの範囲であり、すべてのPython型や極端な数値の互換性までは保証しない。

日付・呼び出し番号の値自体の検証、重複の学習利用、人数・待ち時間の業務上の上限は今後の要件とする。
23:00上限は上記の業務条件の変化時に見直す。Excelでの空欄と文字列`"NaN"`の識別は現行読込ではできない。
API公開時には業務状態と品質の表現、状態コードと結果列、Excel読込と直接入力の欠損解釈の契約を確定する。
