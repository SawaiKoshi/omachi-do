# ADR-0016: 合成call限定UIの確認・固定送信と未確定操作の復旧

- 状態: 採用（合成call限定UIへの接続。自動試験結果は設計記録へ分離し、実ブラウザ確認は未完了）
- 記録日: 2026-11-10
- 関係: [ADR-0015](ADR-0015.md)の次工程として、ブラウザ呼出と未確定記録を実装する。
  同ADRの通常ラボ隔離・24時間・結果不明の原則を維持する。
  [ADR-0010](ADR-0010.md)の認証、[ADR-0007](ADR-0007.md)の操作台帳を再利用し、
  [ADR-0013](ADR-0013.md)・[ADR-0014](ADR-0014.md)の読取り専用原則への例外を合成callラボだけに限定する。

## 背景

call限定入口のAPI試験ができても、ブラウザには確認途中の変更、応答喪失、再読込み、複数タブという別の危険がある。
一般のスタッフ画面に書込みを開放せず、対象の確認と操作要求の固定をUI側でも検証する必要がある。
既存5秒更新の中止処理にPOSTを混ぜると、応答だけ失われて成功・失敗を取り違え得る。
またsessionStorageはタブごとで、単独では二つのタブによる新規操作を抑止できない。

## 決定

1. 認証済みの読取りに`X-Omachi-Preview: synthetic`と`X-Omachi-Preview-Actions: call`があり、
   v2、revision_required、write_enabled、訂正無効、正しいdatabase_id等がそろう場合だけcall UIを利用可能にする。
   サーバー由来の検証済み設定と応答ヘッダーを併せて確認し、画面の文言・ポート番号だけでは許可しない。
   これはUIの制限であり、実際の権限は既存call限定入口とCookie・Origin・CSRF・ストアが強制する。
   通常の8443ラボと一般画面では業務書込みも未確定操作の保存も始めない。
2. waiting/absentのメニューだけに実行可能な「呼出」を置く。
   選択時に最新operation-contextを取得し、日付付き番号、受付日時、人数、状態、操作内容を確認させる。
   確定直前にも再取得し、対象ID・状態・revision・DB識別子・世代・設定・許可操作等が変われば実行しない。
   called/seated/cancelledには新規呼出を提示しない。call以外は引き続き実行不可とする。
3. 同じブラウザの同一originではWeb Locks APIによる排他を必須にする。
   呼出UIを利用するタブが排他ロックを保持し、他タブまたは未対応環境では新規呼出・固定再送を許可しない。
   既存の未確定記録がある場合の認証付き結果照会は妨げない。
   これは協調するタブの抑止であり、サーバーのrevision・操作ID保護を置換しない。
4. 確定時にUUIDを一つ発行し、受付ID・database_idと、operation_id/action/expected_revision/write_epochの
   固定4項目を送信前にsessionStorageへ保存・読戻し検証する。失敗・破損では送信しない。
   同時に一つの未確定操作だけを扱い、連打、メニュー閉鎖、一覧更新で別IDを作らない。
   共有認証情報、Cookie、CSRF、受付詳細、予測、スナップショットは保存しない。
5. POSTと結果照会は通常の一覧・詳細更新と別の通信として扱う。各通信は15秒で期限を設けるが、
   中止・タイムアウトはDBの失敗証明としない。ログアウト等で受付表示を消しても、固定要求は保持する。
   通常ポーリングによってPOSTや結果照会を不要に中止しない。古い画面宛ての応答を受付表示へ適用しない。
6. POSTの応答喪失、形式不正、保存結果を伴わない409等では「結果不明・要照会」を残す。
   結果照会は人が選べるようにし、GETのHTTP 200と本文response_status/outcomeを分けて判定する。
   保存された拒否も確定した過去の結果であり、照会404は未実行の証明ではない。
   新ID・最新revisionへの自動付替え、旧APIへのフォールバックは行わない。
7. 通常復旧期間はADR-0015どおり24時間。期限内、同じDB・世代で、最新状態も再確認できる場合だけ、
   人の明示操作による同一ID・同一本文の再送を認める。要求の修正はしない。
   再ログイン後は新しいCSRFをメモリで取得し、まず既存操作IDを照会する。
   環境不一致では再送・新規呼出を止めて手動確認とする。期限超過・時計逆行では固定本文を
   最小の要手動確認マーカーへ置き換え、新規呼出を止める。
   破損・欠落が検出され復旧を保証できない場合も、安全側に停止する。
8. 保存結果を一覧へ直接書き戻さない。成功・無変更・拒否の確定結果は過去の受領証として表示し、
   最新operation-contextとの整合を確認してから未確定記録を解決し、全ページ一覧を再取得する。
   contextの照合に失敗すれば記録を維持し、記録解決後の一覧失敗では既存の表示拒否を行う。
   結果が確定した後の読取り失敗を理由にPOSTし直さない。
9. 5秒更新、受付IDによるDOM再利用、全ページの整合性検査とfail-closedを維持する。
   対象の状態・保護情報が変われば確認画面を失効させるが、送信済みの固定要求は消さない。
   変化のない背景更新で対象メニュー・フォーカス・スクロールを不用意に初期化しない。

## 理由

固定要求の保存と永続操作台帳を組み合わせれば、通信状況と受付状態を混同せず結果を照会できる。
読取りの更新世代と書込み結果の寿命を分けることで、画面の更新が操作の確定情報を壊さない。
合成ラボの明示的な能力とサーバー側の拒否を重ね、一般画面へ機能が広がることを防ぐ。

## 代替案

| 案 | 判断 |
| --- | --- |
| ポート・ラベル・allowed_actionsだけでcallを有効にする | 一般画面や汎用APIとの混同を防げないため不採用 |
| 確認画面の開始時だけ再取得する | 確定までの変更を見落とすため、確定直前も照合する |
| POSTを通常ポーリングと同じAbortControllerで管理する | 背景更新で結果不明を作るため不採用 |
| sessionStorageだけで複数タブの重複を防ぐ | タブごとに別記録を持てるため不採用。Web Locksを追加する |
| Web Locks非対応時は無保護で実行する | 今回の安全な検証条件を満たさないため実行不可とする |
| 404・期限超過・409の後に新IDを発行する | 未確定の操作と対応が切れるため不採用 |
| 保存済みreceptionを現在行として描画する | 操作後の別スタッフの変更を巻き戻して表示し得るため不採用 |

## トレードオフ・影響

ストレージ・Web Locksが利用できないブラウザでは、閲覧できてもcallは利用できない。
同一originの排他は同じブラウザの協調範囲に限られ、別ブラウザ・端末を隔離しない。
タブ終了・ブラウザ終了・ストレージ消去で未確定記録が失われる可能性があり、
再読込み時のロックの引継ぎもサーバー側の恒久的な排他ではない。
記録を失ったこと自体を必ず検出できるとは主張しない。sessionStorageだけで全復旧を保証しない。
残る場合は別の新規呼出へ進めず、操作台帳・現在状態の手動確認が必要となる。

共有資格情報は個人本人確認ではなく、複数worker用セッション基盤も未完成のまま。
ラボの通常終了では合成DBが破棄され、再起動するとdatabase_id・世代は別になる。
旧要求の再送を止める一方、消滅した旧DBの結果を新DBから取り戻すことはできない。
callは「声掛けの到達」や通知送信を証明しない。LINEは追加しない。
実DB、モデル、特徴量、推論、受付時予測、実待ち時間、品質承認、顧客UIは変更しない。
