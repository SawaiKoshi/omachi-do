# ADR-0001: データリーケージ防止のための予約件数の扱い

- **状態:** 採用（初期モデルの特徴量選定方針。モデル実装・精度検証は未実施）
- **記録日:** 2026-10-26
- **対象:** 飲食店待ち時間予測アプリ「おまちどう」
- **位置づけ:** 過去に決定した初期モデルの方針を遡って文書化する

## 1. 背景

「おまちどう」は、飲食店でお客様が受付した時点の情報から、実際に席へ案内されるまでの待ち時間を予測するアプリケーションである。

モデル開発に向けて、PISOLAの受付・案内記録と、曜日・天気・人数・時間帯別予約件数などのデータを収集した。

予約件数は店舗の混雑状況に関係する可能性があり、待ち時間予測に有用な特徴量の候補である。

しかし、収集したExcelの予約件数には、事前予約と当日追加された予約が混在している。

さらに、記録されている件数が、個々のお客様の受付時点で実際に把握できた予約件数であることを保証する履歴情報がない。

そのため、集計後の予約件数をそのまま学習に使うと、受付時点では知り得なかった情報が混入する可能性がある。

## 2. 解決すべき問題

### 2.1 データリーケージのリスク

データリーケージ（Data Leakage）とは、本来予測時に利用できない情報をモデルの学習や評価に利用し、実運用時よりも有利な条件で予測してしまう問題である。

例えば、18:10に受付したお客様の待ち時間を予測する場合を考える。

| 時刻 | 出来事 |
|---|---|
| 12:00 | 19:00来店予定の予約Aが登録される |
| 18:10 | お客様が受付し、待ち時間を予測する |
| 18:40 | 19:00来店予定の予約Bが追加される |
| 営業終了後 | 当日の予約件数がまとめられる |

18:10時点で、予約Aの存在は把握可能である。一方、18:40に新たに登録される予約Bは、その時点では未知の情報である。

営業終了後の集計値に予約Aと予約Bの両方が含まれていた場合、18:10の待ち時間予測にその集計値を使用すると、未来の情報を利用することになる。

重要なのは、**予約の来店予定時刻が未来であること自体は問題ではない**という点である。

受付時点ですでに登録されている将来の予約は、予測に使用できる可能性がある。

問題は、予約の登録・変更が予測時点より前だったか確認できないことである。

### 2.2 学習時と実運用時の情報の不一致

過去データでは営業終了後の予約件数を利用できても、実際のアプリでは受付時点で未登録の予約を把握できない。

この違いにより、学習時の入力情報と実運用時の入力情報が一致しなくなる。

その結果、オフライン評価で高い精度が得られても、実運用では同じ精度を再現できない可能性がある。

## 3. 決定

**初期の待ち時間予測モデルでは、時刻帯別の予約件数を説明変数（特徴量）から除外する。**

対象となる列は以下のとおりである。

| 除外する列 | 理由 |
|---|---|
| `予約件数_11時台` | 受付時点の集計値である保証がない |
| `予約件数_13時台` | 同上 |
| `予約件数_17時台` | 同上 |
| `予約件数_18時台` | 同上 |
| `予約件数_19時台` | 同上 |
| `予約件数_20時台` | 同上 |

また、`当日予約追加後か` についても、受付時点で利用可能な情報としての定義が確定しておらず、欠損も多いため、初期モデルの特徴量には採用しない。

これらの列は元データから削除しない。将来的な分析や特徴量追加の検討に利用できるよう保持する。

予約件数に由来する派生特徴量についても、予測時点で利用可能であると確認できるまでは生成・使用しない。

なお、他の特徴量についても同様に、受付時点で取得可能かを確認する。予約件数の除外だけで、すべてのデータリーケージが防止できるわけではない。

## 4. 検討した代替案

| 代替案 | メリット | 不採用・保留理由 |
|---|---|---|
| A. 既存の予約件数をそのまま使用 | 混雑を説明する情報を活用できる | 受付後に追加された予約を含む可能性がある |
| B. 予約件数の欠損を0などで補完して使用 | 欠損への対処が容易 | 欠損補完では未来情報の混入を解決できない |
| C. 受付時点の予約件数を既存データから再構成 | 情報を活用しながらリーケージを防げる可能性 | 各予約の登録・変更履歴が不足しており、現時点では正確な再構成ができない |
| D. 予約件数を一律に除外 | 予測時点で不明な情報の混入リスクを避けられる | 予約状況という有用な特徴量を利用できない |
| E. 受付時点の予約履歴を新たに収集 | 将来、正確な予約情報をモデルへ利用できる | 追加のデータ収集と管理の仕組みが必要 |

**採用案はDとする。**

ただし、予約件数を永久に利用しないという意味ではない。Eの方法で情報を取得できるようになった場合には、Cに相当する受付時点の予約情報の再構成を検討する。

## 5. 採用理由

第一に、待ち時間予測は受付時点での意思決定を支援する機能であるため、実際の予測時点で取得できる情報を使用する必要がある。

第二に、現在の予約件数の記録からは、個々のお客様の受付時点で利用可能だった件数を確実に再現できない。

第三に、誤った入力条件で高い評価値を得るよりも、実際の運用条件に近い情報だけで性能を評価することを優先した。

以上から、初期モデルでは予約件数を除外する方針が適切と判断した。

## 6. トレードオフ

### メリット

予測時点で把握できない予約情報の混入リスクを抑えられる。

また、学習時と実運用時に利用する情報の差を小さくできる。

初期モデルの特徴量選定も単純になり、各特徴量の利用可能性を説明しやすくなる。

### デメリット

予約件数は実際の混雑や席の利用状況に影響する可能性があるため、除外によって予測精度が低下する可能性がある。

特に、同じ曜日・時間帯・人数であっても、予約状況によって待ち時間が大きく変わる場合、その違いをモデルが十分に捉えられない可能性がある。

ただし、予約件数の除外によって実際にどれだけ精度が変わるかは、現時点では検証していない。

また、予約件数を除外しても、受付時点では未知の情報が別の特徴量に混入すれば、データリーケージは発生し得る。

## 7. 実装・検証方針

### 7.1 特徴量の選定

初期モデルの特徴量を設計する際、予約件数の6列と`当日予約追加後か`を予測入力から除外する。

学習用データに元の列を保持することと、モデルの入力に使用することは区別する。

将来、モデルの学習・評価・APIへの入力の各段階で、除外対象の列が使用されていないことを確認する。

### 7.2 評価方法

初期モデルの評価では、受付時点で利用可能な特徴量だけを使用する。

モデルの性能は、単純なベースラインと比較し、MAE（平均絶対誤差）などで評価する。

また、同じ営業日のデータが学習側と評価側に混在することによる過大評価を避けるため、日付を単位としたデータ分割を採用する方針とする。

ただし、日付による分割だけでは、未来情報を特徴量に使用する問題は解決できない。時系列を考慮した評価と、特徴量の利用可能性の検証は別々に必要である。

### 7.3 将来の再検討

予約情報を特徴量として採用するには、少なくとも各予約の登録・変更・取消がいつ行われたかを判定できる記録が必要である。

受付時点を時刻tとした場合、予約件数の再構成には、時刻tまでに確定していた情報のみを使用する。

その条件を満たせるようになった場合、予約件数を含むモデルと含まないモデルを、同じ評価条件で比較する。

比較する際には、予測精度だけでなく、必要なデータ収集・管理コストや、運用中に予約情報を取得できなかった場合の対処も考慮する。

## 8. 検証結果と現在の状態

ADR作成時点では、予約件数を除外した機械学習モデルの学習・精度評価は未実施である。

データ品質監査では元データ233件を確認し、暫定学習候補226件を抽出しているが、これは予約件数の除外による予測性能を示すものではない。

現時点で確認済みなのは、収集した予約件数に事前予約と当日追加予約が混在しており、受付時点の予約件数として利用可能であったことを保証する情報が不足しているというデータ収集上の制約である。

本ADRは、モデルの性能比較結果ではなく、リーケージ防止のための事前設計判断を記録したものである。

## 9. 残課題と見直し条件

予約件数を利用するために必要な履歴情報の収集方法は未確定である。

また、予約以外の特徴量についても、受付時点での利用可能性を個別に確認する必要がある。例えば、その時刻の待ち組数や天気などの情報は、実運用時点で利用できる形で構築する必要がある。

予約の登録・変更履歴を信頼できる形で取得できるようになった場合、本判断を再検討する。

再検討時は、データリーケージの有無を確認したうえで、モデルの性能比較を実施し、必要に応じて新たなADRに設計変更を記録する。
