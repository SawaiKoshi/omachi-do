# ADR-0014: 背景更新と対象単位の操作継続

- 状態: 採用（閲覧専用UIに実装、合成データで検証。実画面・実タッチの再確認は未完了）
- 記録日: 2026-11-04
- 関係: [ADR-0013](ADR-0013.md)の決定7の「再取得開始で閉じる」を部分的に置換。
  [ADR-0010](ADR-0010.md)の認証と[ADR-0011](ADR-0011.md)の全ページ検証・公開制限は維持する

## 背景

利用者のWindowsブラウザ確認で、5秒ごとの画面揺れとメニュー・操作の中断が報告された。
コードでは更新中メッセージを通常フローへ挿入して成功時に隠し、一覧の利用可能高さを変えていた。
またrefreshから呼ぶabortReadsが毎回メニュー・スワイプを破棄し、タブを無効化していた。
行は同一データなら再生成しなかったが、1行の変更でも一覧全行を作り直す構造だった。
非同期応答の世代検査・ページング拒否は維持すべき保護であり、これらを外して症状を隠さない。

## 決定

1. 取得完了から5秒後のポーリングを維持し、認証済みの検証済み一覧がある場合は背景で取得する。
   通常の更新開始では一覧・組数・タブ・フォーカス・メニュー・進行中スワイプを初期化しない。
   最終確認時刻は固定の表示枠で更新し、通常の更新中メッセージと薄色化は行わない。
2. セッションと両一覧の全ページを取り、版、取得条件、DB識別子・世代・設定、順番、重複・上限を検査する。
   完了まで部分データを表示へ適用せず、行と組数を同じ同期処理で反映する。
   古い通信は中止と画面側世代検査で破棄する。通常の定期取得は重複させない。
3. 受付IDと一覧種別でDOMを対応付け、表示項目・revision・有効案内イベント・許可操作が同じ行を再利用する。
   JSONプロパティ順だけの違いを変更とみなさない。追加・削除・変更行だけを挿入・削除・置換し、全一覧を作り直さない。
   反映直前のスクロール位置を保ち、通信開始時点へ戻さない。未変更行を不用意に移動・再フォーカスしない。
4. 同じ対象行とDB版・識別子・write_epoch・モード・訂正設定等が不変ならメニュー・スワイプを継続する。
   無関係な受付による全体view_versionの進行だけでは閉じない。
   閲覧詳細も初回取得で一覧の版を照合し、その後は対象・保護情報が不変なら維持する。
5. 対象消失、状態・revision・表示内容・許可操作・有効イベントの変更、DB世代・設定変更では対象表示を閉じる。
   通信失敗、409、形式不正、ページ不整合、認証失敗・期限切れ、ログアウト・非表示化では、
   メニューと受付情報を消すfail-closedを維持する。明示的な閉じる・タブ・外側・フォーカス移動・スクロール等も維持する。
6. ステータスと最終確認時刻に共通の固定高を用意し、表示切替で上部情報を押し下げない。
   既存のstableなスクロールバー領域を維持し、ブラウザの自動スクロール補正を抑える。
   1組1行・5列・上部集計・内部スクロール・タブ・閲覧専用メニューの基本構成は変えない。
7. 維持したメニューは最後に検証できた読取り対象であり、最新の書込み権限やロックではない。
   状態変更APIは引き続き接続しない。将来は実行直前の対象再取得、人の確認、操作ID保持・再送照会、
   expected_revision・write_epoch、409の自動再実行禁止を必須とし、メニューの保持で省略しない。

## 理由

変更がない定期取得をユーザーの操作と切り離し、同じ情報の確認で操作を中断しない。
継続の単位を対象受付にしつつ、背景取得の失敗時には速やかに閉じることで、閲覧の連続性と保護を両立する。

## 代替案

| 案 | 判断 |
| --- | --- |
| 更新間隔を延ばす・メニュー中は更新しない | 古い状態の検知を遅らせ、DOMと高さ変化の原因も残るため不採用 |
| 更新開始で常に閉じる | 初期方針だが、5秒ごとに操作が中断されるため見直す |
| 常にメニューと古い一覧を残す | 失敗・対象変更の後も操作対象と誤認するため不採用 |
| 全行を作り直して後からフォーカス・位置を復元 | 同じDOMの保持より副作用が多いため、対象IDによる差分反映を採用 |

## トレードオフ・影響

取得中は前回検証済みの閲覧情報を保持するため、外部変更の発生から更新完了までの遅延は残る。
通信ごとの期限15秒と既存セッション期限を維持し、失敗時は表示を消す。
変更行の置換や対象消失では操作中断が必要となり、一覧が短くなればスクロール位置も末尾へ制限され得る。
実際の高さ、フォーカス、タッチ感度とスクロールの慣性は模擬DOMでは証明できない。
RF、受付DB、品質承認、スタッフ認証、顧客UI、予測更新・キャッシュは変更しない。
