# ADR-0007: スタッフ操作の永続冪等性と競合防止

- 状態: 採用済み方針の後追い記録（今回レビュー対象）
- 記録日: 2026-11-02
- 記録区分: Step 5-Bの操作保護工程で採用した判断を今回初めてADR化する
- 関係: [ADR-0005](ADR-0005.md)の受付登録用キーとは別の保護。[ADR-0006](ADR-0006.md)のv2構造を使用

## 背景

同状態への再送を無変更にするだけでは、別の操作が間に入った後の古い要求を識別できない。
複数端末の競合やバックアップ復元後の遅延要求で、受付状態・案内実績を上書きする危険がある。

## 決定

1. 呼出・不在・復帰・案内・取消は保護付き`POST /staff/receptions/{id}/operations`で扱う。
   UUIDのoperation_id、expected_revision、write_epochを必須とする。
   認証主体はサーバーが決め、現在の共有認証を`shared_staff_token / shared-staff`として記録する。
2. `staff_operations`に要求版、正規化JSON全文とSHA-256、認証主体、結果本文・HTTP状態を永続保存する。
   トークンやその指紋は保存しない。同一ID・同一主体・同一要求は保存結果を返すだけで再適用しない。
   同一IDで内容・主体が異なる場合は409。ハッシュだけで同一性を判断しない。
3. 新規要求は現在世代とrevisionを比較し、不一致は409。
   有効な状態変更だけrevisionを1増やす。同状態の要求も最新条件が必要で、無変更時は増やさない。
   構文上有効な業務拒否も台帳に保存するため、「拒否ならDBファイル全体が不変」とはしない。
4. 書込ロック内で既存操作を照合してから、新規要求の世代・revision・遷移を確認する。
   状態・revision・イベント・操作結果を同じ`BEGIN IMMEDIATE`で確定する。
   保存済み再送結果は当時の結果であり、最新状態は別の読取りで確認する。
5. 結果照会`GET /staff/operations/{operation_id}`も毎回認証し、主体を照合する。
   通信応答が失われた場合は同じID・同じ要求で照会／再送する。
   409でrevisionだけを更新して自動再実行せず、最新情報と人の判断に基づく別操作にする。
6. v1とv2 legacyの旧API互換性は残すが、`revision_required`では旧`transition()`経路を
   ロック内で拒否し、DBトリガーも維持する。ブラウザからはlegacy時の保護付き書込みも拒否する。
   旧APIへのフォールバックはしない。
7. 復元だけでは世代は変わらない。復元後の再開前に停止下でwrite_epochを更新し、ストアを作り直すことを
   必須の運用条件とする。保存済み旧操作は歴史的結果を返せるが、新規の旧世代要求は拒否する。

## 理由

操作の同一性、対象の更新版、DBの書込み世代を分けて検査することで、再送・競合・復元の異なる危険に対処する。
状態と結果台帳を一緒に確定し、成功したのに結果が残らない中間状態を作らない。

## 代替案

| 案 | 判断 |
| --- | --- |
| ボタン無効化、同状態判定だけ | 複数端末・通信喪失・古い要求に対応できない |
| 既存本文なしAPIを必須JSONに変更 | v1/legacy利用者を壊すため専用APIを追加 |
| revisionだけ、または期限付きメモリ内操作ID | 復元後の版一致や再起動後の再送を防げない |

## トレードオフ・影響

台帳は増え続け、削除・ID再利用の運用は未実装。共有主体は個別スタッフを特定できない。
legacyでは旧経路を許すため、全書込み保護の強制には別途モード切替が必要。
実DBでの切替・世代更新コマンドは未提供で、この記録でも有効化しない。
受付順・受付日時・保存スナップショット・予測・実待ちの計算式は維持する。
