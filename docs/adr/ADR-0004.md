# ADR-0004: 少数営業日の待ち時間回帰モデルと時系列評価

- 状態: Step 3完了。本人による実データCV比較・最終テスト済み。事前固定のRandom Forestを初期採用、Dummyを比較基準として維持
- 日付: 2026-10-27（最終テスト結果の記録更新）
- 前提: [ADR-0001](ADR-0001.md)、[ADR-0002](ADR-0002.md)、[ADR-0003](ADR-0003.md)

## 背景と対象

受付時点の情報から案内までの待ち時間（分）を予測する複数の回帰モデルを、同じ過去→未来の
条件で比較する。本人によるStep 2の確認結果は、学習候補226件・14営業日である。
この件数と日数は汎用の分割・モデル判定条件へ埋め込まず、最終テスト専用CLIの実験設定として確認する。

初期モデルは「待ち組が発生する状況での案内までの待ち時間予測」を対象とする。
通常の平日や待ち時間0分を含む全来店客への予測性能は未検証である。データには実際に案内され、
記録の整合性を確認できた組だけが含まれる。取消客の仮想的な待ち時間を推定するものではない。
平日に待ち組が少ないという本人の現場経験は、待ち組発生確率の定量的な検証結果として扱わない。

営業日数が少なく、同じ日の記録には共通の混雑状況があるため、ランダムな行分割では過大評価の
恐れがある。最終テストを隔離し、開発用期間だけで学習期間を広げる時系列検証を行った。
候補固定後の最終テストも本人がWSLで実施した。AIは本作業で生Excelを読まず、最終テストを再実行しない。
以下の実データCV比較・最終テスト結果は、本人から共有された実測値として記録する。

## 決定: Step 3終了時点の初期採用モデル

事前に固定したRandom ForestをStep 3終了時点の初期採用モデルとする。Dummyを比較基準として残す。
最終テスト結果を使ったモデル再選定やパラメータ調整は行わない。この決定は運用投入の判断とは分ける。
将来は新たに収集したデータを用いて、受付時点の待ち組数や混雑情報などの特徴量追加と再評価を検討する。
これらの情報は現時点では取得しておらず、特徴量としても未実装である。

## 決定: Step 2の出力をそのまま評価へ渡す

`prepare_training_data()` が返すX・y・metadataを利用する。品質判定、学習候補抽出、
日付変換、時刻変換、曜日の符号化は再実装せず、Step 1・Step 2の仕様を変更しない。

Xは `BASE_FEATURE_COLUMNS` の10列、すなわち大人・子供・受付時刻（分）と曜日7列に限定する。
予約件数とその派生値、案内時刻、待ち時間、取消、識別情報、日付そのもの、品質判定列を含めない。
天気・祝日・長期休暇の特徴量は今回のモデル比較へ追加しない。
yはStep 2が計算・検証した待ち時間（分）、metadataは日付と元行位置の対応に利用する。

`model_evaluation.py` に次の責務を置き、ファイルI/Oから切り離す。

| API | 責務 |
| --- | --- |
| `ModelData(X, y, metadata)` | 評価に必要な3要素をまとめる |
| `split_development_test(prepared, final_test_days=2, expected_test_dates=None)` | 最新の営業日を最終テストとして隔離し、`DataPartition(development, final_test)` を返す |
| `expanding_date_folds(dates, initial_train_days=6, validation_days=2)` | 開発用期間の日付だけから、学習・検証の行位置を生成する |
| `compare_models(development, models=None, initial_train_days=6, validation_days=2, seed=42)` | 開発用データだけで比較し、`ComparisonResult` を返す |

X・y・metadataの長さ・インデックスの対応と特徴量の列構成を確認する。行の抽出は `.iloc` の
位置でそろえ、元入力の順序を保つ。インデックスが重複していてもラベルで結合し直さない。
日付を並べ替えるのは分割境界の決定に必要な営業日一覧であり、Xだけを独立に並べ替えない。

## 比較候補と過学習対策

各モデル群につき最初は1設定だけとする。下記は比較開始時の固定設定であり、性能によって
最適だと確認した値ではない。

| 候補 | 初期設定 | 採用理由・対策 |
| --- | --- | --- |
| `DummyRegressor` | `strategy="median"` | 各foldの学習区間の中央値を返すベースライン。複雑なモデルがこの基準を改善するかを見る |
| `Ridge` | `StandardScaler` と組むPipeline。`alpha=1.0`, `solver="svd"`, `random_state=42` | 正則化付きの単純な線形比較。単位の異なる人数・時刻等を標準化し、係数の複雑さを抑える |
| `RandomForestRegressor` | `n_estimators=100`, `max_depth=3`, `min_samples_leaf=5`, `random_state=42`, `n_jobs=1` | 非線形な関係を比較する。深さと葉の最低件数に制約を設け、少数行への過度な適合を抑える |
| `LGBMRegressor` | `n_estimators=100`, `learning_rate=0.05`, `max_depth=3`, `num_leaves=7`, `min_child_samples=10`, `reg_lambda=1.0`, `random_state=42`, `n_jobs=1`, `deterministic=True`, `force_col_wise=True` | 勾配ブースティングを比較する任意候補。深さ・葉数・葉の件数・正則化で複雑さを抑える |

全モデルに同じ日付分割を適用し、foldごとに推定器をcloneして学習する。乱数を使用する
モデルのseedを固定する。Dummy・StandardScaler・RidgeのSVD解法は乱数による学習を行わない。
実行時にはseed・モデルパラメータ・依存バージョンを残し、異なる環境で完全に同一の結果になる
ことまでは保証しない。

Ridgeの標準化は各foldのPipeline内で学習区間だけにfitする。検証区間へは学習済みの変換を
適用し、全データで平均・分散を計算しない。Ridgeでは正則化を用いて曜日7列を保持し、
Step 2の特徴量契約を維持する。学習を伴う別の変換を追加する場合も同じ隔離が必要である。
これは[scikit-learnのリーケージ防止とPipelineの説明](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage)
に従う。

中央値ベースラインの動作は[DummyRegressorの仕様](https://scikit-learn.org/stable/modules/generated/sklearn.dummy.DummyRegressor.html)、
正則化と解法は[Ridgeの仕様](https://scikit-learn.org/stable/modules/generated/sklearn.linear_model.Ridge.html)、
木の制約と乱数固定は[RandomForestRegressorの仕様](https://scikit-learn.org/stable/modules/generated/sklearn.ensemble.RandomForestRegressor.html)
を参照した。LightGBMの深さ・葉数・葉の件数とCPUでの決定性の設定は、
[公式パラメータ仕様](https://lightgbm.readthedocs.io/en/stable/Parameters.html)を参照した。

## 評価設計と最終テストの隔離

入力に存在する有効な営業日を昇順に列挙し、最新2営業日を先に最終テストとして取り分ける。
本人が指定した今回の最終テスト日は **2026-07-12、2026-08-07** である。
実データ実行時は `expected_test_dates` にこの日付を外部設定として渡し、実際に隔離した最新2日と
一致することを確認する。日付をモデルの判定ロジックへハードコードせず、入力の追加・変更により
境界が意図せず動いた場合は、本人が評価計画を確認できるようエラーにする。

残る12営業日には、既定値で次の3foldを生成する。

| fold | 学習 | 検証 |
| --- | --- | --- |
| 1 | 最初の6営業日 | 続く2営業日（7〜8日目） |
| 2 | 最初の8営業日 | 続く2営業日（9〜10日目） |
| 3 | 最初の10営業日 | 続く2営業日（11〜12日目） |

営業日数はカレンダー上の連続日数ではなく、学習候補がある異なる日付の数である。
学習は常に検証より前とし、同じ営業日を両方に入れない。営業日数が不足する場合や、指定した
検証日数に満たない余りが生じる場合はエラーとし、ランダム分割や無言の行・日付の省略へ切り替えない。
学習区間を拡大するため、前foldの検証日が次foldの学習日に入ることは評価計画の一部である。

`compare_models()` の引数は `development` だけであり、`final_test` を受け取らない。
最終テストの正解・予測・誤差をモデル比較に使わず、通常の `step3_evaluate.py` には最終テストを
採点する機能を設けない。最終テストはモデル群・パラメータ・特徴量・アンサンブル重みの選択に
使用しない。固定した候補の最終評価は、本人が専用コマンドを明示実行したときだけ行う。

### 固定候補の最終テスト専用機能

`final_evaluation.py` は既存の `split_development_test()`・`candidate_models()`・誤差計算を再利用する。
`step3_final_test.py` は既存のExcel読込・`prepare_training_data()` を再利用し、最終テスト日が
2026-07-12と2026-08-07、開発206件・12営業日、テスト20件であることを学習前に確認する。
期待値は専用CLIの実験設定とし、汎用分割やモデルの判定条件には埋め込まない。
相違があれば評価を始めず終了する。学習日とテスト日の非重複・過去→未来の順序も確認する。

既存設定のRandom Forest（seed=42）と中央値Dummyだけを開発206件でそれぞれ再学習し、
最終20件を予測する。モデル生成・特徴量変換を二重実装せず、fitには開発X・yだけを渡す。
最終テストはfit・特徴量の統計量推定・モデル選定に渡さない。最終テスト専用CLIには
モデル・seed・ハイパーパラメータを変更するオプションや自動ランキングを設けない。

全体および営業日別のMAE・RMSEに加え、次の割合（%）を計算する。

- 絶対誤差10分以内: `100 * mean(abs(y - prediction) <= 10)`。10分ちょうどを含む。
- 絶対誤差20分超: `100 * mean(abs(y - prediction) > 20)`。20分ちょうどを含まない。

予測や誤差を丸めてから判定しない。これらはお客様向けサービスの実用性を確認する補助指標で、
モデル再選定・パラメータ調整には使用しない。CLIは集計値だけを表示し、個人情報・元行・
行ごとの予測は表示・保存しない。ライブラリ内部の予測対応は元の入力順と `.iloc` 位置で保つ。
最終テスト機能の実装確認は合成データで行い、その後、本人がWSLで実データの最終テストを明示実行した。
その実測値は上記に記録し、この文書更新では再実行しない。

### 指標と比較方法

主要指標はMAE（分）とし、RMSE（分）も報告する。
MAEは `mean(abs(y - prediction))`、RMSEは `sqrt(mean((y - prediction) ** 2))` で計算する。

`ComparisonResult` は次を返す。

- `fold_metrics`: モデル・foldごとの期間、件数、学習MAE/RMSE、検証MAE/RMSEと誤差の差。
- `daily_metrics`: モデル・fold・検証営業日ごとの件数、MAE、RMSE。
- `summary`: foldを同じ重みで扱う平均と標準偏差（`ddof=0`）、検証予測をまとめたMAE/RMSE。
- `predictions`: 検証行の予測と正解、および行・日付の対応。最終テストの行を含めない。
- `model_parameters`: 比較した設定。`skipped_models`: 任意依存などで比較できなかった候補と理由。

foldの単純平均と、全検証行をまとめた指標は重みが異なる。後者は件数の多い日・foldの影響を
強く受けるため、営業日別の値も併せて確認する。初期学習期間だけに使う6営業日は、検証全体の
指標には含まれない。学習誤差は学習データへの当てはまりであり、将来への予測性能とは区別する。

3foldは学習期間が重なり、独立した試行ではない。標準偏差は今回のfold間のばらつきを表す記述値とし、
信頼区間や統計的な優劣の証明に読み替えない。わずかなMAE差だけで優劣を断定せず、中央値基準からの
改善、営業日別の安定性、過学習の兆候、モデルの単純さを見て本人が判断する。自動採用は行わない。

## 代替案と保留理由

| 代替案 | 判断 |
| --- | --- |
| ランダムな行分割 | 同日の状況が学習・検証に混在し、未来への性能を評価できないため不採用 |
| 通常の行単位の時系列分割 | 同日を途中で分ける恐れがあるため、異なる日付を単位に分割する |
| 単一の検証期間 | 期間依存を確認しにくいため、最終テストを温存した拡大学習の3foldを初期案とする |
| 全データで標準化してから分割 | 検証・最終テストの分布が学習へ入るため不採用 |
