# ADR-0005: 受付管理と参考待ち時間予測の分離

- 状態: Step 4実装（合成データで検証。本人による配信用モデル生成は未実施）
- 日付: 2026-10-27
- 前提: [ADR-0001](ADR-0001.md)、[ADR-0002](ADR-0002.md)、[ADR-0003](ADR-0003.md)、[ADR-0004](ADR-0004.md)
- 対象: ローカル開発用バックエンド。外部公開・実店舗への導入は行わない

## 背景

お客様が入力するのは大人人数と子供人数だけとし、受付日時、曜日、番号、待ち組数はシステムが生成する。
スタッフは番号・人数・状態の一覧から、呼び出し、案内完了、キャンセル等を記録する。
待ち時間予測が取得できない場合も受付業務を続けられることを優先する。

Step 3の初期採用モデルは事前固定のRandom Forestである。実用に十分な精度は確認されておらず、
通常の平日や待ち組がない状況の性能も未検証である。受付データの蓄積、予測値の提示、モデル更新の判断を分け、
Step 1〜3の既存実装・特徴量契約・実測結果は変更しない。

## 決定: 受付管理・予測・本人用学習を分ける

| モジュール | 責務 |
| --- | --- |
| `reception_store.py` | SQLiteへの受付登録、番号発行、待ち組集計、受付時点の保存、状態遷移、イベント、冪等登録 |
| `prediction_service.py` | 予測対象条件の判定、Step 2の特徴量生成、固定モデルによる推論、参考値の注意文 |
| `model_artifact.py` | 固定RFの学習関数、モデル情報、ローカル保存・読込と配信契約の確認 |
| `step4_train_model.py` | 本人確認後にだけExcelを読み、226候補全件で配信用モデルを生成するCLI |
| `prediction_api.py` | FastAPIの入力検証、ローカル接続制限、スタッフ認証、上記機能のHTTP窓口 |

APIは学習処理やExcel読込を呼ばない。DBとモデルの準備はimport時には行わず、
[FastAPIのlifespan](https://fastapi.tiangolo.com/advanced/events/)で行う。
モデルは起動時に一度読み込み、変更したファイルをリクエストのたびに自動読込しない。

## APIと入力の契約

| API | 利用者・動作 |
| --- | --- |
| `GET /health` | ローカルからDBの読取、モデル利用可否、スタッフ操作の設定有無を確認 |
| `POST /predict` | 人数から参考予測と現在のスナップショットを返す。受付登録・採番・イベント保存をしない |
| `POST /receptions` | 人数と`Idempotency-Key`を受け、実受付を登録。初回201、同じ受付の再送200 |
| `GET /queue` | スタッフ認証必須。未案内の受付番号・人数・状態を受付順で返す |
| `POST /receptions/{id}/seat` | スタッフ認証必須。実際の案内完了を記録 |
| `POST /receptions/{id}/cancel` | スタッフ認証必須。キャンセルを記録 |
| `POST /receptions/{id}/call` | スタッフ認証必須。呼び出しを記録 |
| `POST /receptions/{id}/absent` | スタッフ認証必須。呼び出し後の不在を記録 |
| `POST /receptions/{id}/return` | スタッフ認証必須。不在から受付待機中へ戻す |

お客様用POSTのJSONは`adults`と`children`だけで、どちらも0以上の整数、合計1〜100人とする。
文字列・真偽値・小数・欠損・余剰項目を拒否する。
既存の人数判定と同じく大人0人・子供1人も受け付ける。
100人は新APIの技術的な入力上限であり、店舗の収容人数やモデルの精度を保証する値ではない。
大人数を含む人数別の性能は別途確認が必要である。
[Pydanticのstrict mode](https://docs.pydantic.dev/latest/concepts/strict_mode/)を利用し、暗黙の型変換を避ける。

日時、曜日、合計人数、番号、待ち組数をお客様から受け取らない。スタッフ操作も本文を受け取らず、
日時等を含む本文があれば422とする。日時はタイムゾーン付きのサーバー時計から生成し、JSTで保存する。
入力不正422、存在しない受付404、不正な遷移・冪等キーの人数不一致409とする。
DBのロック待ち超過や保存失敗は503とし、`Retry-After`と同じ送信キーでの再試行を案内する。
保存に失敗した受付を成功扱いしない。

## 受付番号・同時登録・二重送信

内部IDはUUID、表示番号はJSTの受付日と日別連番からなる`YYYYMMDD-NNN`とする。
連番は3桁以上で表示し、日付を含めて一意制約を設ける。受付順には別の単調増加整数
`reception_order`を使用し、同じ日時の受付を区別する。番号や順番を時刻だけから作らない。

受付登録では個別のDB接続で`BEGIN IMMEDIATE`を取得してから時計を読み、受付直前の集計、
採番、受付・スナップショット・予測結果・イベント・再送用応答の保存を同じトランザクションで行う。
案内やキャンセルも同じ書込ロックを使い、途中の状態が集計に混ざらないようにする。
処理失敗時はロールバックし、番号やイベントだけが残らないようにする。
[SQLiteのトランザクション仕様](https://www.sqlite.org/lang_transaction.html)に従い、同時書込は直列化する。
ロックの待ち時間には上限があり、無制限に待ち続けない。

登録にはUUIDの`Idempotency-Key`を必須とする。キーと内部IDの対応をDBで一意に保存し、
同じキー・同じ人数の再送は、後で状態が変わっていても**初回登録時の応答**を返す。
再予測・再採番・イベント追加はしない。同じキーで人数が異なる場合は409とする。
別のキーなら同じ人数でも別受付として登録するため、同じ人数という理由だけで重複排除しない。
Step 5では1回の受付操作に1個のキーを生成し、通信再試行中はそのキーを保持する必要がある。

DB全体の最終記録時刻を保存し、新しい書込時刻がそれより前なら拒否する。
時刻逆転を翌日扱いに補正したり、実際とは違う時刻へ切り上げたりしない。
時計の設定不良は本人が確認して解消する。日付が変わっても未処理受付は自動削除・自動終了せず、
新しい日の日別連番と区別して一覧・集計に残す。

## 状態と実際の待ち時間

| 状態 | 意味 | 異なる状態への許可遷移 |
| --- | --- | --- |
| `waiting` | 受付待機中 | `called`、`seated`、`cancelled` |
| `called` | 呼び出し中。まだ席への案内は完了していない | `absent`、`seated`、`cancelled` |
| `absent` | 呼び出したが不在。受付は未終了 | `waiting`、`called`、`seated`、`cancelled` |
| `seated` | 実際の案内完了 | なし |
| `cancelled` | キャンセル完了 | なし |

同じ状態への再送は現在の記録を返し、イベントや時刻を追加・更新しない。
案内済み・キャンセル済みから別の状態への変更は拒否する。呼び出さず直接案内・キャンセルする操作も許可する。
`called_at`は最新の呼び出し時刻を保持し、過去の呼び出し・不在・復帰の経緯はイベントに残す。

`seated_at`は案内完了時だけ、`cancelled_at`はキャンセル時だけ保存する。
実際の待ち時間は`(seated_at - received_at).total_seconds() / 60`で計算し、小数分を保持する。
呼び出し時刻で代用せず、予測値を実績へコピーしない。
受付と同じ時刻の案内も可能で、実際の待ち時間0分を記録できる。
キャンセル・未案内の実待ち時間は`NULL`とする。

業務DBは翌日に実際に案内した場合も実日時の差を保存し、23:00超や日付またぎを推測補正しない。
これは既存学習データの「同日・23:00以下・整数分への丸め」というラベル定義とは別である。
新しい受付記録や0分の実績を現行モデルの学習へ自動投入しない。

## 受付順・案内順と受付時点の保存

待ち組数は`waiting`・`called`・`absent`を含む未案内グループとして集計する。
`seated`・`cancelled`は含めない。不在でも受付を終了していないため、現段階では待ち組数に含める。

受付の挿入直前に、本人を含めず以下を保存する。

- `waiting_groups`: 未案内グループの総数。
- `ahead_groups`: 受付順で本人より前にいる未案内グループ数。
- `party_size_groups`: 合計人数1〜2名、3〜4名、5名以上ごとの未案内グループ数。
- `ahead_same_size_groups`: 本人と同じ人数帯で、受付順が前の未案内グループ数。
- `captured_at`と`source`: 集計の基準日時と取得元。

新規受付を末尾へ追加する現在の処理では、既存の未案内受付はすべて本人より前なので
`waiting_groups`と`ahead_groups`は同値になる。総数と受付順上の前方組数という意味は分けて保存する。
人数帯の組数は同じ人数帯に属する組数であり、合計人数が完全に同じ組数ではない。
保存済みのスナップショットは、その後の案内・キャンセル・追加受付で更新しない。
`POST /predict`も仮の新規来店者として同じ集計を読み取るが、その値をDBへ保存しない。

受付順は案内順の保証ではない。先着4名より後着2名を先に案内しても、先着順情報や過去の集計は変更しない。
実際の案内順は案内完了イベントから確認する。
空席数や席の変化は取得しておらず、推測値を実測として保存しない。
APIの注意文とStep 5の画面には「人数や席の空き状況により、ご案内順が前後する場合があります。」を使用する。

## DBで分けて保存するもの

SQLiteファイルは既定で`var/receptions.sqlite3`とし、外部キーと一意制約・値の制約を使用する。
`PRAGMA user_version=1`を記録し、未知のバージョンや想定外のテーブル構成は起動時に拒否する。
既存DBの自動移行・自動削除は実装しない。

| テーブル | 保存する理由・主な情報 |
| --- | --- |
| `receptions` | 内部ID、表示番号、受付順、受付日時、人数、現在状態、呼出・案内・取消日時、実待ち分、記録日時、取得元 |
| `reception_snapshots` | 受付時点で利用可能だった待ち組数・人数構成を、後続の状態変更から独立して保持 |
| `predictions` | 予測日時・取得元、状態、予測分、モデル版、注意文を保存し、後で実績と比較可能にする |
| `reception_events` | 登録と状態変更の前後状態、発生日時、記録日時、取得元を保持し、受付後に確定した情報を区別 |
| `daily_counters` | 日別番号をトランザクション内で発行 |
| `idempotency_keys` | キーと人数・受付ID・初回応答を保存し、同時送信や再送を同じ受付に対応付ける |
| `store_metadata` | DB全体で記録時刻の逆転を検知 |

日時の取得元は受付API、スタッフ操作、受付DB、ローカル予測サービスとして区別する。
イベントは現在の即時操作では`occurred_at`と`recorded_at`が等しいが、意味を分けて保存する。
将来の遅延取得・訂正を実装済みとはしない。APIの応答スキーマで必要な項目だけを返す。
氏名・電話番号等は受付スキーマに持たず、予測や受付管理に不要な個人情報は保存しない。

## 参考予測を返す条件とモデルの生成

数値の予測を返す条件は、JSTで金・土・日曜日、受付直前に未案内グループが1組以上、
受付時刻が23:00以下、かつ本人確認後の配信用モデルを利用可能であることとする。
これは取得済みデータに合わせた初期の運用制限であり、その範囲で十分な精度を保証するものではない。
開店時刻の下限は未確認のため仮定しない。23:00直後の端数秒も対象外にする。

予測対象外は`no_waiting_groups`・`unsupported_weekday`・`unsupported_time`、
モデル未配置・読込不整合は`model_unavailable`、推論失敗は`prediction_failed`として、
予測分を`NULL`で返す。条件を順に判定するため、モデル未配置でも対象外の理由が先に返る場合がある。
待ち組なしを0分予測へ置き換えず、即時案内も保証しない。
推論値は有限かつ非負の場合だけ生の小数分で返し、丸め・0分への補正を行わない。
登録時には予測不能の状態も保存し、受付を継続する。実際の待ち時間と混同しない。
注意文では精度未確認・対象の偏り・案内順の前後を示し、金曜日は2営業日・12件という少なさも伝える。

モデル入力は既存の`build_features()`から得る、次の固定10列を同じ順序で使用する。

```text
大人, 子供, 受付時刻_分, 曜日_月, 曜日_火, 曜日_水, 曜日_木, 曜日_金, 曜日_土, 曜日_日
```

待ち組数は保存と予測可否の判定に使用するが、現行RFの特徴量へ追加しない。
天気・予約・席情報・案内時刻・待ち時間・識別情報も追加しない。
Step 2の時刻変換を再利用し、秒・マイクロ秒は小数分で扱う。

RFは`candidate_models(seed=42, include_lightgbm=False)`の既存設定を再利用する。
木100本、`max_depth=3`、`min_samples_leaf=5`、`max_features=1.0`、`random_state=42`、
`n_jobs=1`を変更せず、追加アンサンブル・探索・自動採用を実装しない。DummyはStep 3の比較基準として残す。

正式配信用モデルの生成は本人が`--confirm-full-training`、Excelパス、モデル版を明示して実行する。
CLIはExcel日付方式1900、学習候補226件・14営業日・2026-05-24〜2026-08-07の条件を確認してから、
最終テスト用に分けていた行も含む全候補で固定RFを再学習する。
APIの配信時にも、本人確認済み全候補での再学習というメタデータ条件を確認する。
これはファイルの出所や本人の操作を暗号学的に証明する仕組みではない。

モデルbundleにバージョン、生成時刻、全パラメータ、seed、特徴量順序、学習件数・日付一覧・期間・
目的変数の定義・取得元・Excel日付方式、Pythonと主要依存のバージョン、既存前処理等4ファイルのSHA-256を保存する。
読込時は環境・コード・設定・学習済み列名の一致を確認し、不一致なら予測を利用不可にする。
依存は`requirements-api.txt`に固定し、モデル更新は本人の明示操作とする。
保存は一時ファイルから単一bundleを作成し、同じモデル版の既存ファイルを上書きしない。

配信用再学習では精度評価を実行せず、Step 3のCV・最終テスト実測値を書き換えない。
226件で再学習したモデルの将来性能を、206件で学習した最終テスト結果と同一視しない。
自動再学習は行わず、新しい期間の品質監査・評価・比較を本人が確認した場合だけ更新を検討する。

## セキュリティとローカル開発の制約

Uvicornはloopbackへbindし、転送ヘッダーを信用しない設定で起動する。APIでも接続元がloopbackか確認する。
[TrustedHostMiddleware](https://www.starlette.io/middleware/#trustedhostmiddleware)で許可するHostを
`127.0.0.1`・`localhost`・`[::1]`に限定する。Host検証と接続元制限はそれぞれ行う。
`Origin`がある場合は同一オリジンだけを許可し、CORS・プロキシ経由接続を有効化しない。
OpenAPI、Swagger UI、ReDocは無効にし、オンラインのドキュメント資材を読み込まない。

スタッフ一覧と状態変更は`X-Staff-Token`で分ける。本人が32文字以上のランダムな値を
`OMACHI_STAFF_TOKEN`に設定し、比較には定数時間の比較を使う。
未設定時はスタッフ操作を503、トークン不足・不一致は401とする。短い・空白だけの設定は起動時に拒否する。
お客様側へトークンを渡す設計は採用しない。
これはローカル開発用の共有トークンであり、スタッフ別アカウント・権限・操作責任者の監査は未実装である。

モデルパスは本人の設定からだけ受け取り、モデルアップロードやURLからの取得は実装しない。
joblibは読込時にコードを実行し得るため、本人が管理する信頼できるローカルファイルだけを指定する。
読込後のメタデータ検証は、安全なデシリアライズや改ざん・悪意あるファイルへの対策を保証しない。
モデルが使えなくても受付は継続するが、信頼できないファイルを安全に試す用途には使わない。

DB・SQLite付随ファイル・モデル・元Excel・環境変数ファイルはGit管理対象外とする。
入力検証応答やモデル読込エラーに元の入力値・ローカルパスを返さず、応答のキャッシュを抑止する。
ローカルPCにアクセスできる利用者への保護はOSの権限に依存する。
DB暗号化、バックアップ・復元、保存期間・削除、公開環境のHTTPS・認証・負荷制御は未実装であり、
今回の構成をそのまま外部公開・実店舗運用へ持ち込まない。

## 将来の追加情報と採用しなかった設計

現在は自然に得られる受付・状態変更・予測を分けて保存する。将来の追加観測は受付に紐付く別の構造として、
項目名・値・単位・観測日時・記録日時・取得元・受付時点で利用可能になった日時を検討する。
未取得の値や利用可能日時は`NULL`等で表現し、未取得を0や推測値で埋めない。
この追加観測テーブル、観測API、受付時点の再構成処理は今回実装していない。

今回保存した待ち組数・人数帯・前方の同人数帯組数は、新データで有効性を検証する将来の特徴量候補である。
天気・気温、祝日・学校休暇、受付時点で確定している予約、席種別の空席状況、席状態の変化時刻も将来候補にとどめる。
これらの自動取得、外部サービス連携、特徴量化は未実装で、スタッフに毎回の手入力を求めない。
予約は登録・変更履歴を確認し、天気や空席も受付後に確定した値を混ぜない。

| 代替案 | 採用しない理由 |
| --- | --- |
| 予測と同時に必ず実受付を保存 | 試算が実履歴へ混入するため、`/predict`を分離 |
| モデルが使えなければ受付も停止 | 受付業務を維持する必要があるため |
| `MAX(番号)+1`やメモリ上の採番、ロック前の集計 | 同時受付や複数接続で番号・待ち組数が競合するため |
| 同じ人数・日時の受付を自動削除 | 正当な別グループを誤って消すため、送信キーで再送を識別 |
| 受付順にしか案内できない制約 | 人数と席により案内順が前後する業務に合わないため |
| 呼び出し時刻を案内完了として扱う | 実際の待ち時間の定義が変わるため |
| 現在の待ち組数から過去の値を再計算 | 受付時点の情報を失い、未来情報が混入するため |
| 推測した空席・天気等や未学習特徴量を追加 | 実測の裏付けとモデル評価がないため |
| 受付のたびに再学習・最終テストで再選定 | 品質確認と将来期間の評価を経ない更新になるため |
| クラウドDB・外部公開・本格画面・複雑な権限管理 | Step 4のローカル最小構成を超えるため |

## 合成テストとStep 5の課題

pytestは合成データと一時DB・一時モデルだけを使用する。既存の元Excel読込ガードを維持し、
同時受付の番号・集計、同一キー同時再送、状態遷移、案内順の入替、スナップショット不変性、実待ち分、
0分、日時逆転、予測のみの無書込、未配置モデル、固定特徴量順序、モデル保存・読込、入力とスタッフ権限を検証する。
最終のpytest件数・実行コマンド・`git diff --check`結果はREADMEと作業報告を参照する。
この合成検証は、実店舗運用やモデルの予測精度を検証した結果ではない。
AIは生Excelの読込・変更・実データ学習・最終テスト再実行を行わず、本人が後でWSLで配信用モデルを生成する。

人数だけの受付画面と顧客向けの最新待ち状況は、後述のStep 5-Aで追加する。
スタッフ専用一覧と呼出・不在・復帰・案内・取消の操作画面、スタッフ認証情報の保持方法は今後の対象とする。

実店舗のタブレットからLAN接続する構成は現状のloopback制限では動かない。導入前に端末とスタッフの認証・
通信保護・共有PCの扱い、DBの保存先・バックアップ・復旧、時刻同期、日跨ぎの未処理受付、
不在を待ち組数に含める運用、受付の訂正や誤取消の救済、保存期間、予測誤差の許容範囲を本人が確認する。
今回の実装には訂正・復元・自動営業終了・席管理・外部通知・予約連携・モデル自動更新を追加しない。

## Step 5-A追記: 顧客向けダッシュボード（2026-10-28）

同一オリジンのHTML・CSS・JavaScriptで、トップ画面の待ち状況から人数選択へ進む受付画面を追加する。
`POST /receptions`の成功を確認するとすぐトップへ戻し、受付番号・人数・受付時点の前方待ち組数・参考予測を
30秒間の通知で伝える。通知中も次の受付を開始でき、各番号を一覧でも30秒間強調する。
前方待ち組数は本人を含まない`snapshot.waiting_groups`を使い、最新一覧の組数と区別する。
予測が`NULL`なら表示できない旨を示し、0分に置き換えない。予測の注意文と案内順が前後する旨を表示する。

表示専用の`GET /public/queue`を新設し、スタッフ用`GET /queue`は顧客画面から呼ばない。
公開応答は`waiting_groups`、`groups`、`notice`だけとし、`groups`の各要素も
`display_number`・`total_people`・`status`に制限する。専用の応答モデルでも余剰項目を除く。
状態は`waiting`・`called`・`absent`だけで、すべて待ち組数に含め、受付順で返す。
内部UUID・内部履歴・スタッフ認証情報等は公開しない。呼出中・不在は専用領域にも表示し、
番号は常に`YYYY/MM/DD · NNN番`と表示して、日付をまたぐ未案内受付を区別する。

一覧はページが表示されている間、前の取得完了から5秒後に更新し、15秒でタイムアウトする。
通常の定期取得を重複させず、受付成功時は直ちに再取得し、成功前の古い取得結果を適用しない。
失敗時は最後の一覧と更新時刻を残して最新ではない旨を表示し、初回未取得の組数は0組にしない。
通知は新しい人数選択、タブ非表示、ページ離脱でも消し、受付番号や応答をブラウザ保存領域へ残さない。

UUIDの`Idempotency-Key`と人数だけを送信前に`sessionStorage`へ保存し、結果不明なら同じキーで再送する。
再読み込み・履歴復帰後も未確認のキーを保持し、確認前の人数変更・戻る操作・自動リセットを止める。
60秒間の無操作によるトップへの自動復帰は未送信の人数選択だけに適用し、送信中・結果不明には適用しない。
DB、既存APIの入力・予測・認証の契約、loopback・Host・Origin制限は変更しない。
「公開一覧」は認証不要のローカル表示用であり、外部公開や別端末からのLAN接続を可能にする変更ではない。

初回Step 5-A画面の人数選択・受付登録・60秒後のリセットは本人が実ブラウザで確認済み。
追加改善は一時DBの公開API統合テストとJavaScriptのDOM・通信・時計のテストで検証し、
今回のダッシュボードの実ブラウザ・実機タブレットでの表示確認は別途必要とする。
件数と実行コマンドはREADMEに記録し、Step 4の検証結果は変更しない。

## Step 5-A追記: 参考予測を中心とするUI・UX（2026-10-28）

子供から高齢者まで参考待ち時間と受付操作を読み取りやすくするため、トップの優先順位を
**AI参考待ち時間 → 現在の待ち組数 → 受付する**とする。最初は大人2名の参考値だけを大きく表示し、
必要な場合に「大人4名」へ切り替える。人数選択では選択中の大人・子供に対応する参考値を示す。
予測できない場合は数値を作らず、その旨を表示して待ち組数を最も目立たせる。

横向きタブレットでは2列に分け、左に主要情報と受付ボタン、右に受付完了通知と一覧を配置する。
1024×768・1366×768では主要情報と受付ボタンをスクロールなしで確認できるCSS構成とし、長い一覧は内部でスクロールする。
完了通知は右側に収め、受付ボタンを押し出さない。呼出中・不在の番号は維持し、該当者がいない専用領域だけを非表示にする。
一覧の番号は3桁以上の連番を大きく、受付日を補足として表示し、日付をまたぐ番号を区別する。
狭い画面や短い画面では縦並びとし、受付ボタンを画面下部に固定してページスクロールを許す。
通常文字18px以上、操作領域44px以上を基本とし、読みやすさを保つために文字を縮小しない。
定期更新では変わらない行を再利用し、スクロール位置やフォーカスを不用意に変えない。

受付前の参考値には既存の読取用`POST /predict`を使い、JSONは`adults`・`children`だけとする。
予測の表示・人数変更で受付登録、番号発行、DB保存を行わない。受付は既存の`POST /receptions`で確定し、
予測の取得中・不可・通信失敗でも確定できる。予測応答を待つ処理や新しい確認操作は設けない。
モデルの精度・特徴量・予測対象条件・Step 3の評価結果は変更しない。
現在の待ち組数や席の空き状況を特徴量に含まないことを説明し、現在の混雑から正確に求めた時間と誤認させない。
曜日・時刻・モデルの条件外や待ち組数0では数値を示さず、`null`を0分へ置き換えない。

大きな参考値は`約13分`のように`Math.ceil()`で1分単位に切り上げる。
APIの値は変更せず、元の小数分とすべての注意文を開閉式の説明で確認でき、取得時刻も表示する。
受付完了通知は従来どおり受付APIが返した予測の小数分と`snapshot.waiting_groups`を使い、
受付前の参考値や現在の待ち組数で置き換えない。

予測取得の制御を`web/static/prediction-preview.mjs`へ分け、公開一覧の5秒更新とは独立させる。
同じ大人・子供の組合せの結果を60秒保持し、最大32件に制限する。
トップ表示中だけ約60秒間隔で再取得し、人数変更では400ms待って最後の入力を取得する。
同じ人数の有効な結果と取得中リクエストを再利用し、古い人数・画面に対するリクエストは取り消す。
非表示時や受付送信中は予測取得を止め、一覧更新のたびに推論しない。
公開一覧で0組を確認したら数値表示と定期予測を止め、0組・待ち組ありの切替でキャッシュを破棄する。
0組から待ち組ありへ変わった場合は、画面が表示中で予測取得が可能な状態なら改めて1回取得する。
キャッシュによる通常最大約60秒前の参考値は取得時刻で補う。同じ人数の再取得中だけは直前値と「更新中」を示し、
15秒のタイムアウトまたは失敗後には数値を消す。人数変更では別人数の古い値を表示しない。
受付時点の予測は従来どおり受付APIから受け取る。

受付成功後の即時復帰・30秒通知と番号強調、未送信の人数選択だけを対象とする60秒の無操作復帰、
公開一覧の5秒更新、`Idempotency-Key`による結果不明時の同一受付再送を維持する。
DB・既存API・スタッフ認証・localhost/loopback・Host・Origin制限を変えず、スタッフ用`GET /queue`を顧客画面から使わない。
公開一覧の情報制限も維持し、スタッフ認証情報・内部UUID・内部履歴を追加公開しない。

改善前後の静的ファイル量・通信件数・受付操作回数・待ち状況の反映間隔と、レイアウトの静的確認を
[性能・表示確認記録](../step5-a-ux-performance.md)に残す。新しい予測モジュールにより初回の資産取得が1回増えるが、
外部フォント・画像・フレームワークは追加しない。実ブラウザがインストールされていないため、
実際の描画速度、各サイズの見切れ、タッチ操作、文字拡大の実画面検証は未実施とする。
DOM・通信・時計のテストとHTTP統合テストの結果はREADMEと作業報告に記録し、
通信件数の比較を実ブラウザの高速化や実モデルの推論精度の検証と混同しない。

## Step 5-A追記: 人数選択と完了通知の簡素化（2026-10-28）

本人が1024×768で確認したトップの基本構成を維持し、人数選択の入力・参考予測を横並びにして、
その下へ全幅の受付確定ボタンを置く。余白・重複説明を減らし、本文18px・人数操作64pxを維持する。
詳細な予測説明を展開した場合は説明部分をスクロールさせ、主要操作を押し下げない。

完了通知は「受付完了・日付付き受付番号・受付人数」と閉じる操作だけにし、内部スクロール・重ね合わせを使わない。
読み取る時間を確保するため30秒表示を維持し、次の受付開始・非表示・ページ離脱でも消す。
