# ADR-0015: 呼出限定の合成HTTPS検証と結果不明操作の復旧境界

- 状態: 採用（合成call限定ラボを実装。ブラウザ書込み・未確定操作の保存は次工程の設計）
- 記録日: 2026-11-09
- 関係: [ADR-0007](ADR-0007.md)の操作台帳と競合保護、[ADR-0010](ADR-0010.md)の認証を再利用する。
  [ADR-0012](ADR-0012.md)の閲覧専用入口は変更せず、別入口の限定実験を追加する。
  [ADR-0013](ADR-0013.md)・[ADR-0014](ADR-0014.md)のUIは引き続き閲覧専用とする。

## 背景

呼出をブラウザへ接続する前に、実DBへ到達せずに認証・冪等性・競合・復旧を検証したい。
通常ラボの書込み制限を解除すると、汎用operations APIの案内・取消まで利用できてしまう。
また応答が届かないだけで失敗と断定して新IDで再送すると、保存済み結果を追跡できなくなる。

## 決定

1. 呼出の状態遷移、認証、操作結果保存は既存
   `POST /staff/receptions/{id}/operations`とストアに任せる。
   ラボの追加コードは通信の許可範囲を狭めるもので、別の呼出処理・認証方式は実装しない。
2. 通常の`staff_https_lab.py`は閲覧専用・legacy・訂正無効のまま維持する。
   新しい明示入口`staff_call_https_lab.py`だけが、新規一時領域の合成v1を生成し、
   そのDBだけをv2へ明示移行して`revision_required`に設定する。訂正は無効のままとする。
   DB・モデル・待受ホスト・worker・操作範囲を選ぶ引数や汎用書込みスイッチは設けない。
3. HTTPSの`staff.localhost`、127.0.0.1、単一worker、proxy非信頼、アクセスログなしを維持する。
   新入口の既定ポートは8444。Cookieはポート別に分離されないため、同ホストのラボを同時利用しない。
   既存TLSファイル検証・秘密を出さない診断を再利用し、HTTPへのフォールバックは行わない。
4. 通常ラボが許可するGET/HEADとセッションPOST/DELETEに加え、正確なoperations経路の
   `action="call"`だけを許可する。HTTPSとHostを入口でも確認し、別Hostからのヘッダートークン認証へ逃がさない。
   JSONは4 KiB・受信5秒に制限し、重複キー・不正形式・非有限数・余分なフィールドを拒否する。
   既存の厳密な要求モデルでUUID・整数revision等を検査した元の本文だけを既存アプリへ渡す。
   Cookie・Origin・CSRF・モード・操作ID・期待revision・write_epochはそこで必ず検査する。
   seat/absent/return/cancel、訂正、品質操作、旧更新API、顧客向け業務APIは通さない。
5. 通信切断・タイムアウト・応答の解析不能は「結果不明」とする。画面側の中止はDBの中止証明ではない。
   同じ操作ID・同じ主体・固定要求の再送と認証付き結果照会で回復し、新IDで自動再実行しない。
   409で期待revisionを書き換えて自動再送しない。404の結果照会だけでも未実行とは断定しない。
   保存済み結果は過去の受領証であり、現在状態は別途operation-contextで確認する。
   結果照会のHTTP 200と、本文の`response_status`・`outcome`も区別する。
6. 次工程のUIでは、メニュー選択時と最終実行直前に対象を再取得し、受付番号・人数・状態を確認画面に示す。
   ID、状態、revision、database_id、write_epoch、許可操作・設定の変化があれば確認を無効化する。
   処理中・結果不明では同じ対象の新規操作を抑止する。背景更新で未確定操作を破棄しない。
   現UIのメニュー保持はロックでも実行許可でもない。今回UIのボタン・API接続は追加しない。

## 次工程のsessionStorage方針（今回未実装）

- スタッフ専用オリジン・タブ単位で、一度に一つの未確定操作を保存する。
  保存範囲は形式版、操作UUID、受付UUID、action、期待revision、write_epoch、database_id、
  作成時刻・期限に限る。共有トークン、Cookie、CSRF、氏名、人数、予測、スナップショット、応答全文は保存しない。
  認証秘密の保存禁止はADR-0010のまま維持する。localStorageへは移さない。
- 固定要求を送る前に保存と読戻しを検証し、保存できなければ送信しない。
  固定要求の保持・通常復旧期間は作成から24時間とする。期限・形式・UUID・整数・DB識別子を検証する。
  期限超過や時計の逆行では再送しない。結果不明を期限だけで成功・失敗に確定しない。
  期限超過後は固定要求を捨て、操作UUID・受付UUID・database_idと「要手動確認」の最小マーカーを
  解決まで残す。マーカーを残せない場合も、新IDでの自動再実行を禁止する。
  このマーカーは24時間を超えて残り得る。24時間は自動復旧対象の上限で、未確定記録の自動消去期限ではない。
- 再ログイン後は新しいセッションとメモリ上のCSRFを取得し、まず同じ操作IDの結果を照会する。
  保存された値を権限の証拠にせず、共有認証主体とDBの一致をサーバーで確認する。
  結果があれば受付・actionとの対応を確認し、現在状態も再取得してから解決する。
  404や通信失敗は未確定のまま扱う。期限内かつDB・世代が一致する場合に限り、
  人が選択した同じID・固定本文の再送を検討し、自動送信しない。
  別DB・世代変更時は過去の結果照会と手動確認に限定し、旧要求を新世代へ付け替えない。
- ログアウト・セッション失効では受付表示と認証情報を消すが、未確定記録を解決済みにしない。
  確定した結果と現在状態を照合した後に記録を消す。結果受領後の読取り失敗では操作をやり直さない。
- タブを閉じる、ブラウザを終了する、ストレージを消去する等で記録は失われ得る。
  sessionStorageだけでは他端末・全障害の復旧を保証しない。操作IDを失った場合の監査検索・手動確認手順、
  複数タブの抑止も次工程で検証する。保存・照会・期限・再ログインの試験が揃うまでUI書込みを完成扱いにしない。

## 理由

既存の原子的な操作台帳と認証を通すことで二重の実装を避け、実験の権限をcallに限定できる。
結果不明を明示すれば、通信状態を業務状態と誤認せず安全に復旧できる。
段階を分けることで、UIを接続する前にサーバー側の拒否条件を独立して確認できる。

## 代替案

| 案 | 判断 |
| --- | --- |
| 通常ラボにallow-writesを追加 | 閲覧専用の保証とADR-0012を曖昧にするため不採用 |
| 新しいcall APIと独自認証を作る | 既存の冪等性・認証・監査と二重管理になるため不採用 |
| 汎用operationsをそのまま公開 | 別アクションまで実行可能になるため不採用 |
| 応答喪失時に新ID・最新revisionで再実行 | 先の操作との対応が切れるため不採用 |
| sessionStorageだけで復旧完了とする | タブ喪失・別端末・DB復元後を保証できないため不採用 |

## トレードオフ・影響

要求の検査がラボ入口と既存APIの二段になるため、API契約変更時には入口の試験も見直す。
一時領域は同じOS利用者の悪意あるコードを隔離するサンドボックスではない。
通常終了では破棄するが強制終了時の一時領域残存はあり得る。合成データ以外を入れない。
業務時刻はfixtureの最終時刻に固定し、セッション期限は実時間で計測する。
実モデルは読み込まず、RF・特徴量・実績・品質承認・顧客UIを変更しない。
callは既存のwaiting/absentからcalledへの遷移を使う。同じrevisionのcalledへの再要求は既存のno_changeであり、
実際に声を掛けたことや外部通知の到達を証明しない。LINE機能は追加しない。
ラボの読取りAPIが示す汎用allowed_actionsはcall限定入口の権限を広げず、UI項目も実行不能のままである。
共有認証は個人の本人確認ではない。実店舗向け個人認証・複数worker・運用復旧は未完成で、実DBへ適用しない。

## 2026-11-10追記: ブラウザ呼出接続への移行

上記の未接続・未実装は2026-11-09の記録として保持する。
次工程の合成call限定ブラウザ接続は[ADR-0016](ADR-0016.md)と[設計記録](../design/staff-call-ui.md)で扱う。
通常ラボの閲覧専用、固定要求、24時間後の最小マーカー、結果不明の維持、共有主体の限界は変更しない。
同一origin内の複数タブによる新規操作を抑えるため、Web Locks必須という追加判断を0016に記録する。
これは実店舗・別端末・記録喪失をまたぐ完全な復旧の実装を意味しない。
