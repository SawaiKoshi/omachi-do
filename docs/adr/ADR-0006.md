# ADR-0006: SQLite v2と合成DB限定の明示移行

- 状態: 採用済み方針の後追い記録（今回レビュー対象）
- 記録日: 2026-11-02
- 記録区分: Step 5-Bの移行ラボ・v2ストア統合で採用した判断を今回初めてADR化する
- 関係: [ADR-0005](ADR-0005.md)のDB契約を拡張。自動移行禁止とv1互換性を維持する

## 背景

スタッフ操作の監査、訂正、品質管理にはv2が必要だが、既存の受付情報・予測・実績と
イベントID・採番を失う移行は許容できない。既存DBを開くだけで変換する設計も避ける。

## 決定

1. 既存7テーブルを維持し、revision、DB識別子・write_epoch・操作モード等、イベント監査列と、
   操作台帳・品質問題・レビュー・判定・移行記録の5テーブルをv2に追加する。
   移行済み受付のrevisionは0、旧イベントは`legacy_v1`とし、操作者や過去revisionを捏造しない。
2. 移行は`python -B -m reception_migration`の明示処理だけで行う。
   現コマンドは`temporary_workspace()`が登録した一時合成DBに限定する。
   専用一時領域・所有者・権限・リンク・inode・SHA-256を検査し、実DB・バックアップ・指定実験DBを対象にしない。
3. `isolation_level=None`でトランザクションを明示制御し、`executescript()`を使わない。
   BEGIN前に外部キーOFFを確認し、`BEGIN IMMEDIATE`の中で新テーブル作成、明示列コピー、
   旧テーブル削除、新テーブルを正式名へ変更する。旧テーブルを先にリネームしない。
   制約・トリガー再作成と検査、移行記録・user_versionを同じコミットに含め、終了後は外部キーONを確認する。
4. 旧全カラムをSQLiteの型、NULL、実数表現、元JSON文字列まで比較し、
   主キー、受付順、日別採番、旧event_idと`sqlite_sequence`を維持する。
   実待ち時間や保存予測を移行中に再計算しない。
5. ストアは既知のv1/v2の定義と履歴を厳密に検査し、不完全・未知・版不一致を修復せず拒否する。
   開いた版と、v2のdatabase_id/write_epochを固定し、業務DML前にも同じトランザクションで再検査する。
   新規DBはv1のまま。アプリ起動時に移行を呼ばない。
6. 移行後は`staff_write_mode=legacy`、`seat_corrections_enabled=0`。
   コミット前の失敗は全体を戻し、コミット後検証失敗は`PostCommitValidationError`として隔離を求める。
   後者を「ロールバック成功」と報告しない。

## 理由

移行を通常起動から切り離すことで、誤接続時の破壊を防ぎ、値と型を保持したことをレビューできる。
連番の最大値だけで復元すると削除済みIDを再利用し得るため、元のsequence自体を保存する。

## 代替案

| 案 | 判断 |
| --- | --- |
| 起動時に自動移行・不足列を補完 | 意図しない実DB変更と未知状態の隠蔽につながるため不採用 |
| DBを作り直してJSONや待ち時間を再生成 | 元の型・表現・履歴・採番の保持を保証できないため不採用 |
| 任意パスを許可する汎用移行CLI | 実データ向け手順・復旧が未承認のため保留 |

## トレードオフ・影響

厳密な定義照合は手動のインデックス追加等も拒否し得る。履歴検査にはデータ量に応じた負荷がある。
リンク・登録検査は誤指定防止であり、同じOSユーザーによる故意の改変を隔離する仕組みではない。
強制終了試験は電源断・ストレージ故障の保証ではない。実DB移行と実運用の復元手順は未提供である。
この判断はRF、特徴量、Excel前処理、API応答・顧客UIを変更しない。
