# ADR-0011: スタッフ読取りの整合性と公開情報の分離

- 状態: 採用済み方針の後追い記録（今回レビュー対象）
- 記録日: 2026-11-02
- 記録区分: Step 5-Bの読取りAPI・閲覧画面工程で採用した判断を今回初めてADR化する
- 関係: [ADR-0005](ADR-0005.md)の公開応答制限を維持。[ADR-0007](ADR-0007.md)・[0010](ADR-0010.md)の操作・認証を支援

## 背景

未案内一覧だけでは誤案内の訂正対象を探せない。
画面に古いrevisionと新しい状態を混在させたり、最初の50件だけで待ち組数を集計したりすると、誤操作につながる。
操作のためのDB識別子や監査情報を顧客向けAPIへ追加することも避ける。

## 決定

1. 毎回認証する`GET /staff/receptions`と`GET /staff/receptions/{id}/operation-context`を使う。
   既存の詳細・イベント・操作結果照会APIは用途と契約を維持する。
   公開一覧をスタッフ用内部情報で拡張しない。
2. `active`はwaiting/called/absentを元のreception_order昇順、日付の下限なしで返す。
   `recently_seated`は現在有効な案内event_id降順、案内時刻から既定24時間、指定1〜168時間とする。
   案内日時と受付日時を分け、日付またぎの未案内や最近の案内を受付日で落とさない。
3. 行は許可列だけから構成する。ID、日付付き番号、受付順・日時、人数、状態・状態日時、実待ち、revision、
   allowed_actions、有効案内イベントを返す。共通metadataにdatabase_id・write_epoch・モード・view_version等を含める。
   共有秘密、保存予測JSON、操作要求本文を新しい一覧・操作対象応答に含めない。
4. 有効案内イベントは現在seated、最新イベントもseated、from_statusが未案内、時刻整合を確認して返す。
   訂正済みの旧案内を対象として提示しない。allowed_actionsは既存の遷移表とモードから導出する。
   v1/legacyはブラウザ操作不可、訂正にはさらに有効化フラグを必要とする。
5. 1ページ既定50件・最大100件のkeysetページングとする。
   各応答のmetadata・行・イベントは一つの読取トランザクションで取得する。
   カーソルはHMAC付き、条件・as_of・イベント最大IDを含む版・設定に結び付け、5分で失効する。
   版変更は409、改変・期限切れ・条件変更は422。各ページも認証する。
6. 複数ページを一つの長いDBトランザクションで保持する方式は採らない。
   画面は全ページの版・順序・重複・進行を確認し、両一覧の版が一致した場合だけ公開する。
   100件×最大100ページを超えた場合は不完全な組数を出さず失敗とする。
   組数は全active行から状態別に数え、タブで隠れた行も集計に含める。
7. 取得完了から5秒後に定期更新し、各通信は15秒で期限を設ける。
   古い応答は中止と画面側世代検査で破棄する。通信失敗・409・不正形式時は組数・行・詳細を消し、
   古い値を最新として表示しない。詳細も一覧の版と照合する。
   API文字列はtextContent等で扱い、HTMLとして実行しない。

## 理由

現在の操作対象を認証済みの限定応答として取得し、状態変更の保護に必要な情報を一貫させる。
ページング途中の更新は検出してやり直すことで、異なる時点の集計を黙って混ぜない。

## 代替案

| 案 | 判断 |
| --- | --- |
| 公開APIへ内部ID・revisionを追加 | 顧客への公開範囲を広げるため不採用 |
| 最初のページだけ集計、オフセットだけで続き取得 | 誤集計・更新中の重複や欠落につながるため不採用 |
| 長時間のDB読取をページ間で保持 | 接続管理・期限・ロックの負担が増えるため現段階では不採用 |

## トレードオフ・影響

全体イベント版の変化でページングをやり直すため、繁忙時には表示まで時間がかかり得る。
全件取得と定期認証の負荷は実データ量で評価する。view_versionは品質レビュー版や学習許可を表さない。
allowed_actionsは表示支援であり、書込時の認証・revision等の再検査を置換しない。
読取りでは状態・受付順・スナップショット・保存予測・品質判断を更新しない。
