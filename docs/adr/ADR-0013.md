# ADR-0013: 横向きタブレット一覧と実行しない操作メニュー

- 状態: 採用済み方針の後追い記録（今回レビュー対象、実機UX検証は未完了）
- 記録日: 2026-11-02
- 記録区分: 今回の横向きタブレットUI実装後に初めてADR化する。実装前から存在した記録ではない
- 関係: [ADR-0010](ADR-0010.md)・[0011](ADR-0011.md)を再利用。顧客向けUIを記録した[0005](ADR-0005.md)とは別の画面

## 背景

忙しい飲食店では複数組を一目で確認したい一方、各行へ多数の実行ボタンを置くと高さと誤タップが増える。
主な利用環境は横向きタブレットとし、縦スクロール、PC・キーボードでも同じ情報に到達できる必要がある。
状態変更の安全な確認・再送管理を作る前に、見た目のメニューを実操作へ結び付けてはいけない。

## 決定

1. 1024px程度の横向きタブレットを主対象とし、1組1行のコンパクトな5列にする。
   日付付き受付番号、受付時刻、大人・子供、現在状態、常設「⋯」を表示する。
   番号の主要部分を強調して年付き日付も残す。未案内は元の受付順で、状態による並べ替えをしない。
2. 通常高さではヘッダー・取得状況・待機/呼出/不在の組数・切替タブをスクロール外に置き、
   一覧内部を縦スクロールする。見出しはstickyとし、未案内と最近の案内履歴を同じ領域のタブで切り替える。
   最近の案内は有効イベント順を維持し、案内時刻と元の受付時刻を区別する。
3. 標準行高は最小60 CSS px、操作領域は44px以上、三点は幅48pxを確保する。
   縦向き・PCにも対応し、狭幅は横スクロール、短い画面は外側スクロールを許して情報を隠さない。
   件数を収めるために文字やタップ領域を過度に縮小しない。
4. 右スワイプは指を離した時に**メニューを開くだけ**とし、状態変更を確定しない。
   タッチ/ペンのみで右72px以上、縦最大20px以内、横が縦の3倍以上、1.2秒以内を初期条件にする。
   縦・斜め優勢、左移動、複数指、中断・離脱・スクロールでは失効させる。
   `pan-y pinch-zoom`で縦スクロール・拡大を残し、移動後のポインタークリックを500ms抑止する。
   これらの閾値は実機検証で見直せる実装値であり、業務上固定の仕様にはしない。
5. 常設「⋯」から同じ表示関数を使い、マウス・キーボードの代替を残す。
   開けるメニューは一つとし、対象番号・状態を明示する。Esc/閉じるで三点へフォーカスを戻す。
   タブはARIAと左右/Home/Endに対応し、静的メニュー説明は見出し付きregionとして扱う。
6. 表示する操作名は既存allowed_actionsの既知項目だけを普通の文章リストにし、
   「未接続・実行不可」を明示する。実行ボタン・危険なダミーハンドラーを置かない。
   番号は従来の読取り詳細を開く。案内・取消・訂正・LINEの実行UIは作らない。
7. 初期実装では更新開始時にもスワイプとメニューを閉じた。
   **2026-11-04: この更新開始時の方針は[ADR-0014](ADR-0014.md)で変更する。**
   同じ対象・状態・revision・DB世代・設定なら背景更新をまたいで維持し、対象変更や検証失敗時に閉じる。
   別行、タブ切替、外側、フォーカス移動、スクロールでは従来どおり閉じる。
   通信失敗・409・期限切れ・ログアウト・非表示では対象番号を含む情報を消す。
   古いDOMからも開かせず、認証済み・一覧が最新のときだけ閲覧操作を許可する。
8. **UI実装と状態変更API接続を別工程にする。** 現UIの通信は既存読取りとセッション作成・破棄に限定する。
   次工程では重要操作の確認画面、最新対象取得、操作ID保持・結果照会、revision・世代、
   409の自動再実行禁止、訂正理由・有効イベントを別途設計・結合検証する。
   現時点でこれらの状態変更UIを実装済みとは扱わない。

## 理由

一覧の比較しやすさを保ちながら、操作候補の発見と実行を分け、誤スワイプが業務記録を変更する危険を避ける。
三点を残せばジェスチャーの発見しにくさと入力手段の違いを補える。
認証・読取り・データ更新の既存責務を変えずに、操作性を先に評価できる。

## 代替案

| 案 | 判断 |
| --- | --- |
| 行下へ全操作ボタンを常設 | 行高・誤タップの懸念がある。実機でメニュー方式が遅ければ再比較する |
| スワイプ即時案内・スワイプだけのメニュー | 誤操作と入力手段の制約から不採用 |
| 未案内と履歴を上下に常時表示 | 画面全体が長くなりやすいためタブを第一候補にする |
| メニューと状態変更を同時に接続 | UX評価と更新安全性を分けて確認するため現段階では不採用 |

## トレードオフ・影響

メニューを開く1操作が増え、隠れた項目の発見性が課題となる。
初期実装の5秒更新による閉鎖はWindows確認で操作中断が報告され、ADR-0014で見直した。
実機で誤タップ・縦スクロール・短いスワイプ・文字拡大を比較し、必要なら変更・削除する仮設計である。
1024×768で約6行等の目安はCSSからの見積りで、実測値ではない。
受付順・実待ち・保存予測・品質管理・認証・顧客用更新間隔/キャッシュは変更しない。
既存バックエンドに状態変更APIがあることと、現UIから実行可能であることを混同しない。

## 検証方法・実装範囲

[HTML](../../web/staff/index.html)、[CSS](../../web/staff/assets/staff.css)、[JS](../../web/staff/assets/staff.mjs)、
[JS試験](../../tests/frontend/staff.test.mjs)と[タブレット記録](../design/staff-tablet-ui.md)を照合した。
模擬DOMで受付順・5項目、スワイプ中断、三点との一致、Esc/フォーカス、更新失効、
151件の集計、通信・認証失敗、業務POSTなしを確認する。前工程の記録はPython 1,613件・JS 208件成功。
このADR追加では再実行していない。

新レイアウトの実描画・実タッチは未検証。合成HTTPS環境で1024×768、1280×800、縦向き、PC、
文字拡大・ブラウザUIの高さ変動、内部スクロール、実測行数、連続操作とNetworkの業務POST不在を手動確認する。
既存プレビューは少数行なので、大量行の実機スクロールには別の合成fixtureが必要。
前工程で利用者が確認したWindows基本動作を、この新レイアウトの検証結果に流用しない。
