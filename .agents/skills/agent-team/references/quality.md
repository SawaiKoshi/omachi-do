# 品質確認と、失敗したときの対応

## 品質確認の流れ

| 段階 | いつ | 誰 | 内容 |
|------|------|----|------|
| 実行前の確認 | プラン（手順3〜4） | 子・統括 | 前提にするファイル・関数・コマンドが実在するか（`git ls-files`、`git grep`）。承認が要る場所に触るか。依存の追加がないか |
| ゲート | 実装・修正のたび（手順7・10） | 実装役 | `.agents/team/gate.sh`：秘密情報の混入チェック、空白エラー、リポジトリ固有のテスト・静的チェック |
| 回帰の差分分析 | レビュー（手順8） | Codex | 変えた関数・ファイルの呼び出し元を `git grep` でたどり、変わる挙動を一覧にする |
| 例外ケースの検査 | レビュー（手順8） | Codex | `profile.md` の「例外ケースの観点」を1つずつ確認する |
| 最終確認 | 手順11 | 統括 | 最新SHA・ゲート結果・PR本文・変更範囲 |

## テストが失敗したとき

1. 失敗したテスト名と、エラーの最初の数行（秘密情報が出ていないか確認してから）を記録する。
2. 原因を「今回の変更が原因」「元から失敗していた」「環境の問題」に分ける。元から失敗していたかは、worktree の外で `origin/main` を確かめるか、ユーザーに聞く。推測で決めない。
3. 今回の変更が原因なら直す。テストを消す・skip にする・期待値を実装に合わせて書き換えることはしない（仕様変更としてプランで承認されている場合を除く）。

## 同じ失敗を繰り返すとき（止まる基準）

- **同じテストが同じ理由で2回続けて失敗したら止まる**。3回目は試さない。
- **修正の往復（実装→ゲート失敗→修正）が合計3回を超えたら止まる**。
- 止まったら、試したことと結果、考えられる原因、次の選択肢（例：プランを見直す／範囲を狭める／ユーザーが調べる）を統括に返す。統括は Issue に `agent:needs-human` を付け、ユーザーに報告する。

## 切り戻し

- 自分のブランチの自分のコミットを取り消すときは `git revert <SHA>` を使い、履歴を書き換えない（force push が要る操作はしない）。
- まだコミットしていない変更を捨てたいときは、どのファイルを捨てるか統括に報告する。`git reset --hard`・`git clean`・`git checkout -- .` は安全ガードが止めるので、必要ならユーザーに頼む。
- プランから外れてしまった場合は、それ以上進めず、外れた範囲を報告する。

## 秘密情報

- ゲートは差分に含まれる秘密情報らしき文字列を見つけると、**値を表示せずに**ファイル名と行番号だけを出して失敗する。
- 見つかったら、その行をコミットから外し、ユーザーに報告する。すでに push していたら、鍵の無効化が必要かもしれないので、すぐユーザーに知らせる。
