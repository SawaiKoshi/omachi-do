# 12の手順の詳細

`<N>` は Issue番号、`<slug>` は英小文字とハイフンの短い名前（例：`wait-time-rounding`）。

## 1. タスクを拾う

```sh
gh issue list --label agent:ready --state open --json number,title,labels,body --limit 20
```

- 1件ずつ「プロジェクト・規模（小／中／大）・リスク（`profile.md` の承認が必要な場所に触るか）」を判断する。
- 同時に進めるのは `profile.md` の「同時進行の上限」まで。超える分は待たせる。
- 受け入れ条件が書かれていない Issue は拾わず、ユーザーに「受け入れ条件を書いてください」と返す。
- 拾ったら `gh issue edit <N> --add-label agent:in-progress --remove-label agent:ready`。

## 2. worktree と子スレッドを作る

- **T3 Code MCP がある場合**：T3 Code の worktree モードで子スレッドを作り、ブランチ名を `agent/<N>-<slug>`、起点を最新の `origin/main` にする。プロバイダーとモデルは `profile.md` の「プラン」の行に合わせる。最初のメッセージは `prompts.md` の「プラン依頼」。
- **T3 Code が worktree を作れない、または手動モードの場合**：

  ```sh
  .agents/team/new-worktree.sh <N> <slug>
  ```

  表示されたパスで子スレッドを開く（手動モードではユーザーに開いてもらう）。
- 子スレッドの名前は `#<N> <slug>` にそろえる。

## 3. プラン（子スレッド）

子は `team-plan` スキルに従い、プランを最後のメッセージとして返して止まる。統括は子スレッドの結果を待って読む。

## 4. 衝突を調べて承認シートを作る

- 開いている agent の PR が触るファイル：

  ```sh
  gh pr list --state open --search "head:agent/" --json number,headRefName --jq '.[].number' \
    | xargs -r -I{} gh pr view {} --json number,files --jq '"#\(.number) " + ([.files[].path] | join(" "))'
  ```

- 進行中のほかの子スレッドのプランに書かれた「変更するファイル」と重ならないか。
- プランが `profile.md` の「触る前に承認が要る場所」や依存追加に触れていないか。
- プランが存在しないファイルやコマンドを前提にしていないか（`git ls-files`、`git grep` で確かめる）。

**承認シート**（ユーザーへ）：

```
## #<N> <タイトル>（<プロジェクト>）
やること：<2〜3行>
変えるファイル：<一覧>
確かめ方：<ゲートと追加の確認>
衝突：なし ／ #<PR>と<ファイル>が重なる → <提案する順番>
承認が要る点：<なければ「なし」>
決めてほしいこと：
  1. <判断点>（おすすめ：<案>、理由：<一言>）
→ 「承認」「差し戻し：<理由>」「順番：<指定>」で答えてください
```

## 5. ★ユーザーの承認

- 承認 → 6へ。
- 差し戻し → ユーザーの言葉を原文のまま子スレッドに渡し、3をやり直す。
- 承認されたプラン本文（判断点への答えを含む）は、実装依頼にそのまま貼る。

## 6. 実装用モデルへ切り替え

同じ子スレッドのまま、`profile.md` の「実装」の行の推論の強さに切り替える。モデル自体（Opus など）は変えない。モデルを変えるとそれまでの会話のキャッシュが使えず、会話全体を読み直すことになるため。プロバイダーをまたぐ切り替え（Claude→Codex）はしない。T3 Code が「プロバイダーの切り替えは文脈が欠ける」としているため。Codex を使う作業は `delegate_task` で別の子スレッドとして起動する。

## 7. 実装（子スレッド）

`prompts.md` の「実装依頼」を送る。子は `team-implement` スキルに従って draft PR を出し、PR番号と最新SHAを返す。

## 8. レビュー（Codex の子スレッド）

- `delegate_task` などで Codex の子スレッドを**同じ worktree**、読むだけの設定（サンドボックスは read-only）で起動し、`prompts.md` の「レビュー依頼」を送る。
- Codex が使えないとき（上限・障害）：Claude の別スレッドに `team-review` を実行させ、レビュー担当が Claude だったことを PR 本文に書く。実装したスレッドに自分のレビューはさせない。

## 9. ★指摘の取捨

**指摘シート**（ユーザーへ）：

```
## #<N> レビュー結果（PR #<PR>、SHA <短縮SHA>）
| ID | 重大度 | 場所 | 指摘 | レビュー役の提案 | 統括の意見 |
|----|--------|------|------|------------------|------------|
| R1 | blocker | file:line | … | … | 直す（理由） |
→ 各IDに「直す」か「見送る：<理由>」で答えてください（まとめて「全部おすすめどおり」も可）
```

- 統括の意見は付けてよいが、決めるのはユーザー。blocker を「見送る」にするときは、影響を一言添えて確認する。
- ユーザーの答えは原文のまま子スレッドに渡す。

## 10. 修正と ready（子スレッド）

`prompts.md` の「修正依頼」を送る。子は直す → ゲート → push → PR本文の「レビュー対応」を更新する。統括は 11 の確認が済んでから `gh pr ready <PR>` を指示する（子が実行する）。

## 11. 確かめて完了報告

```sh
gh pr view <PR> --json number,state,isDraft,headRefName,headRefOid,body,statusCheckRollup,files
```

- `headRefOid` が子の報告した最新SHAと一致する。
- ゲートの結果が最新SHAに対するものである。GitHub上のチェック（`statusCheckRollup`）があれば成功している。
- PR本文に「変更理由・確認結果・未確認事項・レビュー対応」がある。画面を変えたPRには PC とスマホの画像がある。
- 変更ファイルが承認されたプランの範囲に収まっている。

**完了報告**（ユーザーへ）：

```
## #<N> 準備完了：PR #<PR>（SHA <短縮SHA>）
ゲート：成功（<実行したコマンド>）
品質の記録：ゲート初回 成功／失敗、修正の往復 <n>回、レビュー blocker <n>・major <n>、差し戻し <n>回
未確認：<実機・本番など、確かめていないこと>
マージしたときの影響：<例：koshi-town は main へのマージで公開サイトに反映される>
→ マージ・レビュアー指定などはご判断ください
```

## 12. ★マージ

統括と子はマージしない。ユーザーがマージしたら、統括は `git worktree remove <パス>`（`--force` なし）で後片付けし、Issue の `agent:in-progress` を外す。worktree に未コミットの変更が残っていて消せないときは、消さずにユーザーへ報告する。

## ラベル

| ラベル | 意味 |
|--------|------|
| `agent:ready` | 拾ってよいタスク（ユーザーが付ける） |
| `agent:in-progress` | 統括が進行中 |
| `agent:needs-human` | 止まっていて、ユーザーの判断待ち |

## 定期実行（任意）

T3 Code のスケジュール機能で「`/agent-team` 手順1〜4だけ実行し、承認シートを作って止まる」を平日朝などに登録できる。手順5以降は必ずユーザーの返事を待つ。最初に `agent:ready` の件数だけを確かめ、0件ならすぐ終わる（空回りで使用量を減らさない）。
