# 精度を落とさずに使用量を減らす

## 大原則

1. **精度・安全・検証は削らない**。ゲート、テスト、レビュー、承認の手順、プランやレビューのモデルと推論の強さは、この節約の対象外。
2. 減らすのは「答えの質に効いていない入力」だけ。使用量は、毎回送る会話全体の長さ・キャッシュの作り直し・やり直しの回数で大きく増える。
3. モデルや推論の強さを下げることは、**測って同等と確かめた役割だけ**、ユーザーの承認を得てから行う（下の「下げる前に測る」）。

## いつも守ること（質に影響しないもの）

### 会話を短く保つ

- **1スレッド1タスク**。終わったタスクのスレッドで別の作業を始めない。
- 統括は会話に状態をためない。タスクの状態は GitHub（ラベル・Issue・PR）と子スレッドにあり、いつでも読み直せる。統括スレッドが長くなったら（目安：タスク3件の完了ごと、または1日の終わり）、新しいスレッドで `/agent-team` を始め直す。
- 子スレッドの結果は「待つ」ツールで1回受け取る。短い間隔で何度も読みに行かない（読みに行くたびに会話全体が送られる）。
- 中継は要点だけにする。ただしユーザーの答えは原文のまま渡す（短くしない）。

### キャッシュを壊さない

Claude Code は会話の先頭部分をキャッシュして安く読み直す。次の操作はキャッシュを作り直させるので、**タスクの途中ではしない**：

- 1つのスレッドの中でのモデルの切り替え（Opus ⇄ Sonnet など）。規模「中」「大」のプラン→実装は同じモデルのまま推論の強さだけを変える（Opus 5.5 では推論の強さを変えてもキャッシュは保たれる）。規模「小」は、プランのスレッドを切り替えずに Sonnet の新しいスレッドで実装する（`.agents/team/profile.md`）
- MCP サーバーやプラグインの追加・削除、ツールの丸ごとの禁止
- fast mode をオンにすること（Codex の fast／ultrafast も使用量が数倍になるので使わない）
- 長い中断。続きがある作業は、まとまった時間に一気に進める

### 読む量を絞る（必要なものは確実に読む）

- まず `git ls-files`・`git grep -n`・`git diff --stat` で場所を特定し、関係する範囲を読む。関係のないフォルダー（`prototypes/review/` の動画・画像、`dist/assets/`、`node_modules`、生成物）は読まない。
- 一度読んだファイルは、変更されていなければ読み直さない。
- 画像（スクリーンショット）は確認に必要な分だけ見る。同じ画像を何度も開かない。
- MCP より CLI（`gh`、`git`）を使う。使っていない MCP サーバーは無効にしておく（ユーザーの設定）。

### やり直しを減らす

- 受け入れ条件があいまいな Issue は、プランの前にユーザーへ確かめる（作り直しがいちばん高くつく）。
- 実装中は、関係するテストだけを先に回してよい（例：`pytest tests/test_x.py -q`、`node tests/frontend/x.test.mjs`）。**PR の前と修正のたびには必ず `gate.sh` を全部通す**。
- 失敗ログは貼り付けず、失敗したテスト名と最初のエラーだけを要約する（原因の調査に必要な行は省かない）。
- 同じ失敗が2回続いたら止まる（`agent-team/references/quality.md`）。

### 定期実行を空回りさせない

- スケジュールで `/agent-team` を回すときは、最初に `gh issue list --label agent:ready` の件数だけを見る。0件ならそこで終わる。

## 下げる前に測る（モデル・推論の強さ）

既定の設定（`.agents/team/profile.md` の「役割とモデル」）は変えない。変えたいときは次の手順で、**1回に1か所だけ**試す。

1. 候補を1つ決める（例：統括を Opus から Sonnet にする）。プラン・実装・レビューの判断を担う役割は、統括より後に検討する。
2. 変える前の直近5タスク以上について、完了報告の「品質の記録」を集める。
3. 変えた後の同じ件数のタスクで、同じ記録を集める。
4. **どれか1つでも悪くなったら元に戻す**：ゲートの初回成功、修正の往復回数、レビューの blocker・major の件数、プランの差し戻し、ユーザーが見つけた漏れ。
5. 件数が少ないうちは差が偶然の可能性が大きい。「悪くなっていない」は「同等が証明された」ではないので、採用はユーザーが決める。

## 使用量の点検（週に1回）

ユーザーに次を頼み、結果を見て「無駄の原因」を1つずつ減らす。

- **Claude Code**：`/usage` を開き、`w` で7日分を表示する。スキル・サブエージェント・MCP ごとの割合と、提案（例：「CLAUDE.md を短くする」）を確認する。`Prompt cache (main)` の行で、キャッシュから読めた割合と取りこぼしの理由を見る。
- **Codex**：CLI では `/status` で残りを確認する。使用量のダッシュボードで週の推移を見る。
- 点検の結果、設定を変えるときは上の「下げる前に測る」に従う。

## 統括の完了報告に足す行

```
品質の記録：ゲート初回 成功／失敗、修正の往復 <n>回、レビュー blocker <n>・major <n>、差し戻し <n>回
```
