# 承認されたプランを実装して draft PR を出す

## 始める前に

1. `AGENTS.md` と `.agents/team/profile.md` を読む。
2. 作業場所を確かめる：`git rev-parse --show-toplevel` が自分の worktree、`git branch --show-current` が `agent/<Issue番号>-...`。違えば止まって報告する。**ほかのタスクの worktree やブランチには書き込まない**。
3. 依頼に「承認されたプラン」が含まれていることを確かめる。なければ実装せずに止まる。

## 実装

- **プランの範囲だけを変える**。範囲の外を変える必要が出たら、変える前に止まって、理由と追加で変えたいファイルを統括に返す。
- 差分は最小にする。関係のない整形・名前変更・ファイル移動をしない。既存の書き方に合わせる。
- ファイルの一部を変えるときは、全体を書き直さず該当箇所だけを編集する。
- 存在を確かめていないファイル・関数・パッケージ・コマンドを使わない。依存パッケージを追加しない（プランで承認されていても、インストールはユーザーが行う）。
- テストを消す・skip にする・期待値を実装に合わせて書き換えることはしない。仕様が変わる場合は、プランで承認されていることを確かめてからテストを更新する。
- 秘密情報（`.env`、キー、トークン、環境変数の値）を読まない・書かない・表示しない。

- 読み方とやり直しの減らし方は `.agents/skills/token-budget/SKILL.md` に従う。実装中は関係するテストだけを先に回してよいが、PR の前と修正のたびには下のゲートを必ず全部通す。

## ゲート

```sh
.agents/team/gate.sh
```

- 成功するまで PR を出さない。失敗したら `agent-team/references/quality.md` の基準に従う（同じ理由で2回失敗したら止まる）。
- `profile.md` に「追加の確認」があれば、それも実行する。実行できなかったものは「未確認事項」に書く。

## コミット

- 意図を説明できる小さな単位でコミットする。
- 1行目：`<種類>: <日本語の要約>`。種類は `feat` `fix` `refactor` `test` `docs` `chore` のどれか。
- 本文の最後に `Refs #<Issue番号>` を入れる。
- `--no-verify`・`--amend`（push済みのもの）・履歴の書き換えはしない。

## draft PR

```sh
git push -u origin HEAD
gh pr create --draft --base main --title "<種類>: <要約> (#<Issue番号>)" --body-file <本文ファイル>
```

本文ファイルは worktree の外（例：`$(mktemp)`）に作り、コミットしない。本文の書式：

```
Closes #<Issue番号>

## 変更理由
## 承認されたプランの要約
## 変更内容
## 確認結果
- ゲート：成功（<コマンド>、SHA <短縮SHA>）
- <追加の確認と結果>
## 未確認事項
## 画面の変更（画面を変えたときだけ。PC・スマホの画像）
## レビュー対応
（レビュー後に追記）
---
実装：<プロバイダー／モデル>　レビュー：<未実施>
```

終わったら、PR番号・最新のコミットSHA・ゲートの結果・未確認事項を返す。

## 修正（レビュー後）

- ユーザーが「直す」にした指摘だけを直す。「見送る」は変更しない。
- 直したら、ゲート → コミット → `git push` → PR本文の「レビュー対応」を更新（`gh pr edit <PR> --body-file <ファイル>`）。

  ```
  ## レビュー対応
  | ID | 決定 | 対応 |
  | R1 | 直す | <何をどう直したか、SHA> |
  | R2 | 見送る | <ユーザーの理由> |
  ```

- `gh pr ready` は統括から指示があったときだけ実行する。
- マージはしない。
