# AIチームの設定：おまちどう（SawaiKoshi/omachi-do）

飲食店の待ち時間予測。データ品質監査・前処理・モデル比較、予測API、受付・スタッフ画面、SQLite の受付記録。

## 役割とモデル

| 役割 | プロバイダー | モデル・推論の強さ | 権限 |
|------|--------------|--------------------|------|
| 統括 | Claude Code | Opus・high | 読む・`gh`（Issue のラベル、PR の確認）。コードは書かない |
| プラン | Claude Code（通常モード） | Opus・いちばん強い設定 | 読むだけ（依頼文の指示で守らせる） |
| 実装（規模「小」：テストの追加・小さな修正） | Claude Code（実装用の新しいスレッド） | Sonnet・high | 自分の worktree の編集、コミット、自分のブランチへの push、draft PR |
| 実装（規模「中」「大」） | Claude Code（プランと同じスレッド） | Opus・medium | 同上 |
| レビュー | Codex | 最新のコーディング向けモデル・high | read-only サンドボックス。読むだけ |

- モデル名は T3 Code のモデル選択に表示されている名前を使う。ここに書いた名前がなければ、いちばん近いものを選び、統括の報告に書く。
- プランの子スレッドは**プランモードで起動しない**。通常モードで起動し、「ファイルを変更しない」は依頼文で指示する。プランモードで起動すると、ExitPlanMode で抜けられず、同じスレッドで実装に進めないことがあるため（#14 で発生）。
- 実装の規模（小／中／大）はプランの「規模」をもとに統括が承認シートに書き、使うモデルとあわせてユーザーが承認する。迷うときは「中」として Opus にする。
- Codex が使えないとき：レビューは Claude Opus（high）の別スレッドで行い、PR 本文にそう書く。プラン・実装と同じスレッドにはさせない。Claude が使えないとき：実装は Codex（workspace-write、承認は都度確認）で行う。
- 規模「小」の実装を Sonnet にするのは、2026-11-26 のユーザーの決定（#17）。採用後も完了報告の「品質の記録」を見続け、ゲートの初回失敗・修正の往復・レビューの blocker／major が Opus のときより増えたら、統括がユーザーに報告する。

## 使用量（Claude Pro・ChatGPT Pro）

- 節約の決まりは `.agents/skills/token-budget/SKILL.md`。精度・検証に関わる設定（上の表のモデルと推論の強さ、ゲート、レビュー）は節約の対象にしない。
- 規模「中」「大」：プラン→実装は同じスレッドで **モデルは Opus のまま**、推論の強さだけを変える（モデルを変えるとキャッシュが使えなくなる）。
- 規模「小」：プランのスレッドのモデルは切り替えず、Sonnet の実装用の新しいスレッドを起動して、承認されたプランとユーザーの答えを原文のまま渡す。
- Codex のレビューはローカルのスレッドで行う（クラウドのタスクは使用量が多くなりやすい）。fast／ultrafast は使わない。
- Claude Pro では5時間ごとの上限に近づきやすいので、同時進行は1タスクから始める。
- 表のモデル・推論の強さを下げたいときは、`token-budget` の「下げる前に測る」で同等と確かめ、ユーザーが決める。

秘密情報、空白エラー、実データ・モデル成果物の混入、`pytest -q -W error`、`tests/frontend/*.test.mjs`、`web/` の JavaScript の構文。

## 触る前にユーザーの承認が要る場所

- `reception_migration/`、`reception_schema.py`、`reception_store.py` の保存形式（スキーマ移行）
- `requirements-*.txt`（依存の追加・更新。インストールもユーザーが行う）
- 実データ（`*.xlsx` など）、`var/`、`models/`、学習済みモデル。**実データを読み込むコマンド（`step1_audit.py` など）を実行しない**
- 認証・HTTPS の入口（`staff_*https_lab.py`、`staff_sessions.py`）とポート・待受設定
- 決まっている業務規則・品質境界を変えること（`docs/adr/` の採用済み ADR と食い違う変更）

## 例外ケースの観点（レビューで1つずつ確かめる）

- 時刻：23:00 を超える受付・案内、案内が受付より前（時刻逆転）、日付またぎ、分単位の丸め
- 人数：大人＋子供と合計の不一致、0人・負の数・小数・非常に大きい値
- 取消・重複・欠損・変換できない値（`valid` 以外の状態の扱い）
- SQLite：同時の書き込み、再送・二重送信、途中で失敗したときの記録
- API：不正な入力、存在しない ID、認証なしのアクセス
- 画面：通信失敗・再送・一覧の更新、スマホ幅、キーボード操作
- 入力の DataFrame を書き換えていないこと（不変性）

## 進め方の決まりごと

- 同時進行の上限：2タスク
- 判断の記録は `docs/adr/ADR-xxxx.md`、操作手順は `README.md`
- テストは合成データと `tmp_path` だけを使う（既存の方針）
